# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

HotspotFreeRAD (a.k.a. MMS Radius) is a multi-tenant SaaS for MikroTik hotspot/PPPoE billing built on Laravel 12 + Livewire 4 + Flux/Flux Pro, backed by FreeRADIUS 3 over a shared MySQL/MariaDB `radius` database. Tenants (ISPs/hotspot shop owners) manage shops, routers, packages, customers, vouchers, PPPoE subscribers, and POS devices; customers pay through a MikroTik captive portal to get provisioned into FreeRADIUS.

Read `docs/current-project-status.md` first in any new session — it is the up-to-date handover doc (stack, local dev quirks, deployment steps, "next good work"). `docs/roles-and-product-direction.md`, `docs/deployment-architecture.md`, `docs/router-onboarding.md`, and `docs/raspberry-pi-deployment.md` cover product rules and infra in depth. `README.md` and the root blueprint markdown are older/less current than `docs/current-project-status.md` — prefer the docs folder when they conflict.

## Commands

Local dev runs on port **8001** (other local projects use 8000):

```bash
php artisan serve --host=127.0.0.1 --port=8001
npm run dev            # Vite
```

Or run everything (server, queue listener, logs, vite) at once:

```bash
composer run dev
```

Tests:

```bash
php artisan test                                  # full suite
php artisan test --filter=AdminPaymentIndexTest    # single test class
php artisan test tests/Feature/HotspotPortalTest.php
```

Test env uses in-memory SQLite (`phpunit.xml`), not the real `radius` MySQL DB — safe to run anytime.

Build/lint:

```bash
npm run build          # production assets
vendor/bin/pint         # Laravel Pint code style (composer require-dev)
```

Useful recovery/maintenance commands (see `docs/current-project-status.md`):

```bash
php artisan optimize:clear
php artisan migrate
```

Custom Artisan commands live inline in `routes/console.php` (there is no `app/Console/Commands` directory — this is a Laravel 12 skeleton app). Notable ones: `hotspot:create-super-admin`, `hotspot:create-tenant-admin`, `hotspot:sync-expired-hotspot`, `hotspot:sync-expired-pppoe`, `hotspot:sync-expired-pos`, `hotspot:prune-security-activity`, `hotspot:backfill-voucher-payments`, `hotspot:scheduler-heartbeat`, `hotspot:sync-wireguard-peers`, `hotspot:resync-walled-garden`. All but the first three are also registered on `Schedule::` in the same file (5-minute RADIUS expiry sync, 5-minute WireGuard peer sync, daily audit-log prune, per-minute scheduler heartbeat used by the Setup Center health check) — `hotspot:backfill-voucher-payments` and `hotspot:resync-walled-garden` are the exceptions, both on-demand-only (a one-off backfill and a manual remediation tool, respectively).

`hotspot:resync-walled-garden {router?} {--all}` re-pushes a router's walled-garden allow-list live over the RouterOS API, synchronously (unlike `SyncRouterWalledGarden` below, it doesn't need a queue worker running) — useful for immediately fixing an already-provisioned router without waiting on a gateway change to trigger the automatic job, or when `QUEUE_CONNECTION=database` locally and no worker is running to drain it.

## Architecture

### Two separate traffic paths — keep them mentally distinct

1. **Customer captive-portal path**: customer device → MikroTik → HTTPS redirect → `App\Http\Controllers\Hotspot\PortalController` (`routes/web.php`, `/hotspot/*`) → payment gateway → RADIUS provisioning.
2. **Router auth/accounting path**: MikroTik → WireGuard tunnel → FreeRADIUS 3 → the same MySQL `radius` database (`nas`, `radcheck`, `radreply`, `radacct`, `radusergroup`, `radgroupreply`, `radgroupcheck` tables). Laravel never proxies RADIUS traffic itself — it only writes rows FreeRADIUS reads.

`App\Services\RadiusProvisioningService` and `App\Services\MikroTikProvisioningService` are the bridge: package/subscriber changes in the app get mirrored into the `radcheck`/`radusergroup`/`radgroupreply`/`nas` tables, and router onboarding generates a RouterOS script from stored provisioning settings.

`App\Services\StandaloneHotspotScriptGenerator` (2026-08-07, revised 2026-08-08) is a deliberately separate, unrelated code path — the "Script Generator" tool at `admin/tools/script-generator` (super admin only, gated by `abort_unless($request->user()->isSuperAdmin(), 403)` in `StandaloneScriptGeneratorController` the same way `TenantController`/`SecurityController` are). It generates a MikroTik hotspot config for routers that are **not**, and don't need to become, a `Router` record on this platform: no WireGuard, no HotspotFreeRAD RADIUS server, no API user, no shop/tenant binding. It branches on RouterOS 6 vs 7 wireless syntax (`/interface wireless` vs `/interface wifi`/wifiwave2) and wireless-vs-wired-only hardware via plain capability toggles in the wizard (`App\Livewire\Admin\StandaloneScriptGenerator`, a 5-step form) rather than a hardcoded router-model catalog — deliberately, since a real model database would need ongoing upkeep as new MikroTik boards ship. Every Ethernet port except the WAN port is bridged into the hotspot automatically (`ethernet_port_count` wizard field, parsed against `wan_port`'s trailing number), and "Router identity" (`/system identity`) is a separate wizard field from "Hotspot name" (the SSID/portal branding) since they're not always the same string. The whole flow is stateless: nothing is persisted, the wizard's Livewire state holds everything, and the result page renders both the copyable/downloadable `.rsc` script and a printable voucher sheet (`voucher_template`: `grid`, `compact`, or `receipt`) in one response via `@media print` CSS — there was no reason to add a database table for something meant to be filled in, generated, and printed/copied in one sitting.

Voucher validity is designed to start counting from a customer's **first login**, not from when the voucher was created — a real gap in the original version, fixed after specific network-engineer feedback plus MikroTik doc research. RouterOS 7 uses the built-in User Manager (`/user-manager`) as a **self-hosted local RADIUS server** pointed at `127.0.0.1` (never leaves the router, so this doesn't reintroduce a platform dependency) — its `profile.starts-when=first-auth` is the officially documented way to do this, and User Manager's richer object model (`limitation` / `profile` / `profile-limitation` / `user-profile` / `user` are five distinct objects, not one) is used deliberately instead of classic `/ip hotspot user profile`. RouterOS 6 has no equivalent, so classic hotspot users are used with an `on-login` script (`StandaloneHotspotScriptGenerator::onLoginExpiryScript()`) bound to the hotspot server profile that creates a one-time scheduler on a user's first login and removes the account when their validity window elapses — a well-established community pattern, not an official RouterOS feature, so it's commented as best-effort the same way other unverified RouterOS syntax is elsewhere in this codebase. Voucher codes support an optional prefix, configurable length, a choice of character set (`StandaloneHotspotScriptGenerator::CHARACTER_SETS` — safe alphanumeric, numeric-only, letters-only, or full case-sensitive), and whether the username and password should be the same or independently generated (`voucher_prefix`/`voucher_code_length`/`voucher_character_set`/`voucher_username_password_same`, all per profile) — mirroring MikroTik's own "Make Vouchers"/batch-user dialog shape (which has separate username-characters/password-characters options). `generateVoucherCodes()` returns `username`/`password` per voucher rather than a single `code`, and both script paths (`userManagerLines()`/`classicHotspotLines()`) and the print templates were updated accordingly — a print card shows one combined line when they're equal, or separate "User:"/"Pass:" lines when they're not.

When the management network is enabled, the generated script also restricts the router's own `www`/`www-ssl`/`winbox`/`ssh` services to that subnet (`/ip service set ... address=<mgmt-cidr>`) — this was originally going to be a custom "web Winbox" page built into this platform, but RouterOS's REST API sends no CORS headers (so a browser can't call it cross-origin from another domain) and a standalone router with no WireGuard tunnel isn't reachable from this app's backend at all. The better, lower-maintenance answer is to properly lock down and point admins at RouterOS's *own* built-in web tools (WebFig, and on v7 the User Manager page at `https://<router-mgmt-ip>/userman`) rather than rebuild them.

Router-to-Pi WireGuard connectivity is app-managed, not manual: `App\Models\Router` auto-generates a WireGuard keypair on creation (`App\Support\WireGuardKeyPair`, via `paragonie/sodium_compat` so it works without the native sodium extension), the private key is baked into the generated script instead of letting RouterOS pick its own, and `App\Services\WireGuardPeerSyncService` (run via the `hotspot:sync-wireguard-peers` scheduled command) reconciles the Pi's live WireGuard peers from the `routers` table. That command is inert everywhere by default (`WIREGUARD_MANAGE_PEERS=false`) and only does anything once enabled on the Pi per `docs/wireguard-server-setup.md`.

Staff/Management Wi-Fi (WPA-PSK SSIDs, distinct from the open customer hotspot) gets a second access control layer beyond the shared password: `App\Models\TrustedWifiDevice` (admin: `admin/trusted-wifi-devices`) registers devices by MAC per shop/network (`staff`|`mgmt`), synced into `radcheck` via `RadiusProvisioningService::provisionTrustedWifiDevice()`. For the MikroTik built-in Wi-Fi test profile (`l009_builtin_wifi`), the script generator also emits a local `/interface wifi access-list` allow/deny list from the same registered devices — regenerated on demand, not live-pushed to the router. See `docs/staff-wifi-access.md` for the external-AP RADIUS MAC-auth path and its current limitations.

Live router monitoring (as opposed to the WireGuard/RADIUS provisioning above) needs to talk to the router directly, not just write RADIUS rows. `App\Models\Router` also auto-generates a RouterOS API user/password on creation (`api_username`/`api_password`, mirroring the WireGuard keypair pattern), baked into the generated scripts by `MikroTikProvisioningService::apiUserProvisioningLines()` and restricted to the WireGuard subnet only. `App\Services\RouterOsConnectionService` (wrapping `evilfreelancer/routeros-api-php`, which needs `ext-sockets`) is the single place that opens a live RouterOS API connection, always with short timeouts so an offline router fails fast instead of hanging a request. Historical bandwidth graphs (`App\Support\RouterUsageHistory`) need none of this — they read existing `radacct` data. CPU/RAM/disk/health/uptime history (`router_metric_samples`, populated every 5 minutes by `hotspot:sample-router-metrics` / `App\Services\RouterMetricSamplingService`) mixes both: latency is a plain ICMP ping needing no RouterOS API at all, while CPU/RAM/disk/health do. Router health alerts (`App\Notifications\RouterAlertNotification`, `implements ShouldQueue`) fire from state *transitions* detected in `RouterMetricSamplingService` (offline/online/high CPU/high RAM) — edge-triggered, not repeated every sample while a condition persists. In-system (database) delivery is always on; email is gated per-user by `User::notify_by_email` inside `via()`. Recipients are every super admin plus the tenant admins of the router's tenant. Being queued, delivery goes through the existing persistent `hotspotfreerad-worker` systemd service (`docs/raspberry-pi-deployment.md`), not a cron-triggered send. See `docs/router-monitoring.md`, including the honest caveats on Wi-Fi scan session cleanup, hardware-health field variability, and the topology view's deliberately-limited scope (org hierarchy, not physical LLDP discovery).

The API user's group policy used to be `read`-only (deliberately denying `write`) since it was originally scoped just for monitoring — but `RouterOsConnectionService::provisionHotspot()`/`provisionPppoe()`/`syncWalledGarden()` all issue genuine write commands (`/radius/add`, `/ip/hotspot/*/add`, `/ip/hotspot/walled-garden/add`), which RouterOS silently rejected under that policy. Compounding it, `evilfreelancer/routeros-api-php`'s `Client::read()` parses a RouterOS `!trap` (rejected command) identically to `!done` (success) and never throws — so `RouterOsConnectionService::runSteps()`/`applyHotspotProfile()` reported every one of those rejected writes back to the admin as a success ("walled garden synced" with nothing actually changed on the router). Found 2026-08-07 from a live report of "Provision via API" appearing to succeed with no effect on the physical router. Fixed both halves: the policy now grants `write` (`apiUserProvisioningLines()`), and `runSteps()`/`applyHotspotProfile()` now call `read(false)` (raw, unparsed) and check for a `!trap` block via the new `RouterOsConnectionService::extractTrapMessage()` before reporting a step successful. A router bootstrapped before this fix needs its script re-run (or just the `/user group set` policy line re-applied) before any API write will actually take effect — `hotspot:resync-walled-garden` (see Commands) is the quickest way to re-push and get an honest success/failure result now.

### Tenant scoping is manual, not a global scope

There is no Eloquent global scope for tenancy. Every tenant-scoped query/authorization goes through the static helpers in `app/Support/TenantAccess.php` (`scopeShops`, `scopeRouters`, `scopePackages`, `assertShop`, `assertRouter`, etc.), each of which special-cases `$user->isSuperAdmin()` to bypass the `tenant_id`/`shop.tenant_id` filter. When adding a new tenant-owned resource, add a matching `scopeX`/`assertX` pair here rather than filtering ad hoc in the controller. Controllers also gate super-admin-only actions with inline `abort_unless(request()->user()->isSuperAdmin(), 403)` (e.g. `TenantController`) — this stays true for `super_admin` vs `tenant_admin`. **`TenantAccess` answers "which rows can this actor see," not "can this actor perform this action"** — that second question is what the `tenant_staff` role below needs, and it's a separate mechanism.

Three roles: `super_admin` (platform owner, no `tenant_id`), `tenant_admin` (full access to one `tenant_id`), and `tenant_staff` (scoped to one `tenant_id` like `tenant_admin`, but further restricted to specific feature areas). Staff authorization is the one place this codebase DOES use route-level middleware: `App\Http\Middleware\AuthorizeTenantStaff` wraps the entire `admin.*` route group in `routes/web.php` and checks each request's route name against the deny-by-default map in `App\Support\StaffPermissions::forRoute()` (`User::canAccessRoute()` is the model-side helper it and the sidebar nav both call). Super admin and tenant admin are unaffected — the middleware is a no-op for them. When adding a new admin route that staff should ever reach, it needs a deliberate entry in that map; nothing is allowed by default. See `docs/roles-and-product-direction.md` for the full rule set and the permission catalog.

### Request flow: thin controllers, fat services

`app/Http/Controllers/Admin/*` and `app/Livewire/Admin/*` stay thin and delegate business logic to `app/Services/*ManagementService.php` (e.g. `PackageManagementService`, `RouterManagementService`, `PppoeSubscriberManagementService`, `PosDeviceManagementService`, `VoucherManagementService`). Reporting has its own service layer (`SalesReportService`, `PaymentReportService`, `SubscriptionReportService`, `SecurityActivityReportService`). Livewire is used for interactive index/filter/table components; plain controllers handle CRUD resources and exports.

The real, tenant-bound router create/edit form (`admin/routers` — not the unrelated standalone script generator) is a 4-step wizard on `App\Livewire\Admin\RoutersIndex` (2026-08-08), not a single flat form: Identity, Hardware (wireless yes/no + port count/roles), Features (POS/PPPoE/QoS + conditional wireless credentials), Network plan. `App\Http\Controllers\Admin\RouterController::create()`/`edit()` now just redirect into this wizard (`?open=create` / `?open_edit={id}`) instead of rendering their own page — the old parallel full-page form (`admin/routers/form.blade.php`) was deleted since maintaining a second, independently-drifting implementation of the same step-gated/conditional form wasn't worth it; `store()`/`update()` and `RouterManagementService::validated()` are kept as-is for non-Livewire regression coverage, just no longer linked from the UI. Wireless-only fields (`builtin_wifi_interface`, `mgmt_wifi_password`, `staff_wifi_password`, `pos_wifi_password`) and POS/PPPoE network fields only render when their matching `enable_*` toggle is on, backed by `required_if` rules in `RouterManagementService::rules()` so they can't be saved blank while enabled.

Ports are no longer typed as raw interface-name strings by default — `App\Support\RouterPortLayout` (pure, static, framework-free) turns a `port_count` into numbered dropdown options (`portOptions()`) and reverse-derives a port number from an existing `"etherN"` string (`portNumberFromInterfaceName()`, returns `null` for anything that doesn't match, e.g. `sfp-sfpplus1`). `RouterManagementService::derivePortInterfaceNames()` converts `wan1_port_number`/`wan2_port_number`/`trunk_port_number`/`pi_port_number` into the `wan1`/`wan2`/`trunk_port`/`pi_port` strings `MikroTikProvisioningService` actually reads — that service needed zero changes, since it still just reads plain interface-name strings. An "advanced: type interface names manually" toggle (`ports_advanced_mode`) bypasses all of this for non-standard interfaces. On edit, `RoutersIndex::routerProvisioningSettings()` reverse-derives port numbers from a router's saved strings so the dropdowns open pre-selected; if any of the four doesn't cleanly parse, it opens in advanced mode instead of guessing wrong — and a router that's never re-edited keeps generating byte-identical scripts, since the derivation only overwrites a string when its `*_port_number` was actually submitted (a real bug caught during this work: `RouterManagementService::validated()` used to call `normalize()` and then `create()`/`update()` called it *again*, so the second pass saw the first pass's defaulted port number as if it had been explicitly submitted and clobbered manually-typed strings like `sfp-sfpplus1` — fixed by making `validated()` return unnormalized data and letting `create()`/`update()` be the single normalization point).

The `provisioning_settings.profile` preset used to include `l009_builtin_wifi`, a preset literally named after a specific MikroTik board — removed in favor of the independent `enable_builtin_wifi` toggle (any of the remaining `starlink_plaza`/`small_hotspot`/`pppoe_isp` bandwidth/VLAN templates can have wireless on or off now). A data-only migration (`2026_08_07_120000_remap_l009_builtin_wifi_router_profile.php`) rewrites just the `profile` key on already-saved rows to `small_hotspot`, leaving every other field (`wan1`/`wan2`/`enable_builtin_wifi`/etc.) untouched — those were already fully materialized per-row at save time, not re-derived from the profile string, so this is cosmetic for existing routers, not a behavior change.

### Payment gateways

Two independent gateway stacks exist, both selected/configured per entity via `App\Support\PaymentGatewayCatalog`:

- **Tenant/shop-level hotspot checkout** (customer paying for hotspot/PPPoE/POS access): `FlutterwaveService`, `PaystackService`, `MonnifyService`, `SquadService`, `StripeService`, `ManualBankTransferService`, orchestrated by `App\Services\Payments\HotspotHostedCheckoutManager` implementing `App\Services\Payments\Contracts\HotspotHostedGateway` per provider, confirmed via `HotspotPaymentConfirmationService`. Entry points are the `/hotspot/pay`, `/hotspot/payment/*` routes on `PortalController`.
- **Platform billing** (tenant paying HotspotFreeRAD for their subscription plan): `PlatformFlutterwaveService`, `PlatformStripeService`, confirmed via `PlatformBillingConfirmationService`. Entry points are the `/billing/*` routes on `Admin\BillingController`.

Webhook routes (`/hotspot/payment/webhook`, `/billing/payment/webhook`) are explicitly excluded from CSRF (`withoutMiddleware([ValidateCsrfToken::class])`) since gateways POST to them directly — keep that exclusion narrow if adding new webhook routes.

A shop has exactly one active gateway at a time (`Shop::paymentGateway()`, defaults to `flutterwave`), not a menu of simultaneously-enabled gateways — `resources/views/hotspot/portal.blade.php` reads it directly (`$shop->paymentGatewayName()`/`paymentGatewayLogoUrl()`) to show the customer which gateway they're paying through, and only Flutterwave gets the OPay/Transfer/Card sub-choice (the other gateways route through `HotspotHostedCheckoutManager` regardless of `payment_method`). Because 5 of the 6 gateways redirect the customer's browser to an external hosted checkout domain *before* the device is RADIUS-authenticated, each gateway also carries `walled_garden_hosts` metadata in `PaymentGatewayCatalog` — `MikroTikProvisioningService::walledGardenLines()` emits `/ip hotspot walled-garden add dst-host=...` entries for the router's shop's active gateway (plus the portal host and `*.cloudflare.com`) in both `generateScript()` and `generateFreshInfrastructureScript()`. Those host lists are best-effort, based on each provider's known public checkout domains — not verified against a live checkout flow from this codebase.

A router whose walled-garden entries don't cover its shop's active gateway fails checkout hard, not gracefully: MikroTik can rewrite the captive-portal login redirect into unencrypted HTTP responses, but for HTTPS destinations outside the walled garden it can't inject anything into the encrypted stream, so it resets the connection instead — the customer sees `net::ERR_CONNECTION_CLOSED` at "Continue to payment" rather than a redirect to login. This only self-heals on routers that get a fresh script paste or a manual "Provision via API" click; a shop that switches gateways without re-provisioning its routers silently breaks checkout (diagnosed 2026-08-07 from a live Squad report — Squad's own domains were already covered by the `*.squadco.com` wildcard, the router just never got the new gateway's entries pushed). Two fixes: `RouterOsConnectionService::provisionHotspot()`'s live API push now also walled-gardens the shop's active gateway (it previously only added the portal host, so even the manual remediation path was incomplete) via a new public `syncWalledGarden()` method it shares with the fix below; and `PaymentSettingsService::update()` now diffs the shop's `payment_gateway` before/after and, when it changed, dispatches `App\Jobs\SyncRouterWalledGarden` (queued, default queue — picked up by the existing Pi worker with no deployment change) for every router the shop owns, so switching gateways in Payment Setup re-syncs live routers automatically instead of requiring a manual re-provision.

`PaymentSettingsService::updates()` **merges** newly-submitted `gateway_settings` into a gateway's existing saved settings rather than replacing the sub-array wholesale (fixed 2026-08-06 — it used to silently wipe every field not resubmitted that save, e.g. losing a saved secret key just from switching the Environment dropdown, contradicting the form's own "leave blank to keep saved value" placeholder text). Any future gateway-settings save logic should keep this merge behavior.

All four online gateways (Squad, Monnify, Paystack, Stripe) carry an `environment` field in `PaymentGatewayCatalog`'s `select_fields` (`live`/`test`, defaulting to `test`) — a per-gateway field that renders as a `flux:select` in `PaymentSettingsCard` instead of a free-text credential input, is excluded from `tenantReadiness()`'s badges (it's a preference, not a "missing credential"), and is validated with a strict `Rule::in()` in `PaymentSettingsService` on top of the generic `gateway_settings.*` wildcard rule. It is only *functional* for Squad and Monnify, which have genuinely different API base URLs per mode: `SquadService`/`MonnifyService::baseUrl()` take `Payment $payment` and pick `config('services.<gateway>.live_base_url')` or `.base_url` (sandbox) based on the shop's saved `environment` — there's no platform-wide `.env`-only base URL forcing every tenant onto the same environment anymore.

Paystack and Stripe share ONE API host regardless of mode — the secret key's `sk_test_`/`sk_live_` prefix is the only thing that actually determines live vs test, so their `environment` field does not change any base URL; it's saved purely for the admin's own reference (2026-08-06, added after a user request for a consistent field across all four gateways). Because an independently-editable field can drift out of sync with the actual key (pick "Live" while a `sk_test_` key is still saved), `PaymentGatewayCatalog::detectedEnvironment(?string $secretKey)` derives the real live/test state straight from the key prefix, and `PaymentSettingsCard` shows it as a read-only badge ("Detected: Live key" / "Detected: Test key" / "Environment not detected") next to the Secret Key field, plus an inline warning under the Environment dropdown when the two disagree. `PaymentSettingsCard::KEY_DETECTED_ENVIRONMENT_GATEWAYS` is the list of gateways this detection applies to (currently `paystack`, `stripe`) — add a gateway there only if it shares this one-URL-plus-key-prefix shape.

`App\Livewire\Admin\PaymentSettingsCard` is the single place gateway credentials/environment are edited (2026-08-06) — it used to be duplicated as hardcoded Flutterwave-only fields on the separate Shops CRUD (`App\Livewire\Admin\ShopsIndex`'s edit flyout and `Admin\ShopController`'s full-page form), which had no way to configure Squad/Monnify/Paystack/Stripe at all despite letting you pick them as the active gateway. Both Shop edit surfaces now embed `<livewire:admin.payment-settings-card>` directly (as a sibling section after the shop-details `<form>`, never nested inside it — Livewire's own `<form wire:submit="save">` inside another `<form>` is invalid HTML) once the shop exists; `App\Services\ShopManagementService` was stripped down to just `tenant_id`/`name`/`location_city`/`is_active` accordingly. A shop must be saved once before its payment settings can be configured.

### Packages and RADIUS attribute mapping

Packages carry bandwidth, uptime, and optional data caps/FUP. When synced to RADIUS: `Mikrotik-Rate-Limit` = bandwidth, `Session-Timeout` = uptime (seconds), `Mikrotik-Total-Limit`/`Mikrotik-Total-Limit-Gigawords` = data quota. Data values are stored/compared in raw bytes (see unit table in `docs/roles-and-product-direction.md`). `NAS-Identifier` on the router must exactly match the router's stored identity — mismatches are the most common "router not registered" support issue.

### Expiry/cleanup model

Hotspot subscriptions, PPPoE subscribers, and POS devices are each revoked from RADIUS by a scheduled command (see Commands section) rather than by a live TTL in FreeRADIUS — the `Schedule::command(...)->everyFiveMinutes()` jobs in `routes/console.php` are what actually cut off expired access. If a feature depends on "access should end at time X," it needs a corresponding scheduled sync, not just an `expires_at` column.

## Known environment quirk

Local XAMPP MariaDB has previously hung due to a crashed `mysql.db` table; if the app hangs on load, check MySQL first and repair with `aria_chk` before assuming an app bug (see `docs/current-project-status.md`).

## Real infra values are not in this repo

`mondiison/hotspotfreerad` is a **public** GitHub repo, so real WireGuard endpoints, public keys, and RADIUS server IPs must never be committed here — the docs in `docs/` intentionally use placeholder values. The actual live values (WireGuard endpoint/port/public key, RADIUS server IP, known `.env` gotchas) are recorded locally in `.local-notes/infra-settings.md`, which is git-ignored. Check that file before re-deriving these from scratch or asking the user to repeat them; it only exists on this machine, not on the Pi or a fresh clone.
