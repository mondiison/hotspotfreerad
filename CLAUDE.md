# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

HotspotFreeRAD (a.k.a. MMS Radius) is a multi-tenant SaaS for MikroTik hotspot/PPPoE billing built on Laravel 12 + Livewire 4 + Flux/Flux Pro, backed by FreeRADIUS 3 over a shared MySQL/MariaDB `radius` database. Tenants (ISPs/hotspot shop owners) manage shops, routers, packages, customers, vouchers, PPPoE subscribers, and POS devices; customers pay through a MikroTik captive portal to get provisioned into FreeRADIUS.

Read `docs/current-project-status.md` first in any new session — it is the up-to-date handover doc (stack, local dev quirks, deployment steps, "next good work"). `docs/roles-and-product-direction.md`, `docs/deployment-architecture.md`, `docs/router-onboarding.md`, and `docs/raspberry-pi-deployment.md` cover product rules and infra in depth. `README.md` and the root blueprint markdown are older/less current than `docs/current-project-status.md` — prefer the docs folder when they conflict.

## Commands

Local dev runs on port **8001** (other local projects use 8000):

```bash
php artisan serve --host=127.0.0.1 --port=8001
npm run dev            # Vite
```

Or run everything (server, queue listener, logs, vite) at once:

```bash
composer run dev
```

Tests:

```bash
php artisan test                                  # full suite
php artisan test --filter=AdminPaymentIndexTest    # single test class
php artisan test tests/Feature/HotspotPortalTest.php
```

Test env uses in-memory SQLite (`phpunit.xml`), not the real `radius` MySQL DB — safe to run anytime.

Build/lint:

```bash
npm run build          # production assets
vendor/bin/pint         # Laravel Pint code style (composer require-dev)
```

Useful recovery/maintenance commands (see `docs/current-project-status.md`):

```bash
php artisan optimize:clear
php artisan migrate
```

Custom Artisan commands live inline in `routes/console.php` (there is no `app/Console/Commands` directory — this is a Laravel 12 skeleton app). Notable ones: `hotspot:create-super-admin`, `hotspot:create-tenant-admin`, `hotspot:sync-expired-hotspot`, `hotspot:sync-expired-pppoe`, `hotspot:sync-expired-pos`, `hotspot:prune-security-activity`, `hotspot:sample-router-metrics`, `hotspot:prune-router-metrics`, `hotspot:backfill-voucher-payments`, `hotspot:scheduler-heartbeat`, `hotspot:sync-wireguard-peers`, `hotspot:sync-wireguard-routes`, `hotspot:sync-zerotier-members`, `hotspot:auto-provision-routers`, `hotspot:resync-walled-garden`. All but the first three are also registered on `Schedule::` in the same file (5-minute RADIUS expiry sync, 5-minute WireGuard peer sync, 5-minute WireGuard route sync, 5-minute ZeroTier membership sync, 5-minute router auto-provisioning sync, 5-minute router metric sampling, daily audit-log prune, daily router-metrics prune, per-minute scheduler heartbeat used by the Setup Center health check) — `hotspot:backfill-voucher-payments` and `hotspot:resync-walled-garden` are the exceptions, both on-demand-only (a one-off backfill and a manual remediation tool, respectively).

`hotspot:resync-walled-garden {router?} {--all}` re-pushes a router's walled-garden allow-list live over the RouterOS API, synchronously (unlike `SyncRouterWalledGarden` below, it doesn't need a queue worker running) — useful for immediately fixing an already-provisioned router without waiting on a gateway change to trigger the automatic job, or when `QUEUE_CONNECTION=database` locally and no worker is running to drain it.

## Architecture

### Two separate traffic paths — keep them mentally distinct

1. **Customer captive-portal path**: customer device → MikroTik → HTTPS redirect → `App\Http\Controllers\Hotspot\PortalController` (`routes/web.php`, `/hotspot/*`) → payment gateway → RADIUS provisioning.
2. **Router auth/accounting path**: MikroTik → WireGuard tunnel (or, per-router, an optional ZeroTier fallback tunnel — see the `tunnel_mode` note below) → FreeRADIUS 3 → the same MySQL `radius` database (`nas`, `radcheck`, `radreply`, `radacct`, `radusergroup`, `radgroupreply`, `radgroupcheck` tables). Laravel never proxies RADIUS traffic itself — it only writes rows FreeRADIUS reads. When both tunnels are active, RouterOS's own RADIUS client fails over between them by priority natively — the app never has to detect or route around a dead tunnel itself.

`App\Services\RadiusProvisioningService` and `App\Services\MikroTikProvisioningService` are the bridge: package/subscriber changes in the app get mirrored into the `radcheck`/`radusergroup`/`radgroupreply`/`nas` tables, and router onboarding generates a RouterOS script from stored provisioning settings.

`App\Services\StandaloneHotspotScriptGenerator` (2026-08-07, revised 2026-08-08) is a deliberately separate, unrelated code path — the "Script Generator" tool at `admin/tools/script-generator` (super admin only, gated by `abort_unless($request->user()->isSuperAdmin(), 403)` in `StandaloneScriptGeneratorController` the same way `TenantController`/`SecurityController` are). It generates a MikroTik hotspot config for routers that are **not**, and don't need to become, a `Router` record on this platform: no WireGuard, no HotspotFreeRAD RADIUS server, no API user, no shop/tenant binding. It branches on RouterOS 6 vs 7 wireless syntax (`/interface wireless` vs `/interface wifi`/wifiwave2) and wireless-vs-wired-only hardware via plain capability toggles in the wizard (`App\Livewire\Admin\StandaloneScriptGenerator`, a 5-step form) rather than a hardcoded router-model catalog — deliberately, since a real model database would need ongoing upkeep as new MikroTik boards ship. Every Ethernet port except the WAN port is bridged into the hotspot automatically (`ethernet_port_count` wizard field, parsed against `wan_port`'s trailing number), and "Router identity" (`/system identity`) is a separate wizard field from "Hotspot name" (the SSID/portal branding) since they're not always the same string. The whole flow is stateless: nothing is persisted, the wizard's Livewire state holds everything, and the result page renders both the copyable/downloadable `.rsc` script and a printable voucher sheet (`voucher_template`: `grid`, `compact`, or `receipt`) in one response via `@media print` CSS — there was no reason to add a database table for something meant to be filled in, generated, and printed/copied in one sitting.

Voucher validity is designed to start counting from a customer's **first login**, not from when the voucher was created — a real gap in the original version, fixed after specific network-engineer feedback plus MikroTik doc research. RouterOS 7 uses the built-in User Manager (`/user-manager`) as a **self-hosted local RADIUS server** pointed at `127.0.0.1` (never leaves the router, so this doesn't reintroduce a platform dependency) — its `profile.starts-when=first-auth` is the officially documented way to do this, and User Manager's richer object model (`limitation` / `profile` / `profile-limitation` / `user-profile` / `user` are five distinct objects, not one) is used deliberately instead of classic `/ip hotspot user profile`. RouterOS 6 has no equivalent, so classic hotspot users are used with an `on-login` script (`StandaloneHotspotScriptGenerator::onLoginExpiryScript()`) bound to the hotspot server profile that creates a one-time scheduler on a user's first login and removes the account when their validity window elapses — a well-established community pattern, not an official RouterOS feature, so it's commented as best-effort the same way other unverified RouterOS syntax is elsewhere in this codebase. Voucher codes support an optional prefix, configurable length, a choice of character set (`StandaloneHotspotScriptGenerator::CHARACTER_SETS` — safe alphanumeric, numeric-only, letters-only, or full case-sensitive), and whether the username and password should be the same or independently generated (`voucher_prefix`/`voucher_code_length`/`voucher_character_set`/`voucher_username_password_same`, all per profile) — mirroring MikroTik's own "Make Vouchers"/batch-user dialog shape (which has separate username-characters/password-characters options). `generateVoucherCodes()` returns `username`/`password` per voucher rather than a single `code`, and both script paths (`userManagerLines()`/`classicHotspotLines()`) and the print templates were updated accordingly — a print card shows one combined line when they're equal, or separate "User:"/"Pass:" lines when they're not.

When the management network is enabled, the generated script also restricts the router's own `www`/`www-ssl`/`winbox`/`ssh` services to that subnet (`/ip service set ... address=<mgmt-cidr>`) — this was originally going to be a custom "web Winbox" page built into this platform, but RouterOS's REST API sends no CORS headers (so a browser can't call it cross-origin from another domain) and a standalone router with no WireGuard tunnel isn't reachable from this app's backend at all. The better, lower-maintenance answer is to properly lock down and point admins at RouterOS's *own* built-in web tools (WebFig, and on v7 the User Manager page at `https://<router-mgmt-ip>/userman`) rather than rebuild them.

`App\Services\StandalonePtpScriptGenerator` (2026-08-08) is a second, equally self-contained standalone tool — the "PTP Radio Generator" at `admin/tools/ptp-generator` (super admin only, same `abort_unless($request->user()->isSuperAdmin(), 403)` gate in `StandalonePtpGeneratorController`, plus the same check again in `App\Livewire\Admin\StandalonePtpGenerator::mount()`). It configures a MikroTik point-to-point wireless bridge/backhaul link — unlike the hotspot tool's one router/one script, a PTP link inherently has two radios that must match (same frequency, channel width, SSID, security), so the 5-step wizard produces **two** scripts in one session (`generate()` returns `['script_a' => ..., 'script_b' => ...]`), one AP/master end and one Station end, either of which can independently be RouterOS 6 or 7. "Bridged" link mode uses `station-pseudobridge` rather than true `station-bridge`, deliberately — pseudobridge works across the widest range of MikroTik wireless chipsets, where true station-bridge needs matching driver support on both ends. `distance_km` sets RouterOS's `distance=` property (ACK-timeout auto-tuning for long links) — like the hotspot tool's on-login script, this is flagged in-script as best-effort/unverified against real hardware rather than presented as guaranteed-correct. The point-to-point subnet (`ptp_subnet`, e.g. a `/30`) is resolved with real CIDR bit math (`ptpSubnetParts()`, using `ip2long`/`long2ip` — deliberately not reusing `StandaloneHotspotScriptGenerator::networkParts()`, which assumes a gateway-first `/24` LAN input, not a narrow point-to-point subnet) to assign the first two usable host addresses to each radio; an optional per-radio route (`add_remote_route`/`remote_network`) points at "whatever's behind the other end" — intentionally scoped to that one static route rather than a routing protocol like OSPF. "Bridged" link mode was initially a real bug — it only flipped the wireless station mode to `station-pseudobridge`/`bridge` without ever creating a RouterOS bridge interface, so an admin using it would get no actual bridge to attach a LAN port to. Fixed via `bridgeLines()`: bridged mode now creates `bridge-ptp`, adds the wireless interface as a port, and addresses the *bridge* (not the raw wireless interface); routed mode is unaffected (no bridge, address stays directly on the wireless interface, each end keeps its own subnet). A bridge with only the wireless interface as a member still extends nothing, though — real feedback on a physical SXTsq Lite5 (single-Ethernet-port CPE hardware, where that one port *is* the LAN connection, not a spare) surfaced this — so each radio also gets an optional `lan_port` (default `ether1`, wizard step 2, shown only when bridged): when set, `bridgeLines()` adds it as a second bridge port and explicitly `/interface ethernet set <port> disabled=no` (belt-and-braces even though Ethernet ports are enabled out of the box). Left blank, the script instead emits a comment telling the admin to add one manually, rather than silently shipping a bridge that does nothing.

A factory-default wireless interface is administratively disabled, and RouterOS can reject `mode=`/`frequency=`/etc changes on a still-disabled interface even when `disabled=no` is in the *same* `set` command as those changes -- confirmed missing from a real script (the interface stayed down). `wirelessLines()` now issues an explicit `/interface wireless enable <interface>` (RouterOS 6) or `/interface wifi enable [find default-name=<interface>]` (RouterOS 7) as its own command *before* the `set`/`configuration=` line that changes mode/frequency, rather than relying on the inline `disabled=no` alone (kept anyway as a second safeguard).

A live "bad band or frequency" rejection (RouterOS 6, a genuinely valid frequency well inside the card's own hardware range) traced to `band`/`country`/`frequency-mode` never being set at all -- RouterOS validates a requested `frequency=` against the *currently-configured* band/country/frequency-mode, and a factory-default interface's `country` (default `etsi`) plus an unset `band` can reject an otherwise-fine frequency outright. Fixed by adding `country` (shared, required, free-text RouterOS country name, e.g. `no_country_set`), per-radio `band` (required, options depend on that radio's own `ros_version` -- `StandalonePtpGenerator::ROS6_BANDS`/`ROS7_BANDS`, since the two ends can be different RouterOS versions with different valid band strings), and `frequency_mode` (`regulatory-domain` default; `superchannel` bypasses country limits entirely and is flagged in-script as a compliance decision the operator is making deliberately) -- all set in the *same* `/interface wireless set` command as `frequency=`, since RouterOS validates a `set`'s properties against the resulting state, not the prior one. Also added, from the same "ask like a pro network engineer" pass: `wireless_protocol` (`802.11` default, `nv2` offered only when both radios are RouterOS 6 -- MikroTik's proprietary TDMA link protocol, no CSMA hidden-node contention or distance throughput penalty, only works between two MikroTik radios which is always true here); `hide_ssid` (default on -- no customer-facing reason to broadcast a backhaul link's SSID); `skip_dfs_channels` (RouterOS 7 only, default on -- avoids channels needing radar-detection CAC delays, better for a fixed link); and per-radio optional `antenna_gain_dbi` (RouterOS 6 only -- the equivalent RouterOS 7 `/interface wifi` property path couldn't be confirmed from documentation across the legacy `wifiwave2`/newer unified `wifi` packages, so it's deliberately left unset there rather than guessed). Separately, RouterOS 7's station role for a *bridged* L3 link was wrongly using plain `station` -- MikroTik's own docs say `station-bridge` is what "enables support for a 4-address frame format, so the interface can be used as a bridge port," which plain `station` doesn't; fixed to match RouterOS 6's existing `station`/`station-pseudobridge` split for the same distinction.

The AP end's RouterOS 6 legacy-wireless master mode is picked by `link_topology` (`'ptp'` default, or `'ptmp'`), not hardcoded — `ap-bridge` (RouterOS's true multi-client AP mode) needs a higher wireless license tier / AP-capable hardware, while `bridge` (single-peer master mode) is included in MikroTik's base/CPE license tier that ships on cheaper dish hardware like the SXTsq. The tool originally always used `ap-bridge`, which is why AP mode was rejected as "not supported" on a real SXTsq Lite5 (confirmed 2026-08-08) — a genuine point-to-point link only ever has one peer, so `ap-bridge` was never the right mode regardless of hardware. `'ptp'` now uses `bridge`; `'ptmp'` uses `ap-bridge` for a hub end meant to serve multiple stations (the wizard still only configures one AP + one Station script per session — a PtMP hub is just re-running the wizard once per additional station against the same AP). RouterOS 7's `/interface wifi` package has no equivalent split (`mode=ap` covers both topologies there, since that driver has no separate single-peer master mode).

Rather than teach the *service* about hardware models (which this codebase deliberately avoids — see the router wizard's rejection of hardcoded presets below), each radio in the wizard gets a `cpe_only` toggle whose meaning is topology-dependent: a CPE-only radio can still be the `'ptp'` AP end (bridge mode is base-tier), just not the `'ptmp'` AP end (ap-bridge needs the higher tier). `App\Livewire\Admin\StandalonePtpGenerator::updated()`/`reconcileApEndForTopology()` auto-flips `ap_end` to the other radio when the current AP end is CPE-only *and* topology is `'ptmp'` (whether that came from toggling `cpe_only` or from switching topology itself) — but won't flip to an equally-invalid CPE-only radio. Step-2 validation independently rejects, only under `'ptmp'`, both "a CPE-only radio selected as `ap_end`" and "both radios marked CPE-only" (no valid AP end left) as a safety net regardless of the auto-flip. `StandalonePtpScriptGenerator` itself stays unaware of `cpe_only` entirely -- by the time config reaches it, `ap_end` is already guaranteed valid for the chosen topology.

The two standalone tools (Script Generator, PTP Radio Generator) share one sidebar entry, "Tools" (`admin/tools/script-generator`/`admin/tools/ptp-generator` are still two separate routes/controllers/Livewire components — nothing consolidated server-side), with an in-page tab strip (`<x-admin.tools-tabs active="hotspot|ptp">`, `resources/views/components/admin/tools-tabs.blade.php`) linking between them via `wire:navigate`. Both routes already share the same nav "active" match pattern (`admin.tools.*`, from `$sectionPatternFor()` in the admin layout), so the single sidebar link correctly highlights on either page without any nav-logic changes.

`admin/docs` (super admin only, `App\Http\Controllers\Admin\DocsController` — same `abort_unless($request->user()->isSuperAdmin(), 403)` gate as Tools/Tenants/Security) renders the `docs/*.md` files inside the admin panel itself, so onboarding a new super admin or checking infra steps doesn't require leaving the app to browse the repo. `App\Support\DocsCatalog` is a read-only, framework-light lister/renderer: it only ever enumerates `*.md` files actually present under `base_path('docs')` and looks up a requested slug against that in-memory list (never re-derives a filesystem path from the request), so it can't be used to read anything outside that one folder. Markdown is rendered via Laravel's `Str::markdown()` (`league/commonmark`, already a framework dependency — no new package needed for parsing) with `html_input: strip` so raw HTML in a doc can't execute; the docs are trusted repo content, not user input, but stripping costs nothing and every doc's few literal HTML snippets (e.g. the login-page example in `router-onboarding.md`) live inside fenced code blocks, which CommonMark always escapes regardless of that setting. `App\Livewire\Admin\DocsIndex` is a single component (not the multi-controller "Tools" pattern) with a live-filtered search box (matches title or full content) and a master-detail layout: `$activeSlug` (synced to `?doc=` via Livewire's `#[Url]` for shareable/bookmarkable links) picks the doc shown in the content pane, while `$showListOnMobile` — a separate flag, not derived from `$activeSlug` — controls which pane is visible below the `lg` breakpoint, so mobile lands on the doc list first but a deep link (`?doc=...`) opens straight into that doc's content with a "Back to docs" control. The priority docs CLAUDE.md itself recommends reading first (`current-project-status`, `roles-and-product-direction`, `deployment-architecture`, `router-onboarding`, `raspberry-pi-deployment`) sort to the top of the list; anything else in `docs/` sorts after them alphabetically with no code change needed when a new doc file is added. Rendered content uses Tailwind's official `@tailwindcss/typography` plugin (`prose prose-zinc dark:prose-invert`) — the one addition to `package.json` this feature needed, since hand-rolling heading/list/code/table styling for arbitrary markdown wasn't worth it against a well-maintained, purpose-built plugin.

Router-to-Pi WireGuard connectivity is app-managed, not manual: `App\Models\Router` auto-generates a WireGuard keypair on creation (`App\Support\WireGuardKeyPair`, via `paragonie/sodium_compat` so it works without the native sodium extension), the private key is baked into the generated script instead of letting RouterOS pick its own, and `App\Services\WireGuardPeerSyncService` (run via the `hotspot:sync-wireguard-peers` scheduled command) reconciles the Pi's live WireGuard peers from the `routers` table. That command is inert everywhere by default (`WIREGUARD_MANAGE_PEERS=false`) and only does anything once enabled on the Pi per `docs/wireguard-server-setup.md`.

A router whose site is behind carrier-grade NAT (CGNAT — common on Starlink/mobile) can never form a WireGuard tunnel at all, since WireGuard has no relay/fallback of its own. `Router::tunnel_mode` (`wireguard` default, `wireguard_zerotier`, or `zerotier`) adds ZeroTier as a per-router opt-in fallback or replacement — ZeroTier has built-in NAT traversal with automatic relay fallback, which raw WireGuard categorically lacks. RouterOS has native ZeroTier support since 7.5+, but as a separate installable package restricted to **ARM/ARM64 hardware only** — this is why it's a router-level choice in the wizard (Identity step, alongside the WireGuard fields), never assumed available, the same "capability toggle, not a hardware model database" pattern as `enable_builtin_wifi`. Deliberately built around a **self-hosted ZeroTier network controller on the Pi**, not ZeroTier Central's cloud service — Central's free plan caps at 10 devices and has zero API access at all (Essential plan, $18+/mo, required for automated node authorization), while a self-hosted controller is free, uncapped, and its local API (`http://127.0.0.1:9993/controller/...`, loopback-only) needs no ZeroTier subscription. See `docs/zerotier-fallback-setup.md` for the one-time Pi bootstrap.

`App\Services\ZeroTierControllerService` was never exercised against a real controller before this shipped, and a live 2026-08-19 report of a router stuck `ACCESS_DENIED` after following the setup doc surfaced two real bugs at once, both now fixed: `setAuthorized()` (backing `authorizeMember()`/`deauthorizeMember()`) was POSTing `{"config": {"authorized": ..., "ipAssignments": [...]}}`, but ZeroTier's real controller API takes those fields flat at the top level and silently ignores an unrecognized `"config"` wrapper — the POST always returned HTTP 200, so every authorize call "succeeded" while never actually authorizing anything, the same class of bug as the RouterOS `!trap`-parsed-as-success issue above. Separately, `listMembers()` assumed `GET .../member` returns an array of full member objects; the real endpoint returns a flat `{address: revision}` map with no per-member detail at all, so it now does a second `GET .../member/{address}` per node (the same endpoint the POST already targets) to get each one's real `authorized`/`ipAssignments` — an N+1 pattern accepted here the same way `WireGuardRouteSyncService` accepts one-request-per-router, given this app's realistic router count. Since `ZeroTierMembershipSyncService::reconcile()` returns early on any `listMembers()` failure, this second bug meant the entire automatic authorization sync silently no-opped on any network that already had a member on it — not just a wrong-field-name issue.

`RouterOsConnectionService::client()` (the single choke point every other method in that file routes through) tries `candidateHosts($router)` in order — WireGuard IP first when applicable, then the ZeroTier IP — so live monitoring/"Provision via API"/etc. all get the fallback for free with no other call-site changes; `evilfreelancer/routeros-api-php`'s `Client` connects synchronously in its constructor, so a failed attempt throws immediately and the loop just tries the next host. `MikroTikProvisioningService::radiusClientLines()` emits one `/radius add` per enabled tunnel — RouterOS's own RADIUS client already fails over across multiple entries, tried in the order they appear in `/radius print`, so that's the entire "use ZeroTier whenever WireGuard fails" mechanism on the RADIUS side, no custom health-check scripting. RouterOS's `/radius` menu has **no `priority` property at all** — confirmed live 2026-08-19 (`unknown parameter priority`) after an earlier version of this line, and the live-API mirror of it, both emitted `priority=1`/`priority=2` for years with neither ever having been exercised against a real router. Correct WireGuard-before-ZeroTier ordering instead falls out for free from emission order alone (`radiusClientLines()` always writes the WireGuard line before the ZeroTier line), as long as an existing entry is never removed and blindly re-added. Since a dual-mode router might send RADIUS traffic from either IP, `RadiusProvisioningService::syncRouter()` writes a **second** `nas` row keyed to the ZeroTier IP (FreeRADIUS matches a NAS/client definition by the packet's source IP) — mirrored in `FreeRadiusClientSyncService::managedContent()`'s optional flat-file path for parity. `MikroTikProvisioningService::apiServiceAddressRestriction()` also extends the RouterOS API's allowed-address firewall rule to include the ZeroTier subnet in dual/ZeroTier-only mode — easy to miss, since without it the tunnel itself works but RouterOS's own firewall still only trusts the WireGuard subnet, so "Provision via API" and friends silently fail. That restriction used to only ever get set once, at script time — a router that had ZeroTier added to it *after* its script was last pasted (the normal path: add a router as WireGuard-only, switch its `tunnel_mode` later) kept trusting only the WireGuard subnet forever, with nothing to fix it short of a manual `/ip service set api address=...` on the router console. Confirmed live 2026-08-19 from a router moved to a genuinely remote site — no longer reachable over WireGuard at all, exactly ZeroTier's reason for existing — where every API call over its now-working ZeroTier tunnel still failed with a timeout (RouterOS silently drops a connection from an address outside this list rather than refusing it, indistinguishable from the tunnel itself being down unless checked specifically). `RouterOsConnectionService::syncApiServiceRestriction()` (public method on `MikroTikProvisioningService` now, reused directly rather than duplicated) closes this the same way the RADIUS/ZeroTier syncs do — wired into `provisionHotspot()`/`provisionPppoe()`, it lists the router's current `/ip service` "api" address, and pushes the correct combined value only when it's actually wrong. The self-healing property this gives: as long as *either* tunnel is currently trusted, running this over that working path pushes a restriction covering *both* — so a router with working WireGuard gets ZeroTier pre-trusted before it's ever needed, not only after something breaks. A router trusted on *neither* currently-working path is the one case this can't fix (nothing can reach it to fix it) — that still needs the one manual console command, same as before.

Switching an already-provisioned router's `tunnel_mode` (e.g. WireGuard-only → `wireguard_zerotier`) used to need the whole script re-pasted by hand — `RouterOsConnectionService::provisionHotspot()`/`provisionPppoe()` previously just blindly ran one `/radius/add` per enabled tunnel every time, with no idea what the router already had. Confirmed live (2026-08-19): re-provisioning a router after a tunnel_mode change would have added a genuine duplicate WireGuard entry alongside the new ZeroTier one. `syncRadiusClients()` replaces that with a real reconcile, mirroring `syncWalledGarden()`'s "list what's actually there first" shape: `desiredRadiusClients()` (pure) says what *should* exist for the current `tunnel_mode`, `planRadiusClientChanges()` (pure) diffs that against a live `/radius print`, and only the actual differences get pushed — `/radius/add` what's missing, `/radius/remove` an entry whose address is one of this app's own two known endpoints (`services.radius.server_ip` / `services.zerotier.pi_ip`) but is no longer desired, leave anything else alone entirely. An earlier version of this also tried to `/radius/set` a mismatched `priority` on an existing entry — removed the same day it was written, once the very first live "Provision via API" click against it came back `unknown parameter priority` (see the `radiusClientLines()` note above: that property was never real). Since there's nothing left to *fix* on a matched entry, "remove-scoped-to-known-endpoints" is the only mutation this performs on anything already present — an entry whose address matches *neither* known endpoint (an admin's own unrelated RADIUS client) is never touched, the same safety boundary `WireGuardRouteSyncService`'s `proto` tag provides for kernel routes, just keyed on address instead of a tag since RADIUS clients have no equivalent ownership marker.

Enabling ZeroTier and actually joining the specific network are two separate RouterOS steps — confirmed live 2026-08-19 from a router that had a real ZeroTier identity (enabled by hand for testing) but had never run `/zerotier interface add`, leaving it authorized on the controller yet permanently unconnected (`vMajor:-1` etc. in the controller's own member listing — never actually checked in). `RouterOsConnectionService::syncZeroTierNetworkMembership()` is the live-API equivalent of `MikroTikProvisioningService::zeroTierLines()`'s `/zerotier enable zt1` + `/zerotier interface add network=... instance=zt1` pair, wired into `provisionHotspot()`/`provisionPppoe()` as a no-op (zero steps, no connection attempt) for a router that doesn't use ZeroTier at all — checks the router's actual state first (`existingZeroTierState()`) so re-running it after the network is already joined is a safe no-op, not a second, likely-rejected "add". `self::ZEROTIER_INSTANCE_NAME` (`'zt1'`) assumes an instance by that name already exists by default on the router, matching `zeroTierLines()`'s existing assumption — confirmed true on the real hardware this was tested against, but not guaranteed universally. `mapZeroTierState()`'s `instance_disabled` check also needed a same-day fix: RouterOS's API frequently omits a boolean property entirely when it's at its `no`/false value rather than echoing it back explicitly, and the first version of this defaulted a missing `disabled` key to `'true'` — meaning a router with ZeroTier genuinely already enabled still got sent an unnecessary (if harmless) `/zerotier/enable`. Fixed to default a missing key to `'no'` instead, matching the one live-confirmed row shape actually seen (`disabled=no` shown explicitly for an enabled instance).

Joining the network still isn't the last step, confirmed live 2026-09-21 from a router that showed `OK`/genuinely connected on the ZeroTier layer *and* genuinely authorized on the controller (`ipAssignments` populated) yet still failed "Test Connection" with a socket error: nothing ever puts an IP address on the resulting interface. The controller's own `ipAssignments` value is only auto-pushed to a client when the network's `v4AssignMode.zt` is on, which this app deliberately leaves off (`docs/zerotier-fallback-setup.md` — IPs are assigned explicitly via `$router->zerotier_ip` instead of ZeroTier's own pool, precisely to avoid needing that feature). Both `MikroTikProvisioningService::zeroTierLines()` and `RouterOsConnectionService::syncZeroTierNetworkMembership()` now also add `/ip address add address=<zerotier_ip>/24 interface=zerotier1` — `self::ZEROTIER_INTERFACE_NAME` (`'zerotier1'`) is the same "confirmed on the real hardware this was tested against, not guaranteed universally" assumption as `ZEROTIER_INSTANCE_NAME`, matching the interface name RouterOS auto-assigns the first `/zerotier interface add`. `zeroTierActionsNeeded()`'s new `'address'` action always sorts after `'join'` deliberately, since the interface it targets doesn't exist until joining has actually run and `runSteps()` executes a batch's queries in the order they were added. The script generator's version is skipped gracefully (with an explanatory comment, not a blank/broken command) when a router doesn't have a saved `zerotier_ip` yet — mirroring how every other "not configured yet" field in this generator degrades.

Addressing that interface hit a second, immediate problem, also confirmed live 2026-09-21 on a genuinely fresh-reset router: `/zerotier interface add` returns control to the next line before RouterOS has actually finished registering the resulting interface, so the very next command addressing it failed outright (`input does not match any value of interface`) even though `/zerotier interface print` had just confirmed `zerotier1` was the correct, eventual name — ruling out a naming-assumption bug. Both the script generator and the live-API path now wait for RouterOS to catch up before touching the interface: `MikroTikProvisioningService::zeroTierLines()` inserts a `:delay 3s` line between the `/zerotier interface add` and `/ip address add` lines (same `filled($router->zerotier_ip)` guard as the address line itself), and `RouterOsConnectionService::syncZeroTierNetworkMembership()` runs the enable/join steps as their own `runSteps()` batch, then `sleep(3)` — but only when this same call is the one that actually just ran the join step; an already-joined router's interface has had plenty of time to exist and skips straight to the address step. A generous fixed wait was chosen over a polling loop deliberately — it only costs a few seconds once during bootstrap, and this app already accepts similar fixed costs elsewhere (see the "Provision via API" latency note below).

Beyond both of the above, the self-hosted ZeroTier network's own config was missing something too, confirmed live 2026-09-21: the Pi's own node stayed authorized with a real `ipAssignments` value on the controller, yet `zerotier-cli listnetworks`/`ip addr` never showed that address, even across a full service restart. Root cause -- a hand-assigned `ipAssignments` address is only actually applied to a device's interface if the network also has a matching **route** covering that address; `docs/zerotier-fallback-setup.md`'s original network-creation command (Step 3b) never set one, since it only ever set `ipAssignmentPools: []`/`v4AssignMode.zt: false`, neither of which covers this. Fixed by adding `"routes": [{"target": "10.9.0.0/24", "via": null}]` to that command for new setups, and documenting the same fix (plus forcing a `zerotier-cli leave`/`join` -- a plain restart alone doesn't bump a device's cached `netconfRevision`) for a network created before this fix existed. This is infra/setup-doc-only, not app code -- nothing in this codebase creates or configures the network itself, that's a one-time manual step done directly against the local controller API per `docs/zerotier-fallback-setup.md`.

A router that joins the network *before* its node ID has been authorized in MMS Radius (the normal order of events for a fresh/reset router) gets stuck on RouterOS's own cached `ACCESS_DENIED` forever otherwise, confirmed live 2026-09-21: RouterOS never re-requests network status on its own just because the controller authorized the node afterward -- only removing and re-adding the interface forces a fresh request (the same fix the Pi's own membership needed above). `RouterOsConnectionService::existingZeroTierState()`/`mapZeroTierState()` now track the interface row's own `status` property (confirmed live against a real RouterOS 7 router's `/zerotier interface print detail` -- the raw API property is `status`, uppercase `"OK"` when genuinely authorized) as `network_authorized`, separate from `network_joined` (which only checked whether the interface row existed at all, regardless of its status). `zeroTierActionsNeeded()`'s new `'rejoin'` action fires when joined-but-not-authorized, and always forces `'address'` back on too -- removing the interface removes its bound address as well, so an already-`address_assigned` router still needs it reapplied afterward. `syncZeroTierNetworkMembership()` handles `'rejoin'` with a `/zerotier/interface/remove` + `/zerotier/interface/add` pair (using the interface row's own `.id`, distinct from the `zt1` service's `instance_id`), and applies the same `:delay`-equivalent `sleep(3)` the join-race fix above needed, since re-adding the interface risks the identical registration race. Because this lives inside `syncZeroTierNetworkMembership()`, both the scheduled `hotspot:auto-provision-routers` job and a manual "Provision via API" click get the fix automatically, with no separate wiring.

Waiting up to 5 minutes for the scheduled job to pick this up was real friction during live testing, so `App\Livewire\Admin\RouterCredentialsCard::authorizeZeroTier()` (button: "Authorize & connect now", shown on the router's Live/credentials card whenever `tunnel_mode` uses ZeroTier and a node ID is saved) collapses what used to be two manual steps -- `hotspot:sync-zerotier-members` on the Pi, then a manual `/zerotier interface remove`/`add` on the router console -- into one click: `ZeroTierMembershipSyncService::authorizeRouter()` (new method, authorizes a single router on the controller regardless of `ZEROTIER_MANAGE_MEMBERS`, the same on-demand-works-even-with-the-flag-off exception `hotspot:resync-walled-garden` already carves out) followed immediately by `syncZeroTierNetworkMembership()` over the live RouterOS API.

**The self-hosted ZeroTier controller went down for roughly two months without anyone noticing, confirmed live 2026-09-24** — an admin trying to remote into the Pi over ZeroTier as a personal-device fallback found `zerotier-cli listnetworks` simply refusing to connect at all. `systemctl status zerotier-one` showed the daemon itself starting fine (`ExecStart` succeeded) but the unit as a whole still `failed`, because a *separate* `ExecStartPost` step — a `systemd-tmpfiles` rule reapplying `www-data` read access on `authtoken.secret` after every restart, added directly on the Pi at some point and never documented in this repo — was failing with `Detected unsafe path transition ... during canonicalization`, and systemd tears down an entire unit (including its already-running main process) when any `ExecStartPost` step fails. Root cause: `/var/lib/zerotier-one` is owned by the `zerotier-one` service account while `authtoken.secret` inside it is owned by `root` (ZeroTier's own default), and a systemd hardening check refuses to let `systemd-tmpfiles` cross that ownership boundary at all, regardless of what the rule itself requests — this is presumed to have started passing silently until a `systemd` package upgrade began enforcing it, which is consistent with the outage's start date lining up with no ZeroTier-related config change on record. The blast radius here is the real lesson: a permission nicety that only matters for the app's own controller-API convenience calls (`hotspot:sync-zerotier-members`, "Authorize & connect now") took down the entire tunnel daemon, including all currently-authorized routers' actual ZeroTier data-plane connectivity, which depends on nothing about `www-data`'s file permissions at all. Fixed by removing the `systemd-tmpfiles`-based `ExecStartPost` entirely and replacing it with a plain shell script (`/usr/local/sbin/hotspotfreerad-fix-zerotier-authtoken`, documented in `docs/zerotier-fallback-setup.md`'s troubleshooting section) that does the same `chgrp`/`chmod` directly — a plain shell command doesn't trigger the same tmpfiles-specific path-canonicalization check — and, critically, always exits `0` even if the file is missing or the permission change itself fails, so a permission hiccup can never again cascade into tearing down the core daemon. This only ever affected the app's ability to *authorize new* ZeroTier nodes over the two-month window; it's independent of WireGuard entirely and doesn't retroactively affect any router that was already authorized/joined before the outage began.

Both syncs make their own separate live connection attempt (to list current state) before the actual write attempt, on top of the several `provisionHotspot()`/`provisionPppoe()` already made — meaning "Provision via API" against a genuinely unreachable router now takes noticeably longer to report failure than before (confirmed: `test_provision_hotspot_reports_a_clear_error_when_router_is_unreachable` went from a few seconds to ~56s). Accepted deliberately: the reachable-router case (what this feature is actually for) only adds a small number of fast, local-network round trips, and a router that's genuinely offline was always going to end in failure regardless of how many attempts it takes to get there.

**The one real limitation, not hidden**: WireGuard automation works because the app generates a router's keypair *before* the router ever connects, pre-authorizing it centrally. ZeroTier is the opposite — a router generates its own node identity locally the first time `/zerotier enable` runs, which this app can't predict in advance, and a new node sits unauthorized on the (required-private) network until approved. `App\Services\ZeroTierMembershipSyncService` (via `hotspot:sync-zerotier-members`, same 5-minute/no-op-by-default pattern as the WireGuard sync, gated by `ZEROTIER_MANAGE_MEMBERS`) only ever authorizes node IDs this app already knows about; a node it can't attribute to any router shows up in that command's `unmatched_members` output instead of being silently ignored. `App\Livewire\Admin\RoutersIndex::fetchZeroTierNodeId()` covers the common case (a router still has working WireGuard) by reading `/zerotier print` back over that link automatically; a router with no working WireGuard at all needs its node ID entered by hand, once, from the router's own console. Ongoing operation is fully automatic either way — only *initial onboarding* of a ZeroTier-dependent router isn't 100% push-button the way pure-WireGuard onboarding is.

`fetchZeroTierNodeId()` originally parsed the node ID from a plain `address` field on `/zerotier print` -- another assumption never checked against real hardware, confirmed wrong 2026-08-19 via a live "no node-ID field was found" report. RouterOS's actual output has no such field; the node's own ID is the part before the first `:` in `identity` (or its public-only counterpart `identity.public`, e.g. `identity="69ae7250fc:0:<public-key-hex>:<private-key-hex>"`) -- both fields only surface via the RouterOS API's full property set, not the interactive terminal's default `/zerotier print` column view (which only shows `NAME`/`PORT` unless you add `detail`, a purely cosmetic CLI difference that has no bearing on what the API itself returns). Fixed to prefer `identity.public` over `identity` when both are present, purely so a parsing failure never has private key material to leak.

Staff/Management Wi-Fi (WPA-PSK SSIDs, distinct from the open customer hotspot) gets a second access control layer beyond the shared password: `App\Models\TrustedWifiDevice` (admin: `admin/trusted-wifi-devices`) registers devices by MAC per shop/network (`staff`|`mgmt`), synced into `radcheck` via `RadiusProvisioningService::provisionTrustedWifiDevice()`. For the MikroTik built-in Wi-Fi test profile (`l009_builtin_wifi`), the script generator also emits a local `/interface wifi access-list` allow/deny list from the same registered devices — regenerated on demand, not live-pushed to the router. See `docs/staff-wifi-access.md` for the external-AP RADIUS MAC-auth path and its current limitations.

**The POS SSID had no equivalent second layer at all** (2026-09-23, confirmed via a live report of an unregistered device getting full internet access on the POS VLAN just from knowing the shared WPA2/WPA3 password) — `App\Models\PosDevice` (`admin/pos-devices`) already had a `mac_address` column and `App\Services\RadiusProvisioningService::provisionPosDevice()`/`revokePosDevice()` already wrote/removed a correct RADIUS MAC-auth record (`radcheck` username = MAC, password = MAC, the standard MAC-auth pattern, plus the package's usual `Session-Timeout`/`Mikrotik-Rate-Limit` group reply via `syncPackageProfile()`) on every register/renew/expiry — but nothing on the router side ever queried it. `MikroTikProvisioningService::generateFreshInfrastructureScript()`'s POS section created the VLAN/DHCP pool but left the actual `/ip hotspot profile add name=mms-pos-profile use-radius=yes login-by=mac` + `/ip hotspot add name=mms-pos ...` pair as **commented-out** lines with no live-API equivalent at all, so `hotspot:sync-expired-pos`'s revocation was equally inert — deleting a device's `radcheck` row had zero effect on a network nothing ever checked it against. Fixed by uncommenting/wiring those two lines unconditionally whenever `enable_pos` is on (no separate opt-in toggle — matches the VLAN's own pre-existing comment, "registered devices, no shared customer password", which was already asserting this was supposed to be enforced), and adding a live-API equivalent: `RouterOsConnectionService::provisionPos()` does an idempotent add-or-set of `mms-pos-profile`, then `applyPosHotspotServer()` adds-or-repoints the `mms-pos` hotspot server object bound to `vlan-pos`/`pool-pos` — both fixed names this app's own script generator always uses, so (unlike the customer hotspot's `applyHotspotProfile()`, which deliberately never creates a hotspot server since its interface/pool could come from a manual `/ip hotspot setup`) it's safe for this one to create the object itself, not just re-point an existing one. `applyHotspotProfile()`'s own "point every hotspot server at saas-prof" loop had to be scoped to exclude `interface=vlan-pos` as part of this fix — before that exclusion, a router with both hotspot servers present would have had this loop silently reassign the POS one back to the customer-facing profile on every subsequent provision, undoing MAC-auth every time. **Nothing about this is yet confirmed against real hardware** (matching this codebase's honest pattern elsewhere for freshly-added RouterOS behavior) — in particular, whether `/ip/hotspot/print` actually surfaces `interface` the way both new methods assume. A router that already has `enable_pos` on needs a fresh script paste or a "Provision via API" click to pick this up — and since this is now a real enforcement change, not just a bookkeeping one, every real POS device's MAC should be registered in `admin/pos-devices` *before* re-provisioning, or it will lose access the moment the fix lands.

`provisionPos()` is deliberately a sibling of `provisionHotspot()`/`provisionPppoe()`, not nested inside either (2026-09-23, per a direct request to make each script section independently pushable rather than bundled behind one "Provision via API" click) — the router's own page gets a third tab, "POS Script" (`App\Http\Controllers\Admin\RouterController::provisionPos()`, route `admin.routers.provision-pos`), mirroring the existing Hotspot/PPPoE Script tabs exactly: its own generated script (`MikroTikProvisioningService::generatePosScript()`) and its own "Provision via API" button that touches only the POS hotspot profile/server, leaving the customer hotspot and PPPoE untouched. `generatePosScript()` deliberately omits its own `/radius add` line, unlike `generateScript()`/`generatePppoeScript()` — POS's hotspot server uses the "hotspot" RADIUS service, which `generateScript()`'s own line (or the Bootstrap/Fresh Infrastructure scripts) already covers, and RouterOS doesn't dedupe `/radius add` entries on its own, so a second one would be a genuine duplicate, not just redundant. It also assumes `vlan-pos`/`pool-pos` already exist (Fresh Infrastructure Script's POS section) rather than offering PPPoE's generic `bridge1`-placeholder fallback, since those are fixed names this app always uses, not something meant to be hand-edited. `App\Services\RouterAutoProvisioningService::provisionRouter()` calls `provisionPos()` unconditionally on every cycle (unlike its explicit `enable_pppoe` check before calling `provisionPppoe()`) — `provisionPos()` already no-ops internally for a POS-disabled router via the same default-true `enable_pos` fallback the script generator uses, so duplicating that check in the auto-provisioning service too was avoided deliberately, the same "don't let two places disagree" concern that's bitten this codebase before (see the `l009_builtin_wifi`/walled-garden-host/`priority`-property stories elsewhere in this file). `provisionPos()` adds two of its own live connection attempts, on top of everything else `provisionHotspot()` already makes, when both are invoked in the same request/cycle (as `RouterAutoProvisioningService` does) — the same latency tradeoff already accepted for the ZeroTier syncs above.

Adjusting a section's SSID/VLAN/addressing/ports used to always need the full 4-step router wizard, even for a single field (2026-09-23, per a direct request, later extended to PPPoE in the same pass) — the Hotspot Script, PPPoE Script, and POS Script tabs now each embed `App\Livewire\Admin\RouterNetworkSettingsCard` (`network="hotspot"`/`"pppoe"`/`"pos"`, one reusable component for all three rather than near-duplicate ones per network), a small Livewire island dropped into the otherwise-plain-Blade router show page — the exact same pattern `App\Livewire\Admin\RouterCredentialsCard` already established there, so none of the rest of that page needed converting to Livewire. Its "Edit settings" button opens a Flux modal whose fields vary per network (`supportsSsid()`/`supportsAddressPool()`/`supportsExtraPorts()`/`supportsWifiPassword()`): hotspot, POS, and (as of 2026-09-23, see below) PPPoE all get VLAN, gateway/network/pool, and extra untagged ports; POS alone also gets the Wi-Fi password (hotspot has none — deliberately open Wi-Fi with RADIUS/captive-portal login as its only auth layer, not a shared PSK); PPPoE alone has no SSID field at all, being wired/PPP dial-in rather than Wi-Fi. When the router has no built-in Wi-Fi radio enabled, the SSID field is shown disabled with an explanatory note, since that setting only affects the built-in-Wi-Fi branch of the generated script and has no effect at all for a router relying on an external AP.

**PPPoE gained the same self-sufficiency, extra-access-port, and idempotent-live-provisioning treatment POS and Staff already had** (2026-09-23, direct request: "work on the provision via api for the pppoe so it include the vlan/dhcp/untagged access port etc"). Before this, `generatePppoeScript()` assumed `generateFreshInfrastructureScript()` had already created `vlan-pppoe` — the same gap already fixed for POS/Staff — and there was no untagged-access-port model for PPPoE at all (explicitly excluded, on the reasoning that PPPoE is "architecturally a dial-up service rather than a shared access-port VLAN"). That reasoning didn't survive a real deployment need for a direct/wired PPPoE access port, so `extra_pppoe_port_numbers`/`extra_pppoe_ports` now exist as a fifth role alongside mgmt/hotspot/staff/pos, wired through every layer that already handled the other four identically: `RouterManagementService::rules()`'s `Rule::prohibitedIf`/`derivePortInterfaceNames()`/`portConflictRule()`, the wizard's Hardware step (simple and advanced-mode pickers), `RoutersIndex::routerProvisioningSettings()`'s reverse-derivation on edit, and `RouterNetworkSettingsCard`'s `supportsExtraPorts()`/`extraPortsEditable()`.

A second, genuine gap surfaced while building this: **PPPoE never had any client-addressing mechanism at all.** `mms-pppoe-profile` set neither `local-address` nor `remote-address`, so nothing ever handed a dialing subscriber an IP. This isn't a DHCP gap — PPP assigns each session's address itself via IPCP, never DHCP — so the fix is a real `/ip pool` (`pool-pppoe`, new `pppoe_network`/`pppoe_pool` settings alongside the existing `pppoe_gateway`) bound via the profile's `remote-address=`, with `local-address=vlan-pppoe` borrowing the VLAN's own gateway IP as the server side of every session. `generatePppoeScript()` now creates the VLAN, any extra untagged ports, the bridge-vlan entry, the address, and `pool-pppoe` itself — same "NOT idempotent, do not paste twice" caveat as POS/Fresh Infrastructure Script — and deliberately adds **no** firewall input-chain accept rule the way POS's MAC-auth hotspot needs one: PPPoE discovery/session negotiation is Ethernet-level (EtherType `0x8863`/`0x8864`), never passes through `/ip firewall filter` (IP-only) at all, so there's nothing to accept. `generateFreshInfrastructureScript()`'s own PPPoE section got the identical pool/local-address/remote-address addition, plus PPPoE's bridge-vlan line now gets its own dedicated untagged entry (pulled out of the shared tagged-only catch-all) whenever it has extra ports configured, exactly mirroring the hotspot/staff/pos precedent already established there.

The live-API side had two real, independent bugs, both confirmed live and fixed together: `RouterOsConnectionService::provisionPppoe()`'s `$pppoeInterface` parameter still defaulted to a stale `'bridge1'` placeholder from before the script generator switched to `'vlan-pppoe'`, and **neither real caller ever overrode it** (`RouterController::provisionPppoe()`/`RouterAutoProvisioningService::provisionRouter()` both call it with zero arguments) — meaning every live "Provision via API" PPPoE push, including every scheduled auto-provisioning retry, had been silently binding the PPPoE server to `bridge1` the entire time, disagreeing with what the script itself does. Separately, the "Add PPPoE profile"/"Add PPPoE server" steps were plain, non-idempotent `/add` calls — the same class of bug `existingHotspotProfileId()` fixed for the customer hotspot profile, just never surfaced here since the wrong-interface bug meant this path likely never succeeded enough times in a row to hit it. Fixed together: the default is now `'vlan-pppoe'`; a new `ensurePppoeInfrastructure()` (mirroring `ensureStaffInfrastructure()`/`ensurePosInfrastructure()`, scoped to VLAN/IP/pool only — no DHCP server/network step, since PPPoE has none to ensure) runs unconditionally, but only actually touches anything when `$pppoeInterface` is still the app's own default (a caller-overridden custom interface name is assumed to mean the admin already has that infrastructure set up their own way, matching `generatePppoeScript()`'s own "retype the interface" escape hatch); and a new `applyPppoeProfileAndServer()` does an idempotent add-or-set of both objects together, mirroring `applyMacAuthHotspotServer()`'s exact shape.

Saving is deliberately save-only — it never pushes live; pushing stays each tab's own separate "Provision via API" button, matching how the full wizard already separates "save" from "provision." A real nuance surfaced while building this: **none of the three per-section incremental scripts** (`generateScript()`/`generatePppoeScript()`/`generatePosScript()`, the ones each tab actually displays) **read SSID/VLAN/addressing at all** — only `generateFreshInfrastructureScript()` does, since that's the one that actually creates the VLAN/addressing/Wi-Fi configuration in the first place. So the card's own copy says plainly that a save is reflected on the Fresh Infrastructure Script tab, not the tab the card itself lives on, and a save still forces a full page reload (not just closing the modal) specifically so that other tab's controller-rendered script text picks up the change — it's rendered once at page load, not reactively by this Livewire island. SSID itself is a genuinely new setting (`hotspot_ssid`/`pos_ssid`) — previously hardcoded literal strings (`"MMS Hotspot"`/`"MMS POS"`) in `MikroTikProvisioningService`'s script generator, defaulted here to those exact same strings so a router that never touches the new field keeps generating a byte-identical script. One bug caught early: `MikroTikProvisioningService::provisioningSettings()` (the private defaults-merge a script generator actually reads from) is a **second, separate** defaults array from `RouterManagementService::defaultProvisioningSettings()` (the one the save/wizard path uses) — both needed the new SSID default added, or a router with no explicit override crashed script generation with an undefined-array-key error; this is the same "two places that must not silently disagree" shape as the walled-garden-host/`l009_builtin_wifi` stories elsewhere in this file.

Adding PPPoE surfaced a second, pre-existing instance of the same "incremental script assumes infrastructure that fresh-infra actually creates" gap `generatePosScript()` already had to account for: `generatePppoeScript()`'s PPPoE server used to bind to a hardcoded generic `bridge1` placeholder the admin had to manually retype before pasting, even though `generateFreshInfrastructureScript()`'s own PPPoE section already creates and binds to a fixed `vlan-pppoe` interface. Fixed to reference `vlan-pppoe` directly, matching `generatePosScript()`'s existing "assumes the fresh infrastructure script already created this VLAN" pattern — a router that doesn't use this app's own VLAN scheme at all can still retype the interface, same as before, just no longer needs to on the common path. The card's own extra-ports save validation reuses `RouterManagementService::portConflictRule()` (made `public` for exactly this) rather than re-implementing a second, narrower conflict check — built against a copy of the router's full existing settings with just this network's extra-ports field overridden. The three "Provision via API" buttons (Hotspot/PPPoE/POS tabs) also switched from a native browser `confirm()` to a real Flux modal, using Flux's named-trigger mode (`<flux:modal.trigger name="...">`/`<flux:modal name="...">`) — confirmed pure Alpine.js with zero Livewire dependency, so the existing plain `<form method="POST">` inside each just moved into the modal's slot unchanged, no conversion needed for the rest of the (non-Livewire) page.

**A real live regression from the card's first version, confirmed 2026-09-23**: `RouterNetworkSettingsCard` originally let a POS extra-ports value be saved regardless of `enable_pos`, on the theory that an admin might want to "pre-configure a network before its toggle is flipped on" (the port-conflict check even forced `enable_pos=true` just to still catch collisions in that case). This directly contradicted `RouterManagementService::rules()`'s own `Rule::prohibitedIf(!enable_pos)` on `provisioning_settings.extra_pos_port_numbers`, which requires that field to be **blank** whenever POS is disabled — the full wizard's own step-2 "Hardware" screen hides the "Extra POS port" input entirely while POS is off, precisely because it can never legally hold a value there. A router edited through the card this way (extra ports set while POS stayed disabled) got silently poisoned: `enable_pos=false` with a non-blank `extra_pos_port_numbers`/`extra_pos_ports`. On that specific router, the wizard's step 2 → step 3 "Next" transition then failed server-side on *every* attempt with a completely invisible error — the validation response genuinely contained `"extra_pos_port_numbers field is prohibited"`, but since the field it's attached to is exactly the one the wizard hides for a POS-disabled router, no `<flux:error>` block ever existed on the page to show it. No browser console error, no failed network request (the Livewire round-trip returns a normal `200`) — just a "Next" button that silently does nothing, which is exactly what made this hard to diagnose from the browser side alone; finding it required reading the raw Livewire response JSON's `memo.errors` key directly. Fixed by making the card match the wizard's actual constraint instead of working around it: `RouterNetworkSettingsCard::extraPortsEditable(array $settings)` (`true` for hotspot unconditionally — there's no `enable_hotspot` flag, hotspot is always on — but for POS only when `enable_pos` is currently `true`) gates the field to disabled-with-an-explanatory-note in the UI, and `save()` now force-blanks `extra_pos_port_numbers`/`extra_pos_ports` whenever the network isn't actually enabled, regardless of what was typed into the (disabled) input — so this state can't be created again, and re-saving an already-poisoned router's POS settings (even with no other changes) self-heals it back to blank. A router already poisoned before this fix needs exactly that: open its POS tab, "Edit POS settings," Save — the wizard's step 2 unblocks immediately afterward.

Turning POS on for that same router surfaced a third, distinct gap the same day: `enable_pos` had been off the last time this router's Fresh Infrastructure Script was applied, so `vlan-pos`/`pool-pos`/the POS DHCP server/its bridge-vlan entry had never actually been created on the router at all — `applyPosHotspotServer()`'s `/ip/hotspot/add interface=vlan-pos` step failed live with RouterOS's `input does not match any value of interface`, and since Fresh Infrastructure Script is explicitly not safe to re-run (duplicates everything else already there), the only path at the time was hand-deriving and pasting the missing pieces individually on the router console. Fixed on both paths this router exposed the need for: `MikroTikProvisioningService::generatePosScript()` (the paste-by-hand "POS Script" tab) is now fully self-sufficient — it creates the VLAN interface, the virtual POS Wi-Fi SSID (when built-in Wi-Fi is enabled), any extra untagged POS ports, the bridge-vlan entry, and the IP/pool/DHCP objects itself, duplicating the equivalent lines in `generateFreshInfrastructureScript()`'s own POS section rather than extracting a shared helper — refactoring that heavily-tested method carried more risk than the duplication does, and this codebase already accepts this same tradeoff elsewhere (see the walled-garden-host note above: "has to go in both places, they're not one shared source of truth"). Like Fresh Infrastructure Script itself, this script is **not idempotent** — pasting it twice on a router that already has these objects creates duplicates. It also now emits the two POS-specific firewall rules, with the input-chain accept using `place-before=[find action=drop in-interface-list=!WAN]` — confirmed live this router's own catch-all input-drop rule would otherwise have stranded a plain appended `add` after it, in a position where RouterOS would never reach it (filter rules evaluate in list order); this `place-before=[find ...]` syntax itself isn't yet confirmed safe on a router with no such catch-all rule at all.

The live-API path got a matching, narrower fix: `RouterOsConnectionService::ensurePosInfrastructure()` (called from `provisionPos()`, before the hotspot profile/server steps) idempotently list-then-creates just the four simple, uniquely-named objects — the VLAN interface, its IP address, `pool-pos`, and the DHCP server/network — reading the exact same defaulted settings `generatePosScript()` uses via `MikroTikProvisioningService::provisioningSettings()` (made `public` for exactly this, the same "one source of truth" reasoning as `portConflictRule()`). Deliberately scoped to just these four: each reduces to a single "does an object with this name/interface already exist" check, safe to run on every `provisionPos()` call including the unconditional one every 5-minute auto-provisioning cycle makes — unlike the bridge-vlan table entry, virtual POS Wi-Fi SSID, and extra access ports, which are deliberately **not** auto-created live, since a bridge-vlan row can already exist covering other VLANs and just need POS's ID merged into it, the same complexity `generateFreshInfrastructureScript()`'s own bridge-vlan-line logic already has to handle for the paste-by-hand case — reconciling that safely over the API is a meaningfully larger effort, deferred rather than risked in this pass. A router still missing those three needs `generatePosScript()`'s now-more-complete output (or the Fresh Infrastructure Script) pasted by hand for that part; `provisionPos()`'s own error reporting will say so plainly if the hotspot-server step still fails afterward.

With the VLAN/DHCP infrastructure in place, POS MAC-auth itself still rejected a live-registered device outright: RouterOS's hotspot log showed `trying to log in by mac` followed immediately by `login failed: invalid username or password`, for a device confirmed correctly registered and active in `admin/pos-devices`, with a matching `radcheck` row present (`Cleartext-Password` = the device's normalized MAC, exactly matching `mms-pos-profile`'s own `radius-mac-format=XX:XX:XX:XX:XX:XX`). Root cause: `RadiusProvisioningService::provisionPosDevice()` also wrote a **second** `radcheck` row, `attribute=Calling-Station-Id`, set to the same normalized MAC — but FreeRADIUS treats every `radcheck` row for a username as a check-item the Access-Request itself must satisfy, not descriptive metadata, so this silently required the request's own `Calling-Station-Id` attribute (however RouterOS actually formats it, never verified against real hardware, unlike the username format `radius-mac-format` explicitly governs) to match too — on top of the password check that was already correct. `provisionTrustedWifiDevice()` (the same MAC-as-username-and-password RADIUS pattern, just for staff/mgmt Wi-Fi) never had this second check-item and works; `provisionPosDevice()` was the only place it existed, with no comment explaining why it was added. Removed to match the simpler, proven-working shape — `revokeMacAccess()` needed no change, since it already deletes every `radcheck` row for a username regardless of attribute.

**That fix alone wasn't enough** — the same device kept getting rejected afterward with the identical RouterOS log message, confirmed via `freeradius -X` in foreground debug mode (the same technique that found the original `http-pap` root cause). The debug output showed the actual mechanism: `mms-pos-profile`'s username/group lookup now succeeded cleanly (`User found in radcheck table`, correct package group loaded), but authentication still failed at `chap: ERROR: Password comparison failed: password is incorrect`. RouterOS's hotspot authenticates MAC-auth over **CHAP**, not plain PAP — it hashes whatever password it decides to send together with a per-request `CHAP-Challenge`, and FreeRADIUS independently re-computes that same hash from the stored `Cleartext-Password` to compare. `mac-auth-password=""` (left blank, MikroTik's documented "defaults to the client's MAC" behavior) does not actually pre-hash the same normalized-MAC string `provisionPosDevice()` was storing as `Cleartext-Password` — confirmed live, this specific blank-default behavior was never verified against real hardware, the same class of undocumented RouterOS quirk this file has hit repeatedly elsewhere. Meanwhile `RadiusProvisioningService::grantSubscriptionAccess()` — the customer hotspot's own MAC-based RADIUS flow, confirmed working via `mac-cookie` in this same router's log — never relied on that ambiguous default at all: it always used a **fixed, non-MAC password** (`'authenticated_device_pass'`). Fixed POS to match that already-proven pattern instead of guessing further at RouterOS's blank-default behavior: `RadiusProvisioningService::POS_MAC_AUTH_PASSWORD` (`'MmsPosMacAuth2026!'`) is a new fixed constant, used as every POS device's `Cleartext-Password` (replacing the MAC-as-password), and set explicitly as `mms-pos-profile`'s own `mac-auth-password=` in both `MikroTikProvisioningService` (the script generator, both `generatePosScript()` and `generateFreshInfrastructureScript()`'s POS section) and `RouterOsConnectionService::provisionPos()`'s live-API profile query — so RouterOS is never left to guess what to send, and FreeRADIUS's re-computed hash always matches. Not a meaningful secret either way: the MAC (the username) is what actually identifies the device; RADIUS just requires some password value for the CHAP exchange to complete.

**A related but distinct bug surfaced live 2026-09-23, once POS MAC-auth was actually working**: a POS device's `radcheck` row would periodically disappear despite the device itself showing a future expiry, requiring a manual Renew/Sync click to restore it. Root cause: `radcheck`/`radreply`/`radusergroup` are keyed purely by `username` (a MAC address string), with **no feature/type discriminator** — the same MAC can simultaneously back a hotspot `Subscription`, a `PosDevice`, and/or a `TrustedWifiDevice` (exactly this case: the test phone had earlier been used for a normal customer hotspot login, then separately registered as a POS device — same MAC, two unrelated records). `hotspot:sync-expired-hotspot` (5-minute schedule) finds every MAC whose most recent hotspot `Subscription` has expired and calls `RadiusProvisioningService::revokeMacAccess($macAddress)` — which did an **unscoped** `DELETE WHERE username=...` across all three RADIUS tables, with no awareness that the same MAC might still be an active `PosDevice`. Every 5 minutes, the expired hotspot subscription's revoke silently wiped the still-valid POS device's `radcheck`/`radusergroup` rows as collateral damage; the same collision is possible in the other direction too (a `PosDevice`/`TrustedWifiDevice` revoke wiping a MAC that still has an active hotspot `Subscription`). Fixed inside `revokeMacAccess()` itself (protecting every caller at once, not just the hotspot sync command) via a new `macStillClaimedElsewhere()` guard: before deleting anything, it checks for an active hotspot `Subscription`, `PosDevice`, or `TrustedWifiDevice` (via each model's own `isCurrentlyActive()`) still claiming that MAC, and no-ops if one exists — the row is left exactly as whichever other feature already provisioned it. `revokeMacAccess()` gained two optional exclusion parameters (`$exceptPosDeviceId`/`$exceptTrustedWifiDeviceId`), passed through by `revokePosDevice()`/`revokeTrustedWifiDevice()` so a device being revoked never blocks its own revocation by matching itself in that same "still active" check (relevant for `PosDeviceManagementService::delete()`/`TrustedWifiDeviceManagementService::delete()`, which call the RADIUS revoke *before* deleting the DB row, so the record being revoked is still technically "active" in the database at that moment). Hotspot `Subscription` revocation (the direct `revokeMacAccess()` call in `hotspot:sync-expired-hotspot`) needs no exclusion — the query it iterates already excludes any MAC with another still-active subscription, so the expiring subscription itself never self-blocks.

An external AP's RADIUS MAC-auth requests only reach the Pi if the router's LAN/VLAN subnets are actually routed through the WireGuard tunnel — by default only the router's own `/32` tunnel IP is (`WireGuardPeerSyncService::desiredPeers()`), which is exactly the gap `docs/staff-wifi-access.md` used to flag as unresolved. `provisioning_settings.route_lan_through_tunnel` (per-router opt-in, Network plan step of the wizard) closes it: when enabled, `desiredPeers()` widens that router's `AllowedIPs` to include its `mgmt_network`/`staff_network` CIDRs alongside its `/32`. Widening `AllowedIPs` alone isn't sufficient, though — `wg set` (used for all runtime peer updates, since this Pi's `wg-saas.conf` has no `[Peer]` blocks at all) doesn't create a kernel route the way `wg-quick up` would from a config file at startup; that's only invisible today because every existing peer IP already falls inside `wg-saas`'s own directly-connected `10.8.0.0/24` subnet. A router's mgmt/staff VLAN isn't part of that subnet, so `App\Services\WireGuardRouteSyncService` (via `hotspot:sync-wireguard-routes`, gated by its own `WIREGUARD_MANAGE_ROUTES` flag — deliberately separate from `WIREGUARD_MANAGE_PEERS` since this one touches the kernel routing table) also manages an explicit `ip route` per opted-in router's subnets. Every route it touches is tagged `proto hotspotfreerad` (registered once in `/etc/iproute2/rt_protos` — `docs/wireguard-server-setup.md`), which is what makes automatic *removal* safe here unlike `WireGuardPeerSyncService` (which deliberately never removes a peer) — reconciliation only ever reads/writes routes carrying that tag, so it can never touch the interface's own connected route or anything added by hand. Not yet verified against a real Pi.

Since every router's `mgmt_network`/`staff_network` defaults to the exact identical literal subnet regardless of profile (`RouterManagementService::defaultProvisioningSettings()`) and WireGuard's `AllowedIPs` must be unique/non-overlapping per peer on a given interface, `RouterManagementService::lanRoutingOverlapRule()` validates a router's subnets against every *other* router that also has `route_lan_through_tunnel` enabled (via the new `App\Support\CidrOverlap` pure helper) before allowing the save — routers that don't use this feature are unaffected by each other regardless of subnet collisions.

The built-in Wi-Fi access-list mechanism (`docs/staff-wifi-access.md`) had the same "not pushed to the router automatically" gap POS's MAC-auth used to have, and no independent per-section script/provision tab either — a device registered or removed under Trusted Wi-Fi Devices only actually took effect on the router after an admin manually re-opened the Fresh Infrastructure Script, re-ran it, and remembered that section carries the same "NOT idempotent, do not paste twice" caveat as the rest of that script. A router's "Staff Script" tab (`App\Http\Controllers\Admin\RouterController::provisionStaffWifi()`, route `admin.routers.provision-staff-wifi`, `show()` also passing `staffScript`) now mirrors the POS tab's shape exactly: `MikroTikProvisioningService::generateStaffScript()` is a standalone, self-sufficient script covering both the Staff and Management SSIDs — VLAN, addressing, untagged ports, and the wireless SSID itself for Staff (gated by `enable_staff`, the same self-sufficiency reasoning `generatePosScript()` already established, since `enable_staff` can be flipped on after Fresh Infrastructure Script was last applied); Management deliberately does NOT recreate `vlan-mgmt`/`pool-mgmt`/`dhcp-mgmt`, since those are core infrastructure Fresh Infrastructure Script always creates unconditionally regardless of any wireless toggle — only Management's wireless SSID itself (`enable_mgmt_wifi`) is created here. If `enable_builtin_wifi` is off entirely, the script is just an explanatory comment pointing at the external-AP RADIUS MAC-auth path instead, the same "explain why, don't silently emit nothing" pattern used elsewhere in this file.

The trailing access-list section of that script is deliberately its own **safely re-pastable** block, unlike every VLAN/Wi-Fi creation section above it (here or in Fresh Infrastructure Script): it opens with `/interface wifi access-list remove [find interface=wifi-staff]`/`wifi-mgmt`, then rebuilds each SSID's list fresh from MMS Radius's current Trusted Wi-Fi Devices — this is the part meant to be re-run every time a device is added, edited, or removed, so it couldn't carry the same "do not paste twice" caveat as the rest.

The live-API side (`RouterOsConnectionService::provisionStaffWifi()`) is deliberately scoped the same way `provisionPos()`'s own live-API side is scoped relative to `generatePosScript()`: `ensureStaffInfrastructure()` mirrors `ensurePosInfrastructure()` exactly (four simple "does this exist" checks — VLAN, IP, pool, DHCP — safe to run every cycle) for Staff only, since Management's VLAN is core and already assumed present. Creating the wireless SSID itself (security + configuration + interface + bridge port) is deliberately NOT attempted live, matching POS's own precedent of deferring that harder, bridge-vlan-table-adjacent work to the paste-by-hand script — if the SSID doesn't exist yet, the access-list sync step below just fails plainly (interface not found) rather than silently no-opping. What IS synced live is the actual value proposition here: `syncWifiAccessList()` reconciles one SSID's `/interface/wifi/access-list` against current Trusted Wi-Fi Devices by removing every existing entry for that interface (one at a time by `.id`, matching this file's existing per-row pattern) and rebuilding it — one accept entry per active device, plus a trailing reject unless zero devices are registered (mirroring `wifiAccessListLines()`'s own "don't lock out the admin before anything's registered" behavior exactly). A full remove-then-rebuild was chosen over a true diff deliberately: the reject entry must always sort last or a device added afterward would never be reached, and a real trusted-device list is small enough that this is cheap and avoids an entire class of ordering bugs a partial diff would need to get right. `App\Services\RouterAutoProvisioningService::provisionRouter()` calls `provisionStaffWifi()` unconditionally every 5-minute cycle, the same "already no-ops internally, don't duplicate the check" pattern `provisionPos()` established — this is what actually closes the automation gap: a device registered or removed under Trusted Wi-Fi Devices now reaches the router within minutes with no manual re-paste or button click needed, the same way WireGuard peers/ZeroTier membership/POS MAC-auth already stay in sync. Not yet confirmed against real hardware — in particular, whether `/interface/wifi/access-list/print` actually surfaces `interface` the way both new methods assume, the same "not yet confirmed" caveat this file already carries for other freshly-added RouterOS behavior.

Confirmed live 2026-09-23, immediately: exactly the deferred case above — a router with `enable_staff`/`enable_builtin_wifi` both on, VLAN infrastructure just created via `ensureStaffInfrastructure()`'s own live step, but whose wireless SSID had never actually been pasted from the Staff Script tab — reported `Sync MMS Staff trusted-device access list (input does not match any value of interface)`, RouterOS's own trap message surfacing raw rather than explained (Management's own sync succeeded on the same run, since `wifi-mgmt` already existed there). The config-level `enable_builtin_wifi`/`enable_staff`/`enable_mgmt_wifi` toggles only say a wireless SSID is *supposed* to exist — not whether it *actually* does yet on this specific router, and the two can legitimately disagree for a while (VLAN infra pushed live, wireless SSID still pending a manual paste). `syncWifiAccessList()` now checks the interface's real live existence first, via `/interface/wifi/print`, before ever attempting the access-list `/add` — failing fast with an actionable message ("paste the wireless SSID lines from the Staff Script tab ... first, then retry") instead of RouterOS's opaque trap text.

**Staff/Management enforcement now works with or without built-in Wi-Fi, matching POS exactly** (2026-09-23, direct request after a live report: an admin had configured an extra Staff access port specifically to test with a wired device/external AP, but both `generateStaffScript()` and `provisionStaffWifi()` only ever no-opped into an explanatory comment without `enable_builtin_wifi` — even though nothing about a wired/external-AP Staff connection actually requires a MikroTik radio). The wifi access-list mechanism above is genuinely wireless-radio-only (RouterOS has no equivalent for a wired port), so it can never be the universal answer here — the real fix was adding a **second, primary mechanism**: a RADIUS MAC-auth `/ip hotspot` server bound directly to `vlan-staff`/`vlan-mgmt`, the exact same pattern POS's `mms-pos-profile`/`mms-pos` already uses, which enforces on the VLAN itself regardless of how a device physically reaches it. `generateStaffScript()` now creates the Staff VLAN/addressing/extra-ports/MAC-auth hotspot (`mms-staff-profile`/`mms-staff`) unconditionally whenever `enable_staff` is on — only the virtual Wi-Fi SSID itself (security/configuration/interface/bridge port) stays conditional on `enable_builtin_wifi`, since that part is genuinely wireless-specific. Management gets a MAC-auth hotspot (`mms-mgmt-profile`/`mms-mgmt`) unconditionally too, since its VLAN is core/always present — there's no reason its enforcement should depend on wireless either. `RouterOsConnectionService::provisionStaffWifi()` mirrors this: `applyMacAuthHotspotServer()` (a new shared private helper — safe to share since both call sites are new code written together, unlike POS's own `applyPosHotspotServer()`, which stays untouched per this codebase's "don't refactor working, heavily-tested code" precedent) applies the Staff and Management hotspot profile/server unconditionally, while the wifi access-list sync step stays gated on `enable_builtin_wifi`. Not yet confirmed against real hardware — in particular, that adding a hotspot server on `vlan-mgmt` doesn't interfere with the router's own Winbox/SSH/API management access on that same VLAN; verify before relying on this in production for a router you also manage over that VLAN.

This reused POS's exact CHAP-password fix for the same reason: `RadiusProvisioningService::TRUSTED_WIFI_MAC_AUTH_PASSWORD` (`'MmsTrustedWifi2026!'`) replaces `provisionTrustedWifiDevice()`'s old MAC-as-password `Cleartext-Password`, since RouterOS's hotspot CHAP exchange has the identical "blank mac-auth-password doesn't hash to match a MAC-as-password radcheck row" problem POS hit. This has a real, documented tradeoff: the old MAC-as-password value was written specifically so an **external AP controller's own RADIUS MAC-auth** (a third-party AP, not MikroTik's hotspot — see `docs/staff-wifi-access.md`) could authenticate by sending a device's MAC as both username and password, a common AP-controller convention. Since `radcheck` only holds one password per username, changing it to the fixed value now requires an external AP controller doing RADIUS MAC-auth against this app to be configured to send that same fixed password for MAC-auth requests instead of the device's own MAC — documented in `docs/staff-wifi-access.md`'s rewritten "External APs" section, which also now leads with the MAC-auth hotspot as the primary mechanism (works with any physical connection) rather than the wireless-only access-list.

**Management's MAC-auth hotspot was corrected to be opt-in the very next day** (2026-09-24), after a live report of exactly the risk its own "not yet confirmed against real hardware" caveat above had flagged: an admin plugged a laptop into an extra wired management port to test connectivity and lost general internet access outright, tracked down through a long diagnostic chain (DHCP worked fine, `/ip route print`/`/ip address print` looked correct, `/interface bridge vlan print`/`/interface bridge port print detail` ruled out a VLAN/PVID misconfiguration, RSTP edge-port convergence was ruled out by re-testing once the port showed active) before `/ip firewall nat print` surfaced the real cause: RouterOS auto-generates dynamic hotspot dstnat/redirect rules the moment a hotspot server is active on an interface, and those rules intercept **any unauthenticated client** on that interface — the laptop's MAC was never registered under Trusted Wi-Fi Devices, so it was silently walled off from browsing despite having full L2/L3 connectivity. Unlike Staff (a network whose entire reason for existing as a separate SSID/VLAN is trusted-device enforcement — turning Staff on IS asking for this), Management is core infrastructure every router already had before this feature existed, and forcing MAC-auth onto it by default risked a much worse failure mode than a locked-out test laptop: if the Pi's own MAC (on `pi_port`) were ever missing from Trusted Wi-Fi Devices or fell out of sync, the Pi could lose its own connectivity to the router, severing the WireGuard/RADIUS/API tunnel this whole app depends on with no remote way to fix it. `provisioning_settings.enable_mgmt_mac_auth` (new, default `false`) now gates the mgmt hotspot in `generateStaffScript()`/`provisionStaffWifi()`, the mgmt wifi access-list in both of those *and* in `generateFreshInfrastructureScript()`'s builtin-wifi branch (a third call site that pre-dated this whole MAC-auth feature and would otherwise have silently disagreed with the other two), and gets its own wizard checkbox ("Require Trusted Wi-Fi Device on management VLAN," step 3) with an inline warning about the Pi-lockout risk whenever it's turned on. A router that already had the unconditional version live needs the hotspot objects removed by hand (`/ip hotspot remove [find name=mms-mgmt]`, `/ip hotspot profile remove [find name=mms-mgmt-profile]`) — neither the script nor the live sync ever removes something already provisioned, only adds/updates, so flipping the setting off alone doesn't retroactively clean up a router that already has it.

Registering a Trusted Wi-Fi Device requires already knowing its MAC address, and there was previously no way to see what's actually connected — a real gap surfaced 2026-08-09 by a live report of devices joining Management Wi-Fi with just the shared password and never showing up anywhere. `RouterOsConnectionService::dhcpLeases()` (a router's `/ip/dhcp-server/lease/print`, optionally filtered `where('server', ...)`) backs a new "Connected Devices" section on a router's Live tab (`App\Livewire\Admin\RouterConnectedDevices`, `resources/views/livewire/admin/router-connected-devices.blade.php`), letting an admin browse live leases per network (`mgmt`/`staff`/`pos`/`hotspot`) and one-click "Register as trusted" (mgmt/staff only, reuses `TrustedWifiDeviceManagementService::create()` as-is). This is **DHCP-lease-based, not wireless/wifi registration-table-based**, deliberately: a registration-table query only ever shows clients associated to the MikroTik's own radio, which stops working the moment a network's AP is an external device (e.g. Ruijie) bridged into the same VLAN instead — DHCP leases are recorded by the router regardless of which physical AP the client came through. This feature is visibility-only — it does not change or fix the enforcement gaps documented in `docs/staff-wifi-access.md` (the built-in Wi-Fi access-list still isn't auto-pushed to the router, and external-AP RADIUS MAC-auth still has the WireGuard LAN-routing gap); the "Register as trusted" action's flash message says as much rather than implying it blocks anything.

Live router monitoring (as opposed to the WireGuard/RADIUS provisioning above) needs to talk to the router directly, not just write RADIUS rows. `App\Models\Router` also auto-generates a RouterOS API user/password on creation (`api_username`/`api_password`, mirroring the WireGuard keypair pattern), baked into the generated scripts by `MikroTikProvisioningService::apiUserProvisioningLines()` and restricted to the WireGuard subnet only. `App\Services\RouterOsConnectionService` (wrapping `evilfreelancer/routeros-api-php`, which needs `ext-sockets`) is the single place that opens a live RouterOS API connection, always with short timeouts so an offline router fails fast instead of hanging a request. Historical bandwidth graphs (`App\Support\RouterUsageHistory`) need none of this — they read existing `radacct` data. CPU/RAM/disk/health/uptime history (`router_metric_samples`, populated every 5 minutes by `hotspot:sample-router-metrics` / `App\Services\RouterMetricSamplingService`) mixes both: latency is a plain ICMP ping needing no RouterOS API at all, while CPU/RAM/disk/health do. Router health alerts (`App\Notifications\RouterAlertNotification`, `implements ShouldQueue`) fire from state *transitions* detected in `RouterMetricSamplingService` (offline/online/high CPU/high RAM) — edge-triggered, not repeated every sample while a condition persists. In-system (database) delivery is always on; email is gated per-user by `User::notify_by_email` inside `via()`. Recipients are every super admin plus the tenant admins of the router's tenant. Being queued, delivery goes through the existing persistent `hotspotfreerad-worker` systemd service (`docs/raspberry-pi-deployment.md`), not a cron-triggered send. See `docs/router-monitoring.md`, including the honest caveats on Wi-Fi scan session cleanup, hardware-health field variability, and the topology view's deliberately-limited scope (org hierarchy, not physical LLDP discovery).

**A router's page gained a fourth history view, "Availability"** (2026-09-27, direct request for a Meraki-style uptime timeline: historical daily/weekly/monthly views, hoverable, showing exactly when a router went offline and came back). There is no stored "incident" table anywhere in this codebase — `RouterMetricSamplingService::evaluateAlerts()` only ever fires an instantaneous, edge-triggered `RouterAlertNotification` on an offline/online transition, it never persists a start/end interval. Rather than add one (a real option, but a bigger, separate effort), `App\Support\RouterAvailabilityHistory::summary()` derives online/offline/no-data windows on the fly by scanning consecutive `router_metric_samples.latency_ms` nullness and stitching same-status runs together — the same "no incidents table, reconstruct from what's already sampled" tradeoff this file already accepts elsewhere for the Connected Devices feature's DHCP-lease reads. A gap between samples bigger than `GAP_THRESHOLD_MINUTES` (15 — three missed 5-minute cycles' worth of slack, the same constant `RadiusAccountingStats::HEARTBEAT_FRESHNESS_MINUTES` already uses for the same reason) is reported as its own `no_data` segment rather than folded into a neighboring `up`/`down` run, since a genuine multi-cycle gap almost always means the scheduler wasn't running (or the router didn't exist yet) — not that every single ping across that whole span actually failed. Uptime % is computed as `up / (up + down)` seconds, deliberately excluding `no_data` time from the denominator, matching how uptime monitors like UptimeRobot treat a "paused"/unmonitored span.

`App\Livewire\Admin\RouterAvailability` (`resources/views/livewire/admin/router-availability.blade.php`) is a new Livewire component mirroring `RouterInsight`'s exact shape (`#[Locked] routerId`, a `Today / 7 days / 30 days` range picker reusing that same terminology, a `mount()`/`setRange()`/`loadSummary()` split) — added as a fifth tab, "Availability," on the router show page (`resources/views/admin/routers/show.blade.php`), needing zero `RouterController` changes since (like Insight) it fetches its own data entirely inside the Livewire component. The hoverable Meraki-style timeline itself is a hand-rolled Alpine.js + absolutely-positioned-`<div>` bar, not Flux Pro's `<flux:chart>` component — confirmed via `docs/router-monitoring.md`'s own documented limitation ("Flux charts have no built-in drag-to-zoom or brush selection") that Flux's chart primitive is a line/area SVG with a tooltip-per-data-point, not a segmented status-bar/range widget, so building this on top of it would have meant fighting the component rather than using it. Each segment is absolutely positioned (`left`/`width` as a percentage of the range's total duration) rather than laid out with `flex`, specifically so a very short blip (a single 5-minute outage inside a 30-day view, well under a visible pixel width at proportional sizing) can still get a `min-width: 2px` floor without disturbing any other segment's position — a `flex` row sizing children by percentage width has no equivalently simple way to floor one child's width without redistributing space taken from its siblings. Per this codebase's own accessibility habit elsewhere (color is never the only signal), the timeline is paired with a plain-text legend and a full "Downtime incidents" table below it (start/end/duration, most recent first) — the same information the hover tooltip shows, so it's never hover-only or color-only.

Since `router_metric_samples` had no retention/pruning at all before this — one row per router every 5 minutes, unbounded (confirmed: ~105K rows/router/year) — and a monthly Availability view is the first thing in this codebase to actually query a wide historical range from it, `hotspot:prune-router-metrics {--days=} {--dry-run}` (new, mirroring `hotspot:prune-security-activity`'s exact shape) was added alongside this feature, scheduled `dailyAt('02:20')` (right after the security-activity prune's `02:15` slot), retention configurable via `config('hotspot.router_metrics_retention_days')`/`ROUTER_METRICS_RETENTION_DAYS` (default 90 — comfortably covers the 30-day view with margin, per direct instruction when scoping this feature).
`App\Support\RadiusAccountingStats` (the Routers index/Dashboard/Topology "Last seen"/"Active/recent" status, `refreshRouterHealth()`) used to match `radacct.nasipaddress` against `Router::wireguard_internal_ip` only — confirmed live 2026-09-23 that a ZeroTier-only router (`tunnel_mode=zerotier`) permanently showed "Last seen never"/"No recent accounting" despite genuinely active traffic, since its RADIUS accounting rows are keyed to `zerotier_ip`, not the stored-but-unused `wireguard_internal_ip`. This is the exact same dual-IP concern `RadiusProvisioningService::syncRouter()` already handles by writing a second `nas` row for the ZeroTier IP — `RadiusAccountingStats` just never got the matching update. Fixed via a new `nasIpsFor(Router $router)` helper (both IPs, whichever are actually set) used everywhere this class matches `nasipaddress`: `refreshRouterHealth()`'s per-router queries, `queryForRouters()`'s shared summary/session query, and `onlineSessions()`'s router-name lookup.

**"Online" stopped meaning just "has an active accounting session," per a direct 2026-09-27 request after the dashboard's own "Routers Online" hint text ("Only routers with active accounting sessions are counted online") got flagged as an accuracy gap**: a fully healthy, reachable router with zero customers currently connected (overnight, a brand-new site, etc.) showed identically to a router that's genuinely down, since the old check only ever asked "is there an open `radacct` session right now" — a question about customer traffic, not router liveness. This app already runs a real per-router heartbeat independent of customer traffic (`hotspot:sample-router-metrics`/`RouterMetricSamplingService`, pinging every router every 5 minutes, the same signal `RouterAlertNotification`'s offline/online alerts already fire from), so `refreshRouterHealth()` was rewritten to pull each router's latest `RouterMetricSample` (one bulk query, no N+1) and define online as **heartbeat reachable OR has an active accounting session** — an OR, not a replacement, since a genuinely active customer session is still unambiguous proof of life even in the rare case ICMP itself is firewalled off while RADIUS traffic keeps flowing. A heartbeat sample only counts if it's both reachable (non-null `latency_ms`) and fresh (within 15 minutes — three missed 5-minute cycles' worth of slack). `last_seen_at` now takes the more recent of "last accounting activity" and "last heartbeat sample," so an idle-but-alive router shows a real, current last-seen instead of "Never." The two statuses this replaced (`'No accounting yet'`, `'Accounting unavailable'`) were renamed to `'No data yet'`/`'Monitoring unavailable'` since they're no longer specifically about `radacct` — neither string is compared against by any Blade template (`detected_status` is just displayed raw or checked against `'Online'`/`'Recently seen'`), so this needed no view changes, and Topology/Routers-index inherit the more-accurate status for free since they already call this same shared method.

Wiring the dashboard to this heartbeat surfaced a real, separate, pre-existing bug in the heartbeat itself: `RouterMetricSamplingService::sample()` only ever pinged `wireguard_internal_ip` directly, the exact same "only checks one of two possible IPs" gap `RadiusAccountingStats` itself had before the fix documented in the paragraph above — a `tunnel_mode=zerotier` router's `wireguard_internal_ip` is a stored-but-unused value, so such a router's heartbeat was *always* unreachable regardless of real ZeroTier connectivity, which would have made this whole fix a regression for exactly the ZeroTier-onboarding scenario covered elsewhere in this file. Fixed via a new private `pingReachableHost()` that tries every candidate host for the router's `tunnel_mode` in order (reusing `RouterOsConnectionService::candidateHosts()`'s existing static helper directly, same namespace, no new coupling), returning the first host that actually responds.

The API user's group policy used to be `read`-only (deliberately denying `write`) since it was originally scoped just for monitoring — but `RouterOsConnectionService::provisionHotspot()`/`provisionPppoe()`/`syncWalledGarden()` all issue genuine write commands (`/radius/add`, `/ip/hotspot/*/add`, `/ip/hotspot/walled-garden/add`), which RouterOS silently rejected under that policy. Compounding it, `evilfreelancer/routeros-api-php`'s `Client::read()` parses a RouterOS `!trap` (rejected command) identically to `!done` (success) and never throws — so `RouterOsConnectionService::runSteps()`/`applyHotspotProfile()` reported every one of those rejected writes back to the admin as a success ("walled garden synced" with nothing actually changed on the router). Found 2026-08-07 from a live report of "Provision via API" appearing to succeed with no effect on the physical router. Fixed both halves: the policy now grants `write` (`apiUserProvisioningLines()`), and `runSteps()`/`applyHotspotProfile()` now call `read(false)` (raw, unparsed) and check for a `!trap` block via the new `RouterOsConnectionService::extractTrapMessage()` before reporting a step successful. A router bootstrapped before this fix needs its script re-run (or just the `/user group set` policy line re-applied) before any API write will actually take effect — `hotspot:resync-walled-garden` (see Commands) is the quickest way to re-push and get an honest success/failure result now. `syncWalledGarden()` also lists the router's existing walled-garden entries first and only sends `/add` for hosts genuinely missing (`RouterOsConnectionService::missingWalledGardenEntries()`) — RouterOS doesn't dedupe `dst-host` on its own, so re-running a sync repeatedly used to keep piling up duplicate entries.

`MikroTikProvisioningService::generateBootstrapScript()` never set up WAN/internet access at all until confirmed live 2026-09-21 — a router that still had *some* leftover factory-default bridge/DHCP client with a working uplink could dial out fine, masking that this was ever missing, but a genuinely fresh/reset router (no default config left at all) had no path out for either WireGuard or ZeroTier to actually reach anything, leaving ZeroTier stuck at `REQUESTING_CONFIGURATION` forever with nothing in the script to explain why. Fixed by mirroring `generateFreshInfrastructureScript()`'s own WAN/DHCP-client setup at the very top of the bootstrap script (now requires a `$profile` parameter, default `starlink_plaza`, to resolve the router's configured `wan1` port the same way) — bootstrap is meant to stand entirely on its own on a blank router, not assume the full script runs first or afterward. Its interface-list creation is deliberately guarded with `:if ([:len [...]] = 0) do={...}` (the full script's own equivalent line is unguarded) specifically so a router that gets the full script pasted afterward doesn't hit a duplicate-list error re-creating "WAN".

Onboarding a router used to still need a human in the loop between "paste the bootstrap script" and "the rest of the config lands" — an admin had to notice the router had come online and manually click "Provision via API". `App\Services\RouterAutoProvisioningService` (via `hotspot:auto-provision-routers`, same 5-minute/no-op-by-default pattern as the WireGuard/ZeroTier syncs, gated by `AUTO_PROVISION_ROUTERS`) closes that gap: it finds every router with API credentials but no `auto_provisioned_at` yet, and just re-attempts `provisionHotspot()` (always) plus `provisionPppoe()` (only when `provisioning_settings.enable_pppoe`) every cycle until both fully succeed — no separate reachability probe needed first, since those methods already fail fast and cleanly against an unreachable router and are already fully idempotent (`syncRadiusClients()`/`syncWalledGarden()`/`syncZeroTierNetworkMembership()`/`syncApiServiceRestriction()` all list-then-diff before writing), so retrying on a schedule is safe. `RouterController::provisionHotspot()`/`provisionPppoe()` (the manual buttons) also set `auto_provisioned_at` on success, so a router an admin finishes by hand isn't redundantly retried by the background job. Deliberately no attempt is made to distinguish "still offline" from "reachable but a step genuinely failed" by inspecting RouterOS error text — every failed step is just reported plainly on each cycle, since that kind of string-matching has been a real source of bugs in this codebase before (see the `!trap`-parsed-as-success and `priority`-property stories elsewhere in this file).

The Bootstrap Script/auto-provisioning loop above only ever covers what `provisionHotspot()`/`provisionPppoe()` push: the RADIUS client, hotspot/PPPoE profile, walled-garden entries, and the login page. It deliberately assumes the router already has basic VLAN/bridge/hotspot-server infrastructure in place some other way -- VLANs, the bridge, POS/staff networks, QoS, and firewall rules only exist in `generateFreshInfrastructureScript()`'s output (the "Fresh Infrastructure Script" tab), which was copy-paste-only until `RouterOsConnectionService::pushFreshInfrastructureScript()` (2026-09-21) added a "Push via API (run once)" button for it too (`RouterController::pushFreshInfrastructure()`). Unlike every other live-API action in this file, this one is deliberately **not** idempotent -- most of what the generated script does (bridge VLAN entries, DHCP servers, the hotspot profile/server, queue types, firewall rules) are plain `add` commands with no "does this already exist?" check, the same as pasting the script by hand, so running it twice on the same router creates duplicate objects. There is no equivalent of `syncWalledGarden()`'s "list what's there, only add what's missing" here -- building that out (translating ~50 lines across VLANs/bridge/DHCP/hotspot/queues/firewall into a proper list-then-diff reconciliation, the same pattern already used for RADIUS clients/walled-garden/ZeroTier membership) was considered and deliberately deferred as a much larger, separate effort; the button's confirm dialog says so explicitly, and it's meant for a router that hasn't had it applied yet, not a repeatable sync. Implemented via RouterOS's own `/system script` object (`/system/script/add` with the full generated script text as `source=`, then `/system/script/run`) rather than translating the script's `:global` variables and `:if` guards into individual API `Query` calls one-for-one -- this executes the exact same script RouterOS's own terminal would from a paste, with identical behavior, and needs no per-line reimplementation; the temporary script object is removed again afterward (success or failure) so nothing is left behind on the router. Not yet confirmed live -- the `policy=` granted to the temporary script object (`read,write,test,sensitive,ftp,api`, mirroring this app's own API user's granted policy from `apiUserProvisioningLines()`, since a script's policy can't exceed what the running user already has) hasn't been exercised against real hardware yet.

**That caveat was warranted -- confirmed live 2026-09-26**, onboarding a second router: "Push Fresh Infrastructure Script (Push via API)" failed outright with `Could not upload the script: input does not match any value of policy`, the exact `!trap` message this codebase has hit twice before for an invalid/malformed RouterOS policy string (the `dude`/`tikapp` story and, separately, the `mmsradius-api-group` deny-list story, both in `apiUserProvisioningLines()`'s own docblock). The hand-rolled allow-only string above (`read,write,test,sensitive,ftp,api`) turned out not to be valid input for a `/system/script` object's `policy=` property on this router, even though every individual token in it is a real RouterOS policy name -- apparently (not fully confirmed why) a script object's policy property doesn't accept the same partial/implicit-deny shorthand `/user/group` tolerates, unlike the assumption the original "not yet confirmed live" comment made. Fixed by extracting the *actual*, already-live-confirmed policy string (the full explicit allow/deny list baked into `mmsradius-api-group`, confirmed working on a real RouterOS 7.18.2 router) into a new public `MikroTikProvisioningService::apiGroupPolicy()` method, and pointing `pushFreshInfrastructureScript()`'s `/system/script/add` at it instead of a second, independently-guessed string -- reusing one known-good policy string everywhere a RouterOS `policy=` property is set, rather than maintaining two that can silently drift apart and only one of which was ever actually exercised against hardware.

**Getting past that surfaced a second, unrelated bug the same day, found by pasting the Fresh Infrastructure Script directly onto the router's own terminal to keep diagnosing**: `/ppp profile add name=mms-pppoe-profile ... local-address=vlan-pppoe remote-address=pool-pppoe` failed with `invalid value for argument local-address: input does not match any value of pool / invalid value for argument address`, which then cascaded into the very next line (`/interface pppoe-server server add ... default-profile=mms-pppoe-profile`) failing with `input does not match any value of default-profile`, since the profile it references was never actually created. Root cause: RouterOS's `/ppp profile` `local-address` property only accepts an actual IP address or an `/ip pool` name -- never a bare interface name, which is what `local-address=vlan-pppoe` was passing (a mistaken assumption made when PPPoE's client-addressing was first built, see that entry above -- "borrows that interface's own gateway IP" turned out to describe the *intent* correctly but not the actual required syntax). This exact bug existed in three places that had all copied the same wrong line: both script generators (`generatePppoeScript()`, `generateFreshInfrastructureScript()`) and the live-API path (`RouterOsConnectionService::applyPppoeProfileAndServer()`). Fixed in the two script generators by baking in the VLAN's bare gateway IP (`str($settings['pppoe_gateway'])->before('/')`) instead of the interface name -- the exact same `->before('/')`-stripping pattern this file already uses correctly for POS/Staff/Management's own DHCP `gateway=`/`dns-server=` lines, just never applied here. The live-API path needed a slightly different shape: a new private `pppoeLocalAddress()` only has a real answer for the app's own default `vlan-pppoe` interface (reading the same `pppoe_gateway` setting `ensurePppoeInfrastructure()` already uses to address that VLAN) and returns `null` for a caller-overridden custom interface, in which case `local-address` is simply omitted from the query rather than guessed -- the same "assume the admin manages this another way" stance `ensurePppoeInfrastructure()`'s own no-op already takes for that case.

Saving just `zerotier_node_id` (the one field that changes every time a ZeroTier-only router is reset, since a fresh reset always generates a brand-new node identity) used to need the full 4-step edit wizard -- real friction during repeated live reset/re-onboard testing. `App\Livewire\Admin\RouterCredentialsCard::saveZeroTierNodeId()` (2026-09-21) adds an inline input + Save button directly on the router's own page instead, next to the existing "Authorize & connect now" button, reusing the same uniqueness rule `RouterManagementService::rules()` applies (`nullable`, `max:16`, unique across routers). Saving a node ID that's actually *different* from what was previously saved also clears `zerotier_authorized_at` -- this card displays "Authorized X ago" straight off that timestamp, and leaving a stale one in place after typing in a brand-new ID would misleadingly claim the new (never-yet-authorized) node was already approved. Re-saving the *same* value leaves the timestamp untouched. The full edit wizard's own save path doesn't clear this timestamp on a node ID change either (a pre-existing gap, not fixed here) -- this quick-save action is the one place that got it right, since showing a stale authorization status right next to the very field being edited for exactly that reason would be actively misleading in a way the wizard's more general-purpose form doesn't as directly invite.

`generateFreshInfrastructureScript()`'s firewall input chain only ever accepted `wg-saas`, with no equivalent for ZeroTier at all -- confirmed live 2026-09-21 on the first real ZeroTier-only router to actually apply this script: the tunnel itself stayed `OK`/reachable (the router could still ping the Pi outbound just fine, since that's the forward/output path, not the input chain this bug lives in) and the RouterOS API service was correctly restricted to `10.9.0.0/24`, yet "Test Connection" from the Pi timed out -- the script's own catch-all `in-interface-list=!WAN action=drop` rule silently blocked the Pi's *incoming* API connection on `zerotier1`, since nothing accepted it first. Outbound-works-but-inbound-doesn't is exactly what a missing input-chain accept rule looks like, and ping succeeding is not evidence the API is reachable -- worth remembering for the next report that looks like this. Fixed by making the WireGuard accept rule conditional on `includesWireguard($router)` (previously unconditional even though the router might not use WireGuard at all) and adding a matching `in-interface=zerotier1` accept rule conditional on `includesZeroTier($router)`, mirroring the `includesWireguard()`/`includesZeroTier()` pattern `radiusClientLines()`/`apiServiceAddressRestriction()` already use elsewhere in this file for exactly this kind of per-tunnel branching. A `wireguard_zerotier` dual-mode router now gets both accept rules; before this fix it silently only ever got the WireGuard one, meaning a dual-mode router whose WireGuard tunnel went down would have lost API access over its ZeroTier fallback too, the fallback's entire reason for existing.

`html-directory=flash/hotspot` and `dns-name=<hotspot_dns_name>` are both set on the hotspot profile (`apiUserProvisioningLines()`'s sibling, the hotspot-profile step in `provisionHotspot()`), but RouterOS does **not** redirect hotspot logins to an external URL on its own just because `dns-name` is set — the local `flash/hotspot/login.html` file itself has to do that, or customers "log in" against RouterOS's own stock local form and never reach this app's portal, payment gateways, or RADIUS provisioning at all. That file used to require a manual copy/paste per router (still documented as a fallback in `docs/router-onboarding.md`'s from-scratch walkthrough) — as of 2026-08-09, `RouterOsConnectionService::pushHotspotLoginPage()` automates it as another `provisionHotspot()` step: the router `/tool fetch`es a small redirect-stub HTML from `GET /hotspot/login-page` (`PortalController::loginPage()`, content from `MikroTikProvisioningService::hotspotLoginPageHtml()`) into a local directory. The stub carries MikroTik's own login-time variables (`$(mac)`/`$(identity)`/`$(link-login)`/`$(link-orig)` — substituted by RouterOS when it serves the file, not by Laravel) into the real portal URL via a `window.location.replace()`. It has no per-router content at all — every router fetches the exact same file, since there's only one portal host per install (`MikroTikProvisioningService::loginPageUrl()`, built from the same host as `portalUrl()` rather than Laravel's `route()`/`APP_URL`, so it stays correct if `HOTSPOT_PORTAL_URL` points at a different public host). `/tool fetch` was chosen over trying to write file content through the RouterOS API directly — the binary API has no reliable cross-version way to do that, whereas every router already has outbound reach to the portal host (the same host its own walled-garden entries allow customer devices to reach), so having the router pull the file itself is simpler and more reliable. Needs no new API user policy — `test` (which `/tool fetch` requires) was already granted.

The automatic `provisionHotspot()` step pushes to `RouterOsConnectionService::DEFAULT_HOTSPOT_DIRECTORY` (`flash/hotspot`) — correct for a router freshly onboarded through this app (that's exactly what `saas-prof`'s own `html-directory` is), but **not** guaranteed for a router that already had a hotspot server set up another way (MikroTik's own `/ip hotspot setup` wizard, a differently-named profile, or an older/different RouterOS version — confirmed live: the same file shows as `hotspot/login.html` with no `flash/` prefix on some routers). Blindly hardcoding the destination would silently write into a directory RouterOS never actually serves from, leaving the admin thinking it's fixed when nothing changed on the live router. `pushHotspotLoginPage(Router $router, ?string $directory = null)` takes an optional directory override, and `RouterOsConnectionService::listHotspotDirectories()` (`/file/print` filtered to `type=directory`) lets an admin see a router's real directory layout instead of guessing — both back a standalone "Hotspot Login Page" section on the router's Live tab (`App\Livewire\Admin\RouterHotspotLoginPage`, `resources/views/livewire/admin/router-hotspot-login-page.blade.php`) alongside Wi-Fi Scan/Connected Devices/Console: list directories, pick one (or type one manually), push.

Re-running "Provision via API" used to always push back to the hardcoded default directory regardless of what an admin had picked in that standalone section, confirmed live 2026-09-22 as a real, recurring papercut for a router whose actual directory is `hotspot`, not `flash/hotspot` — every "Provision via API" click (including the scheduled `hotspot:auto-provision-routers` retry) silently reverted it back to the wrong one. Fixed with a new nullable `routers.hotspot_login_directory` column: `RouterHotspotLoginPage::push()` now saves a *successful* push's directory onto the router record (with a "Reset to default" action to clear it back to null/default), and `provisionHotspot()` passes `$router->hotspot_login_directory` through instead of omitting the argument — null for a router that's never had a custom directory saved behaves exactly as before (falls back to `DEFAULT_HOTSPOT_DIRECTORY`), so this is purely additive for every router that doesn't need it.

That fix only covered *where the file gets pushed*, not the *hotspot profile's own `html-directory` property* — a second, more damaging half of the same bug, confirmed live 2026-09-22 from a direct report of "I have to manually fix html-directory after every script paste before login works at all." `saas-prof` (`generateScript()`/`provisionHotspot()`) and `mms-hotspot-profile` (`generateFreshInfrastructureScript()`) both still hardcoded `html-directory=flash/hotspot` unconditionally, completely independent of `hotspot_login_directory` — so a router whose login.html actually lives in `hotspot` kept getting a profile that pointed RouterOS's HTTP server at `flash/hotspot` instead, where nothing exists, and nobody could log in until an admin manually edited the profile by hand after every single provision. This is also exactly why generating a fresh infrastructure script and separately provisioning the hotspot side can produce two profiles with *different* directories: `applyHotspotProfile()` reassigns whichever hotspot server object exists (e.g. `mms-hotspot`, created by the fresh-infra script) over to `saas-prof` — if the two profiles' `html-directory` values disagree, the server ends up pointing wherever `saas-prof` says, not wherever the file actually was written by whichever step ran last. Fixed by adding `MikroTikProvisioningService::hotspotLoginDirectory()` (a one-line `$router->hotspot_login_directory ?: 'flash/hotspot'` helper) and using it for `html-directory=` in all three places this gets generated — both script generators and the live `/ip/hotspot/profile/add`/`/set` step — so the profile and the actual file location can never drift apart again, regardless of which provisioning path was used last.

Pushing the login page live failed with RouterOS's `failure: cannot open file: permission denied` (confirmed 2026-08-09) even though the write-policy fix above already grants `write` — because `/tool fetch dst-path=...` writing to local storage is gated by RouterOS's confusingly-named `ftp` policy flag, not `write`. `ftp` is a holdover name from when file transfer/backup only happened over literal FTP; it does **not** enable the FTP *service* (this app never touches `/ip service ftp`), it gates local file-system write access generally. The API user's policy denied it (`!ftp`) on an original least-privilege assumption made before this account needed to touch files at all. Fixed by granting `ftp` in `apiUserProvisioningLines()`'s policy string. Same remediation as the write-policy fix: a router bootstrapped before this needs its script re-run, or just `/user group set [find name=mmsradius-api-group] policy=<the new string>` pasted directly on the router.

### Tenant scoping is manual, not a global scope

There is no Eloquent global scope for tenancy. Every tenant-scoped query/authorization goes through the static helpers in `app/Support/TenantAccess.php` (`scopeShops`, `scopeRouters`, `scopePackages`, `assertShop`, `assertRouter`, etc.), each of which special-cases `$user->isSuperAdmin()` to bypass the `tenant_id`/`shop.tenant_id` filter. When adding a new tenant-owned resource, add a matching `scopeX`/`assertX` pair here rather than filtering ad hoc in the controller. Controllers also gate super-admin-only actions with inline `abort_unless(request()->user()->isSuperAdmin(), 403)` (e.g. `TenantController`) — this stays true for `super_admin` vs `tenant_admin`. **`TenantAccess` answers "which rows can this actor see," not "can this actor perform this action"** — that second question is what the `tenant_staff` role below needs, and it's a separate mechanism.

Three roles: `super_admin` (platform owner, no `tenant_id`), `tenant_admin` (full access to one `tenant_id`), and `tenant_staff` (scoped to one `tenant_id` like `tenant_admin`, but further restricted to specific feature areas). Staff authorization is the one place this codebase DOES use route-level middleware: `App\Http\Middleware\AuthorizeTenantStaff` wraps the entire `admin.*` route group in `routes/web.php` and checks each request's route name against the deny-by-default map in `App\Support\StaffPermissions::forRoute()` (`User::canAccessRoute()` is the model-side helper it and the sidebar nav both call). Super admin and tenant admin are unaffected — the middleware is a no-op for them. When adding a new admin route that staff should ever reach, it needs a deliberate entry in that map; nothing is allowed by default. See `docs/roles-and-product-direction.md` for the full rule set and the permission catalog.

### Request flow: thin controllers, fat services

`app/Http/Controllers/Admin/*` and `app/Livewire/Admin/*` stay thin and delegate business logic to `app/Services/*ManagementService.php` (e.g. `PackageManagementService`, `RouterManagementService`, `PppoeSubscriberManagementService`, `PosDeviceManagementService`, `VoucherManagementService`). Reporting has its own service layer (`SalesReportService`, `PaymentReportService`, `SubscriptionReportService`, `SecurityActivityReportService`). Livewire is used for interactive index/filter/table components; plain controllers handle CRUD resources and exports.

The real, tenant-bound router create/edit form (`admin/routers` — not the unrelated standalone script generator) is a 4-step wizard on `App\Livewire\Admin\RoutersIndex` (2026-08-08), not a single flat form: Identity, Hardware (wireless yes/no + port count/roles), Features (POS/PPPoE/QoS + conditional wireless credentials), Network plan. `App\Http\Controllers\Admin\RouterController::create()`/`edit()` now just redirect into this wizard (`?open=create` / `?open_edit={id}`) instead of rendering their own page — the old parallel full-page form (`admin/routers/form.blade.php`) was deleted since maintaining a second, independently-drifting implementation of the same step-gated/conditional form wasn't worth it; `store()`/`update()` and `RouterManagementService::validated()` are kept as-is for non-Livewire regression coverage, just no longer linked from the UI. Wireless-only fields (`builtin_wifi_interface`, `mgmt_wifi_password`, `staff_wifi_password`, `pos_wifi_password`) and POS/PPPoE network fields only render when their matching `enable_*` toggle is on, backed by `required_if` rules in `RouterManagementService::rules()` so they can't be saved blank while enabled.

Ports are no longer typed as raw interface-name strings by default — `App\Support\RouterPortLayout` (pure, static, framework-free) turns a `port_count` into numbered dropdown options (`portOptions()`) and reverse-derives a port number from an existing `"etherN"` string (`portNumberFromInterfaceName()`, returns `null` for anything that doesn't match, e.g. `sfp-sfpplus1`). `RouterManagementService::derivePortInterfaceNames()` converts `wan1_port_number`/`wan2_port_number`/`trunk_port_number`/`pi_port_number` into the `wan1`/`wan2`/`trunk_port`/`pi_port` strings `MikroTikProvisioningService` actually reads — that service needed zero changes, since it still just reads plain interface-name strings. An "advanced: type interface names manually" toggle (`ports_advanced_mode`) bypasses all of this for non-standard interfaces. On edit, `RoutersIndex::routerProvisioningSettings()` reverse-derives port numbers from a router's saved strings so the dropdowns open pre-selected; if any of the four doesn't cleanly parse, it opens in advanced mode instead of guessing wrong — and a router that's never re-edited keeps generating byte-identical scripts, since the derivation only overwrites a string when its `*_port_number` was actually submitted (a real bug caught during this work: `RouterManagementService::validated()` used to call `normalize()` and then `create()`/`update()` called it *again*, so the second pass saw the first pass's defaulted port number as if it had been explicitly submitted and clobbered manually-typed strings like `sfp-sfpplus1` — fixed by making `validated()` return unnormalized data and letting `create()`/`update()` be the single normalization point).

`routerProvisioningSettings()`'s own `port_count` handling had a second, separate bug, confirmed live 2026-09-23 and fixed twice: it unconditionally overwrote `provisioning_settings.port_count` with `(the highest role port number in use) + 2` every time the edit wizard opened, discarding whatever the admin had actually saved. A first fix turned that into a floor (`max($savedPortCount, $minPortCount)`) instead of a flat overwrite — but this still won in most cases and the symptom persisted, since `wan2_port_number` defaults to `8` (`RouterManagementService::defaultProvisioningSettings()`) and is always folded into that `max()` even when the router's second WAN is disabled and that port number is functionally irrelevant — so the "floor" itself was almost always `>= 10` regardless of what was genuinely saved. Fixed properly by only ever deriving/overriding `port_count` here when the router's own saved `provisioning_settings` never had the key **at all** (`! array_key_exists('port_count', (array) $router->provisioning_settings)`, e.g. a router created before this field existed) — any router that has ever explicitly saved a value, however small, is now trusted completely rather than second-guessed against a role-port-derived minimum.

Beyond the four singular port roles above, a router can also declare **extra untagged access ports** per VLAN role (management, hotspot, staff, POS — deliberately not PPPoE, which is architecturally a dial-up service rather than a shared access-port VLAN) via four new comma-separated `provisioning_settings` keys (`extra_{role}_port_numbers`/`extra_{role}_ports`, pluralized siblings of `trunk_port_number`/`trunk_port`, derived the same way and short-circuited by the same `ports_advanced_mode` toggle) — motivated by a real router (a MikroTik RB5009UPr+S+IN with no built-in Wi-Fi) needing a second untagged management port (`eth2`, separate from the Pi's own `eth3`, for direct laptop testing) plus three untagged hotspot ports (`eth5`-`eth7`, for non-VLAN-capable APs or direct hotspot testing) — none of which fit the old fixed-4-role model, and deliberately built generic rather than hardcoded to that one topology, since other router models/sites need different numbers of extra ports per role. `App\Support\RouterPortLayout::interfaceNamesFromNumberList()`/`portNumbersFromInterfaceList()` centralize the CSV parsing (mirroring `interfaceName()`/`portNumberFromInterfaceName()` for the singular case), and every individual extra-port number is flattened into `RouterPortLayout::conflictingRoles()`'s label→port map (one entry per port, e.g. `"Extra hotspot port (#1)"`) inside `RouterManagementService::portConflictRule()` — so both cross-role collisions (an extra port reusing WAN1's number) and duplicate numbers typed into the same list (`"5,5"`) are caught by the one existing conflict detector, no new one needed. `MikroTikProvisioningService::generateFreshInfrastructureScript()`'s no-wifi branch previously combined every non-mgmt VLAN into a single shared tagged-only catch-all line (`vlan-ids=20,30,40,50`) — naively adding a dedicated untagged line per role whenever it has extras, without also removing that role's VLAN ID from the catch-all, would have emitted the same `vlan-ids=` value on two separate bridge-vlan-table lines. Fixed by pulling a role's VLAN ID out of the catch-all only when it actually has extra ports configured this run, giving it its own dedicated tagged+untagged line instead (the same shape the built-in-Wi-Fi branch already uses per VLAN, unconditionally) — when a role has no extras, its VLAN ID stays in the catch-all exactly as before, so a router with none of these new keys set generates a byte-identical script to before this feature existed (confirmed by every pre-existing fresh-infrastructure-script test passing unchanged).

`/ip firewall filter` (the router's whole "drop everything but WAN/mgmt/hotspot/POS" ruleset above) only ever sees IP traffic — confirmed live 2026-09-20 from a report of reaching a router over Winbox from a non-management port (an extra hotspot port) despite that firewall being active. Winbox's "Neighbors" discovery and MAC-Telnet are a separate Layer 2 mechanism (`/tool mac-server`, `/tool mac-server mac-winbox`) that bypasses `/ip firewall filter` entirely and is wide open on every interface (`allowed-interface-list=all`) by default — an IP-level firewall alone was never going to stop it. `generateFreshInfrastructureScript()` now also builds an `MGMT-ACCESS` interface list containing the actual physical ports carrying management traffic (`pi_port` plus any `extra_mgmt_ports`) and restricts both mac-server settings to it. This has to reference the physical ports, not the `vlan-mgmt` L3 interface — a MAC-level frame is evaluated at the point it ingresses the bridge, before any VLAN/IP processing happens, so a Layer 3 VLAN interface is the wrong thing to restrict against here.

The `provisioning_settings.profile` preset used to include `l009_builtin_wifi`, a preset literally named after a specific MikroTik board — removed in favor of the independent `enable_builtin_wifi` toggle (any of the remaining `starlink_plaza`/`small_hotspot`/`pppoe_isp` bandwidth/VLAN templates can have wireless on or off now). A data-only migration (`2026_08_07_120000_remap_l009_builtin_wifi_router_profile.php`) rewrites just the `profile` key on already-saved rows to `small_hotspot`, leaving every other field (`wan1`/`wan2`/`enable_builtin_wifi`/etc.) untouched — those were already fully materialized per-row at save time, not re-derived from the profile string, so this is cosmetic for existing routers, not a behavior change.

### Payment gateways

Two independent gateway stacks exist, both selected/configured per entity via `App\Support\PaymentGatewayCatalog`:

- **Tenant/shop-level hotspot checkout** (customer paying for hotspot/PPPoE/POS access): `FlutterwaveService`, `PaystackService`, `MonnifyService`, `SquadService`, `StripeService`, `ManualBankTransferService`, orchestrated by `App\Services\Payments\HotspotHostedCheckoutManager` implementing `App\Services\Payments\Contracts\HotspotHostedGateway` per provider, confirmed via `HotspotPaymentConfirmationService`. Entry points are the `/hotspot/pay`, `/hotspot/payment/*` routes on `PortalController`.
- **Platform billing** (tenant paying HotspotFreeRAD for their subscription plan): `PlatformFlutterwaveService`, `PlatformStripeService`, confirmed via `PlatformBillingConfirmationService`. Entry points are the `/billing/*` routes on `Admin\BillingController`.

Webhook routes (`/hotspot/payment/webhook`, `/billing/payment/webhook`) are explicitly excluded from CSRF (`withoutMiddleware([ValidateCsrfToken::class])`) since gateways POST to them directly — keep that exclusion narrow if adding new webhook routes.

A shop has exactly one active gateway at a time (`Shop::paymentGateway()`, defaults to `flutterwave`), not a menu of simultaneously-enabled gateways — `resources/views/hotspot/portal.blade.php` reads it directly (`$shop->paymentGatewayName()`/`paymentGatewayLogoUrl()`) to show the customer which gateway they're paying through, and only Flutterwave gets the OPay/Transfer/Card sub-choice (the other gateways route through `HotspotHostedCheckoutManager` regardless of `payment_method`). Because 5 of the 6 gateways redirect the customer's browser to an external hosted checkout domain *before* the device is RADIUS-authenticated, each gateway also carries `walled_garden_hosts` metadata in `PaymentGatewayCatalog` — `MikroTikProvisioningService::walledGardenLines()` emits `/ip hotspot walled-garden add dst-host=...` entries for the router's shop's active gateway (plus the portal host and `*.cloudflare.com`) in both `generateScript()` and `generateFreshInfrastructureScript()`. Those host lists are best-effort, based on each provider's known public checkout domains — not verified against a live checkout flow from this codebase.

A router whose walled-garden entries don't cover its shop's active gateway fails checkout hard, not gracefully: MikroTik can rewrite the captive-portal login redirect into unencrypted HTTP responses, but for HTTPS destinations outside the walled garden it can't inject anything into the encrypted stream, so it resets the connection instead — the customer sees `net::ERR_CONNECTION_CLOSED` at "Continue to payment" rather than a redirect to login. This only self-heals on routers that get a fresh script paste or a manual "Provision via API" click; a shop that switches gateways without re-provisioning its routers silently breaks checkout (diagnosed 2026-08-07 from a live Squad report — Squad's own domains were already covered by the `*.squadco.com` wildcard, the router just never got the new gateway's entries pushed). Two fixes: `RouterOsConnectionService::provisionHotspot()`'s live API push now also walled-gardens the shop's active gateway (it previously only added the portal host, so even the manual remediation path was incomplete) via a new public `syncWalledGarden()` method it shares with the fix below; and `PaymentSettingsService::update()` now diffs the shop's `payment_gateway` before/after and, when it changed, dispatches `App\Jobs\SyncRouterWalledGarden` (queued, default queue — picked up by the existing Pi worker with no deployment change) for every router the shop owns, so switching gateways in Payment Setup re-syncs live routers automatically instead of requiring a manual re-provision.

The exact same `net::ERR_CONNECTION_CLOSED` failure mode hit the "Message support on WhatsApp" link on `hotspot.payment-failed` too, confirmed live 2026-09-22 — `wa.me` was never in any walled-garden list at all, since it's not gateway-specific and so was never covered by `PaymentGatewayCatalog::walledGardenHosts()`. Fixed by adding `wa.me`/`*.wa.me` to `walledGardenLines()`'s unconditional entries (alongside the portal host and `*.cloudflare.com`) rather than gating it per-gateway. That fix alone wasn't enough, though, confirmed the same day: `RouterOsConnectionService::syncWalledGarden()` (the live-API path both "Provision via API" and `hotspot:resync-walled-garden` use) has its own **separate, duplicated** `$entries` list rather than calling `walledGardenLines()` -- so neither a re-provision nor `hotspot:resync-walled-garden` ever actually pushed `wa.me` to a live router, both reporting a clean "synced" purely because nothing in *their* (smaller, wrong) list was missing. Fixed by adding the same `wa.me`/`*.wa.me` entries there too -- worth remembering for any future walled-garden host addition: it has to go in both places, the script generator and this live-sync method, since they're not one shared source of truth.

`provisionHotspot()`'s "Add hotspot profile" step was also never made idempotent like everything else in this file -- a plain, unconditional `/ip/hotspot/profile/add`, confirmed live 2026-09-22 to fail every single "Provision via API" click after the very first one with `failure: server profile with such name already exists`, even though nothing was actually wrong (the profile was correct, just already there). `RouterOsConnectionService::existingHotspotProfileId()` (new) checks first via `/ip/hotspot/profile/print`, and the step now does `/ip/hotspot/profile/set` on the existing `.id` instead of `/add` when one's already there -- matching the "list-then-diff" shape every other step in `provisionHotspot()` already has. Failing to reach the router during this check falls back to attempting `/add` (the original behavior), so an unreachable router's error reporting is unchanged.

A second, unrelated bug surfaced in the same live report: a customer whose payment *did* verify and whose RADIUS access *was* granted still saw an endless loop between "Access provisioned" and MikroTik's own login page, with no internet access. `resources/views/hotspot/access-granted.blade.php` auto-submitted a `<form method="POST" action="{{ $loginUrl }}">` to MikroTik's local hotspot login endpoint, and the theory at the time was that this cross-scheme (HTTPS portal → plain-HTTP router) form submission was hitting a browser "this form is not secure" warning an invisible auto-submit could never click through. That theory was never actually confirmed and turned out to be a distraction — see the correction below, at the end of this whole saga, for what the login mechanism actually needed. The rest of this paragraph and the two after it are kept as-written for the debugging trail, since each was a genuine, separately-confirmed bug along the way even though the very first fix attempted here was later reverted.

That fix alone still wasn't enough, confirmed the same day from continued live testing (the loop persisted even for the free "Start test access" path, which shares the exact same `access-granted` mechanism, ruling out anything payment-specific) — a more fundamental gap: `MikroTikProvisioningService::hotspotLoginPageHtml()`'s redirect stub (the file `pushHotspotLoginPage()` pushes to `flash/hotspot/login.html`) only ever captured MikroTik's `$(mac)`/`$(identity)`/`$(link-login)`/`$(link-orig)` template variables — **`$(link-login-only)` was never captured at all**, an oversight present since this stub was first written (neither the code nor its own docblock ever mentioned it). `PortalController::mikrotikLoginUrl()` already explicitly prefers `link-login-only` over `link-login` (checks it first) precisely because `link-login-only` is MikroTik's documented endpoint for external/automated login pages — it accepts a plain username/password directly, with no CHAP-challenge handshake required. Since the stub never passed `link-login-only` through, that preference was never actually reachable in practice: every login fell back to `link-login`, MikroTik's standard *interactive* login endpoint, which expects the router's own challenge-response page flow rather than a directly-submitted plain password — so the login attempt was likely being rejected at the RouterOS level regardless of how it was submitted (form or GET), independent of the browser-warning fix above. Fixed by adding `$(link-login-only)` capture to the stub alongside the existing variables.

Even with that fix deployed and the router's `login.html` confirmed (by directly downloading it from the router) to have `$(link-login-only)` correctly captured, the same loop persisted -- traced to the actual **value** RouterOS was substituting: `http://hotspot.local/login`. `services.mikrotik.hotspot_dns_name`'s own default (`config/services.php`) was `'hotspot.local'` -- and `.local` is reserved for mDNS/Bonjour on iOS, macOS, and many Android resolvers, meaning those devices never send a normal unicast DNS query for it to the router at all (only local multicast discovery, which nothing here answers). MikroTik's own hotspot DNS interception -- the mechanism that's supposed to resolve this name to the hotspot's own IP for still-unauthenticated clients -- relies on intercepting a normal DNS query, so it never even sees the request either. The device can never resolve the login host, the `link-login-only` GET never reaches the router, and the device stays stuck unauthenticated forever: this is what the "Opening internet access" ↔ "Access provisioned" loop actually was, independent of every other fix above (which were all real, necessary fixes too -- this was the last of several layered bugs in the same flow, not a replacement for them). Fixed the default to `'hotspot.example.com'` -- any real subdomain works, since this only ever needs to resolve via MikroTik's own local interception for still-unauthenticated hotspot clients, never a real public DNS record. A router already provisioned with the old `.local` value needs `HOTSPOT_DNS_NAME` set explicitly in `.env` (not just relying on the fixed default) and re-provisioning to push the new `dns-name` to its hotspot profile.

**A correction along the way**: even with DNS resolving correctly (confirmed via `nslookup`) and every fix above genuinely in place, the loop *still* persisted. Chrome DevTools' Network tab, pointed at the exact request `access-granted` was making, showed a real clue: the GET-based `link-login-only` submission (the very first fix in this saga, replacing the original POST form) returned `200 OK` with `expires`/`last-modified`/`cache-control` headers characteristic of RouterOS serving a *static file* -- i.e. RouterOS was just serving `login.html` again for that request, never processing it as a login attempt at all. `access-granted.blade.php` was reverted back to the original `<form method="POST">` on the theory that RouterOS needed POST specifically. That theory turned out to be incomplete -- see below -- but the revert was harmless and POST is what MikroTik's own documentation specifies for this method regardless, so it stayed.

**The actual root cause**: reverting to POST produced the *exact same* symptom -- `200 OK`, identical static-file response headers, RouterOS still just re-serving `login.html` rather than processing the submission -- proving the failure was never about GET vs POST at all. `/radius monitor 0` on the router nailed this down conclusively: its request/accept counters never moved no matter how many login attempts were made (GET, POST, or even a native voucher attempt bypassing this app's flow entirely), meaning RouterOS was never even reaching the point of asking RADIUS anything. The real cause was sitting in the live-provisioning code the whole time: `RouterOsConnectionService::provisionHotspot()`'s hardcoded hotspot-profile `login-by` was `http-chap,cookie,mac-cookie` -- missing `http-pap` -- while both script generators (`MikroTikProvisioningService::generateScript()`/`generateFreshInfrastructureScript()`) correctly included it. `http-pap` is the method that accepts a plain, directly-submitted username/password (exactly what the login form sends); `http-chap` requires a router-issued challenge/response handshake the form never performs. Without `http-pap` in the allowed list, RouterOS never recognized the submission as a valid login attempt of *any* accepted type, and fell back to just re-serving the login page -- before ever reaching a RADIUS check, which is exactly why nothing showed up in `freeradius -X` either. Every router provisioned live via "Provision via API" (as opposed to a manually pasted script) has been missing `http-pap` since this profile-management code was first written -- a router needs `provisionHotspot()` re-run after this fix to pick up the corrected `login-by` on its live profile. The lesson worth keeping twice over: DevTools' response headers (not just the status code) and `/radius monitor`'s request counters were what actually cut through several rounds of plausible-but-wrong guesses about the browser and DNS layers -- the real bug was one hardcoded string missing a single comma-separated value, in a completely different file from where all the debugging attention was pointed.

**USSD and NQR (Nigeria QR)** (2026-09-24, direct request for Nigeria-relevant Flutterwave methods beyond the existing OPay/Transfer/Card trio) reuse the exact same v4 orchestration direct-charge mechanism OPay already used — `FlutterwaveService::initializeCheckout()`/`paymentMethodType()` already passed `$customer['payment_method']` straight through to `payment_method.type` with zero method-specific branching, so adding these needed no service changes at all: `PortalController::pay()`'s validation rule and its dispatch condition (`if ($paymentMethod === 'opay')`) both widened to `in_array($paymentMethod, ['opay', 'ussd', 'nqr'], true)`, and `resources/views/hotspot/portal.blade.php`'s payment-method picker grew two more options. Flutterwave's hosted redirect page is what actually renders the USSD dial code or QR image (the same page that already renders OPay's own UI) — not yet confirmed against a live checkout, matching this codebase's honesty pattern for other freshly-added integrations. No new walled-garden entries needed — `PaymentGatewayCatalog::walledGardenHosts()`'s existing `*.flutterwave.com`/`*.ravepay.co` wildcards already cover any method on Flutterwave's hosted checkout domain, since they're keyed to the gateway, not the specific payment method chosen within it.

**That "not yet confirmed against a live checkout" caveat was warranted** — live testing with test credentials the very next day (2026-09-25) confirmed both USSD and NQR actually failed. NQR's failure was terminal: `"Invalid value 'nqr' for PaymentMethodIn"`, and Flutterwave's own v4 API reference (`developer.flutterwave.com/v4.0.0/reference/orchestration_direct_charge_post.md`) confirms `nqr`/QR was never a real `payment_method.type` for this endpoint at all — the original assumption it existed was simply wrong, so it was removed outright (validation rule, dispatch branch, and the portal dropdown option) rather than fixed, since there's no correct payload shape to fix it to. USSD's failure was narrower and fixable: `"payment_method.ussd must not be null"` — unlike OPay's flat `{type: "opay"}` shape, Flutterwave's v4 API requires USSD charges to carry a nested `payment_method.ussd.account_bank` (the customer's own bank code). `FlutterwaveService::paymentMethodPayload()` now builds that nested object when the type is `ussd`, and a new public `FlutterwaveService::banks(Payment $payment)` (`GET /banks?country=NG`, the same endpoint `PlatformFlutterwaveService::banks()` already used for settlement-account verification) backs a bank-selection `<select>` on the portal that only renders when USSD is chosen (`x-model="payment_method"`/`x-show="payment_method === 'ussd'"` in `portal.blade.php`). `PortalController::ussdBanks()` fetches and caches that list per shop (`Cache::remember`, 6 hours) — gated behind `FlutterwaveService::isConfiguredFor()` so a shop with no saved Flutterwave credentials never triggers a live API call just from loading the portal page, and failing open to an empty list (USSD simply isn't offered) rather than breaking the whole portal on a credentials or network hiccup.

**USSD was removed entirely the next day, confirmed live** (2026-09-25) — even with the correctly-nested `payment_method.ussd.account_bank` payload above, every real checkout attempt came back `REQUEST_NOT_VALID: "Invalid bank code"` from Flutterwave's live API, for every bank the customer picked from the `/banks?country=NG` dropdown. Checked directly against Flutterwave's own v4 docs before concluding this was unfixable from this codebase's side: the `account_bank` field has no documented enum, just a `^\d{3,}$` pattern, and their own integration guide says to reuse the exact bank code from `GET /banks?country=NG` — which is exactly what this app did. Their own documented example value (`"050"`, Ecobank) was tried directly and rejected identically, ruling out "wrong bank" as the cause — Flutterwave's backend is validating `account_bank` against some undocumented, account-specific list of USSD-enabled banks that has nothing to do with the general bank list their own docs point integrators at. This is the same class of "confirmed broken at the platform level, not a code bug" outcome NQR hit — so USSD was removed the same way: the dropdown option, `payment_method` validation rule, `ussd_bank_code` field/validation, `FlutterwaveService::paymentMethodPayload()`'s nested-object branch (reverted to the original flat `['type' => ...]` payload), and `FlutterwaveService::banks(Payment $payment)`/`PortalController::ussdBanks()` (both now dead code with USSD gone, deleted rather than left unused — distinct from `PlatformFlutterwaveService::banks()`, which stays, since it backs the unrelated, still-working bank-account verification feature). Re-adding USSD later would need Flutterwave support to confirm which banks are actually enabled for this account's USSD product, not just retrying the same integration.

**Platform-level Flutterwave card checkout was built out, not just documented as missing** (2026-09-25, direct follow-up once the misleading-text investigation above surfaced that the gap was real and worth closing) — a live report of a broken card attempt against a wallet-enabled shop traced back to `PaymentGatewayCatalog::platformCredentialFields()` deliberately stripping `secret_key` out of the Platform Billing settings form for Flutterwave, on the theory that "platform billing only ever calls the v4 orchestration API." That was true, but the *reason* card couldn't work wasn't the missing field — it's that Flutterwave's v4 `/orchestration/direct-charges` endpoint's `payment_method.type: "card"` requires real encrypted card details on the request, which no server-side redirect flow in this app has ever collected; the tenant-facing hotspot checkout already knew this and routes `card` around its own v4 call entirely (`PortalController::pay()`'s `elseif ($paymentMethod === 'card')` branch, checked *before* the `initializeCheckout()` branch), using the older v3 hosted `/payments` checkout instead. Platform billing's "Default billing method: Card" dropdown option existed in the UI with no working path behind it at all -- selecting it would have sent `payment_method.type: "card"` straight into v4 orchestration and failed the same way NQR did.

Fixed by giving platform billing the same v3 hosted-checkout mechanism the tenant side already has: `platformCredentialFields()` no longer hides `secret_key` (now a real, savable "Secret Key (v3 card checkout)" field on the Platform Billing settings card); `PlatformFlutterwaveService::createStandardHostedCheckout()` mirrors `FlutterwaveService::createStandardHostedCheckout()` exactly, charging a `PlatformBillingPayment` against the platform's own v3 secret key; `verifyPayment()` gained the same `flutterwave_checkout_version === 'standard_v3'` branch tenant verification already uses (its signature changed to take the `PlatformBillingPayment` too, needed to read that payload flag -- its one caller, `PlatformBillingConfirmationService::verifyAndActivate()`, updated to match). `BillingController::checkout()` now detects `active_gateway === flutterwave && default_payment_method === 'card'` before ever calling `initializeCheckout()` and routes to the hosted-checkout method instead, recording `flutterwave_checkout_version` in the payment's payload the same way the hotspot side does; `PlatformBillingConfirmationService`'s existing generic Flutterwave verification-matching branch needed no changes, since a v3 verify response's `data.reference`/`data.tx_ref`/`data.amount`/`data.currency`/`data.status` shape is already compatible with it.

This same platform-level secret key also closes wallet mode's parallel gap: `FlutterwaveService::hostedCheckoutSecretKey()`/`hostedCheckoutCredentialSource()` used to unconditionally return unconfigured for a wallet-enabled shop's card checkout, since no platform-level v3 credential existed anywhere to fall back to -- both now read `PlatformPaymentSettingsService::flutterwaveHostedCheckoutSecretKey()` when `usesWalletCredentials()` is true, so a wallet-enabled shop's customers can use card the moment a super admin saves this one platform-level key, with no other wallet-mode code touched. Not yet confirmed against a live checkout for either platform billing or wallet mode -- matching this codebase's honesty pattern for other freshly-added integrations.

**Card checkout's new v3 hosted-checkout link hit the exact `net::ERR_CONNECTION_CLOSED` walled-garden failure mode documented above, confirmed live 2026-09-25 immediately after the card checkout feature shipped** — Flutterwave's `/v3/payments` response redirected the customer to `checkout-v2.dev-flutterwave.com`, a completely different domain from `flutterwave.com` and therefore not covered by the existing `*.flutterwave.com`/`*.ravepay.co` walled-garden wildcards. Fixed by adding `*.dev-flutterwave.com` to `PaymentGatewayCatalog::onlineGateways()['flutterwave']['walled_garden_hosts']` — unlike the earlier `wa.me` story elsewhere in this file, `RouterOsConnectionService::syncWalledGarden()` and `MikroTikProvisioningService::walledGardenLines()` both already read this same catalog array directly rather than keeping their own duplicated lists, so this one fix covers both the script generator and the live-API sync with nothing else to touch. A router needs a fresh script paste or "Provision via API"/`hotspot:resync-walled-garden` to actually pick up the new host, same as any other walled-garden addition. **Confirmed fixed live 2026-09-26** after resyncing — card checkout now reaches Flutterwave's hosted page instead of `net::ERR_CONNECTION_CLOSED`.

Rendering "Not configured" badges that never cleared no matter how many times the form was saved (confirmed live 2026-09-24, Flutterwave specifically) traced to `PaymentSettingsService::updates()`: the rendered form's credential inputs are all bound to `gateway_settings.{field}` (`PaymentSettingsCard`'s generic per-gateway field loop — the same binding every other gateway already uses), never directly to the dedicated `flutterwave_client_id`/`flutterwave_client_secret`/`flutterwave_secret_key`/`flutterwave_webhook_secret` Livewire properties. The fallback (`$data['flutterwave_client_id'] ?? ($gatewaySettings['client_id'] ?? null)`) used `??`, which only triggers on `null` — but those dedicated properties are always an empty string (never null, since nothing in the blade ever sets them), so the fallback to the actual typed value in `gatewaySettings` never fired, and a Flutterwave credential typed into the real form could never reach the encrypted `shops` columns `FlutterwaveService` actually reads from. The "Clear client credentials"/"Clear webhook secret"/"Clear card checkout secret key" checkboxes were unaffected (they bind directly to their own dedicated properties), which is why clearing worked but re-saving new values afterward silently didn't. Fixed by switching the fallback to a `filled()` check, which correctly treats an empty string as "nothing typed here." The existing `test_livewire_payment_settings_card_saves_credentials` test had been passing the whole time despite this bug, because it sets the dedicated `flutterwave_*` properties directly rather than through `gateway_settings.*` — exercising a path the real rendered form never actually takes.

`PaymentSettingsService::updates()` **merges** newly-submitted `gateway_settings` into a gateway's existing saved settings rather than replacing the sub-array wholesale (fixed 2026-08-06 — it used to silently wipe every field not resubmitted that save, e.g. losing a saved secret key just from switching the Environment dropdown, contradicting the form's own "leave blank to keep saved value" placeholder text). Any future gateway-settings save logic should keep this merge behavior.

**Platform billing gained real Monnify support and a generic multi-gateway settings UI** (2026-09-25, direct request after a super admin noticed `admin/billing`'s platform settings card only ever showed Flutterwave-shaped fields — "Client ID"/"Webhook Secret" — even after selecting Monnify, whose real credentials are API Key/Secret Key/Contract Code). Investigating surfaced something bigger than a UI mismatch: `BillingController::checkout()`'s gateway dispatch was `$gateway === STRIPE ? $stripe : $flutterwave` — **any** non-Stripe active gateway, Monnify included, silently fell through to `PlatformFlutterwaveService` and tried to charge using whatever Flutterwave credentials happened to be saved, completely ignoring the admin's actual selection. Worse, `PlatformStripeService::secretKey()`/`webhookSecret()` reused `PlatformPaymentSettingsService::clientSecret()`/`webhookSecretHash()` — the *same* storage slots Flutterwave used — so Flutterwave and Stripe credentials couldn't coexist at all; switching `active_gateway` to Stripe and saving its real secret key silently overwrote whatever Flutterwave had stored there.

Fixed with a real per-gateway storage redesign, `PlatformPaymentSettingsService` now keeps one `PlatformSetting` row per gateway (`payments.platform.gateway.{key}`, e.g. `payments.platform.gateway.monnify`) plus a separate `payments.platform.general` row for the gateway-independent `active_gateway`/`default_payment_method` choice — mirroring the shape `PaymentSettingsService` already uses for tenants (`tenant.payment_gateway_settings[gateway]`), except every field stays **individually encrypted** here (unlike the tenant side's plaintext JSON) since these are the platform's own master credentials, a meaningfully higher-value target. `gatewaySettings(?string $gateway)`/`gatewayCredential()` are the new generic read primitives; `clientId()`/`clientSecret()`/`webhookSecretHash()` stay as thin wrappers over `gatewaySettings('flutterwave')` purely so `PlatformFlutterwaveService` needed zero changes. A new `PaymentGatewayCatalog::platformCredentialFields($gateway)` mostly mirrors the tenant-facing `credentialFields()`, narrowed for Flutterwave specifically — platform billing only ever calls the v4 orchestration API, never the v3 card-checkout endpoint tenant shops can use, so showing a "Secret Key (v3 card)" field here would be a field that saves but does nothing. A one-time data migration (`2026_09_25_000000_split_platform_payment_settings_per_gateway.php`) splits any already-saved single-slot row into the new shape, mapping its Flutterwave-labeled fields to whichever gateway was actually active at migration time rather than assuming Flutterwave — since that's exactly how a Stripe-active install would have had its real key stored.

New `PlatformMonnifyService` mirrors the tenant-facing `MonnifyService` almost exactly (same `/api/v1/merchant/transactions/init-transaction` init, same access-token caching, same CHAP-free webhook signature check) but reads credentials from `gatewaySettings('monnify')` and charges a `PlatformBillingPayment` instead of a hotspot customer `Payment`. Wired into every dispatch point that used to hardcode "Stripe or else Flutterwave": `BillingController::checkout()`/`platformGatewayIsConfigured()`/`platformWebhookSignatureIsValid()` (now a real `match()`/`if` chain including `monnify-signature` header validation) and `PlatformBillingConfirmationService::verifyAndActivate()`/`verificationMatchesPayment()` (the latter's Monnify branch copied directly from `HotspotPaymentConfirmationService::monnifyVerificationMatchesPayment()`'s already-proven `responseBody.paymentStatus`/`paymentReference`/`currency`/`amountPaid` shape). Not every "live" tenant gateway has a platform equivalent, though — `PaymentGatewayCatalog::platformImplementedGatewayKeys()` is a new, deliberately narrower list (`[flutterwave, stripe, monnify]`) than `implementedGatewayKeys()` (all five online gateways plus manual bank), and `PlatformPaymentSettingsService::activeGatewayIsImplemented()` now checks against it — Paystack/Squad can still be picked as the platform's "Active gateway" for planning (the settings card's copy says as much) but checkout stays disabled until a matching `Platform*Service` actually exists, the same "coming soon" pattern the tenant-facing gateway picker already uses, just scoped to platform-billing readiness specifically rather than tenant-checkout readiness.

**Paystack gained a real platform billing adapter too** (2026-09-26, direct request after a super admin saved Paystack platform credentials and found it permanently stuck on "Adapter pending" with no way to fix it) — new `PlatformPaystackService` mirrors the tenant-facing `PaystackService` exactly (same `/transaction/initialize`/`/transaction/verify/{reference}` shape, same `sha512` HMAC webhook signature check against the raw body), reading credentials from `gatewaySettings('paystack')` and charging a `PlatformBillingPayment`. `PaymentGatewayCatalog::platformImplementedGatewayKeys()` grew to `[flutterwave, stripe, monnify, paystack]`, wired into `BillingController::checkout()`/`platformGatewayIsConfigured()`/`platformWebhookSignatureIsValid()` (`x-paystack-signature` header) and `PlatformBillingConfirmationService::verifyAndActivate()`/`verificationMatchesPayment()` (a dedicated Paystack branch was needed, not the generic Flutterwave-shaped default one — Paystack's top-level `status` field is a **boolean** "did the API call succeed", not a status string, and its `data.amount` is in kobo like the tenant-side `paystackVerificationMatchesPayment()` already accounts for). Building this surfaced a real, pre-existing latent bug: `BillingController::callback()`'s "was this actually successful" gate — which skips checking the `status` query param for gateways that don't send one — had a code comment claiming it already excluded "Monnify (and Paystack/Squad)" but the actual `in_array()` list only ever had Monnify/Stripe; harmless while Paystack had no platform adapter to reach that code at all, but it would have rejected every real Paystack platform billing callback outright the moment one existed. Fixed by adding Paystack to that list to match what the comment already (incorrectly) claimed.

Because Paystack's tenant-facing `PaystackService` never gained the `usesWalletCredentials()` branch Flutterwave/Stripe/Monnify each got when wallet mode/platform billing added them, `PlatformPaymentSettingsService::walletGateway()` needed its own, narrower `PaymentGatewayCatalog::walletCapableGatewayKeys()` list (`[flutterwave, stripe, monnify]`, excluding Paystack) distinct from `platformImplementedGatewayKeys()` — otherwise picking Paystack as the platform's "Active gateway" would have silently routed every wallet-enabled tenant's live customer checkout at a shop-level Paystack credential that doesn't exist for them, the exact failure mode `walletGateway()`'s fallback exists to prevent. `activeGatewayIsImplemented()` (which gates platform *billing* checkout, a separate question from wallet routing) keeps using the wider list, since Paystack billing itself genuinely works now.

**Squad completed the set the very same day** ("squad is next" — the last of the five online gateways without a platform billing adapter) — new `PlatformSquadService` mirrors the tenant-facing `SquadService` exactly (`/transaction/initiate`/`/transaction/verify/{reference}`, same `sha512` HMAC check against `x-squad-encrypted-body`). `PaymentGatewayCatalog::platformImplementedGatewayKeys()` grew to all five online gateways (`[flutterwave, stripe, monnify, paystack, squad]` — only `manual_bank` has no platform equivalent, since there's nothing to automate about a tenant paying by hand). Squad needed its own `verificationMatchesPayment()` branch too, for the same reason Paystack did — its response uses entirely its own field names (`success` boolean, `data.transaction_status`/`transaction_ref`/`transaction_amount` in kobo), nothing like the generic Flutterwave-shaped default branch, mirroring `HotspotPaymentConfirmationService::squadVerificationMatchesPayment()`'s existing currency-is-optional handling exactly.

Squad surfaced a genuinely different redirect-URL problem than Monnify/Paystack, though: unlike them, Squad never appends anything of its own to the callback URL at all — confirmed by `HotspotHostedCheckoutManager::callbackUrl()`'s own pre-existing Squad case, which explicitly embeds `?transaction_ref=...` (its own param name, not the generic `tx_ref` Flutterwave/Stripe use) rather than leaving the URL bare like the Monnify/Paystack case does. `BillingController::checkout()`'s redirect-URL logic, previously a plain two-way ternary (bare for Monnify/Paystack, `tx_ref`-embedded for everything else), became a three-way `match()` to give Squad this same explicit `transaction_ref` treatment. Building this also surfaced two small, genuine gaps in the platform-side callback/webhook extraction that had no consequence until Squad's redirect shape needed them: `callback()`'s tx_ref *lookup* never checked `transaction_ref` at all (only `tx_ref`/`paymentReference`/`reference`), and `webhook()`'s txRef/providerReference extraction never checked `data.transaction_ref` either — both fixed by adding the missing key, matching what the hotspot-side equivalents already checked for the exact same reason.

### Consolidating the tenant/platform gateway pairs into one class per gateway (in progress, Monnify piloted first)

Having just built five `Platform*Service` twins of five existing tenant-facing gateway services, the duplication was obvious enough to ask about directly: could this be one reusable service per gateway instead of one per gateway *per caller*? Reading all ten classes plus both confirmation services confirmed the only real differences per pair were (1) where credentials come from (a shop's own settings vs `PlatformPaymentSettingsService`, with tenant services also branching internally on `wallet_enabled` for the ones that ever gained that support) and (2) what's being charged (`Payment` vs `PlatformBillingPayment`) — the actual HTTP request shapes were identical. Verification-matching logic (`*VerificationMatchesPayment()`) was independently duplicated too, on the same axis, since a gateway's response shape never changes based on who owns the credentials.

Chosen approach, scoped deliberately as a **phased, one-gateway-at-a-time migration** rather than a single rewrite, given how directly real money correctness depends on this code: **Phase 0** extracted `App\Services\Payments\PlatformHostedCheckoutManager` (mirroring the tenant side's pre-existing `HotspotHostedCheckoutManager`) purely to move `BillingController::checkout()`/`webhook()`'s inline per-gateway dispatch into its own class, with zero behavior change — confirmed by every existing `PlatformBillingTest` passing unmodified. **Phase 1** then introduced the actual shared abstraction and piloted it on Monnify specifically (picked as the pilot because its tenant/platform pair was already the closest to identical): `App\Services\Payments\GatewayCredentials` (a trimmed, generic key-value wrapper around whatever `PaymentGatewayCatalog::credentialFields()` defines for a gateway), `ChargeRequest`/`ChargeResult` (plain data — reference, amount, currency, redirect URL, customer info, a freeform `meta` array the caller builds however it needs to), and a `Contracts\HostedGateway` interface, implemented once as `App\Services\Payments\Gateways\MonnifyGateway` and called by both checkout managers. `App\Services\Payments\GatewayCredentialResolver` centralizes the wallet-aware "shop's own settings, or the platform's if this tenant has wallet mode on" branching that used to be duplicated (inconsistently — Paystack/Squad never got it) inside each tenant service's own private `setting()`/`secretKey()` method; both `HotspotHostedCheckoutManager` and `HotspotPaymentConfirmationService` now share it for Monnify. `App\Services\Payments\Verification\MonnifyVerificationMatcher` is the equivalent unification for verification matching, called from both confirmation services with just `{reference, currency, amount}` rather than a concrete payment model.

One asymmetry the migration surfaced along the way: `PortalController::webhook()` (tenant side) dispatches webhook signature validation with its own inline `if`/`elseif` chain across all five gateways directly, unlike `PlatformHostedCheckoutManager`, which already centralized this in Phase 0. Fully generalizing that was out of scope for "migrate Monnify only," so `HotspotHostedCheckoutManager::monnifyWebhookIsValid()` is a narrow, explicitly-named method covering just Monnify's branch of that chain for now — Paystack/Squad/Stripe/Flutterwave stay on their old direct-service calls until they're migrated the same way. `MonnifyService` (tenant) is deleted outright, confirmed to have zero remaining references anywhere. `PlatformMonnifyService` is *not* deleted — `BankAccountResolutionService` still depends on its unrelated `banks()`/`resolveAccount()` methods for settlement-account verification, so only its now-dead checkout methods (`initializeCheckout`/`verifyPayment`/`isConfigured`/`webhookIsValid`) were stripped, with a docblock pointing at `MonnifyGateway` for anyone who goes looking for them. Paystack, Squad, Flutterwave, and Stripe remain on their original, unmigrated tenant/platform pairs — each is a candidate for the same treatment in a follow-up pass, with Flutterwave and Stripe expected to be the hardest (Flutterwave's v3/v4 API split and OAuth-style token cache; Stripe's checkout-session shape, meaningfully different from every other gateway's redirect-and-verify pattern).

**Paystack migrated the same day** ("proceed," continuing the one-gateway-at-a-time consolidation) — a genuinely simpler case than Monnify, since Paystack needs no OAuth token step (a plain secret-key bearer token authenticates every call) and, unlike Monnify, nothing else in the codebase depended on `PaystackService`/`PlatformPaystackService` for anything beyond checkout. Both classes are deleted outright rather than stripped-and-kept. `App\Services\Payments\Gateways\PaystackGateway` is the one implementation now, and `App\Services\Payments\Verification\PaystackVerificationMatcher` replaces both confirmation services' separate `paystackVerificationMatchesPayment()` copies. `HotspotHostedCheckoutManager`/`PlatformHostedCheckoutManager` grew a shared `startSharedGateway()` helper (tenant side) — the Monnify-only version from the previous pass was generalized to take any `HostedGateway` instance plus its gateway key/label, since Monnify and Paystack's checkout-initiation logic (resolve credentials, check configured, build a `ChargeRequest`, initialize, handle the result/failure) turned out to be identical once the DTO abstraction existed — only the concrete gateway instance and a couple of label strings differ per gateway. The tenant-side `hotspotChargeRequest()` builder is now shared by both gateways too, confirming the `meta` field bag (payment_id/tenant_id/shop_id/package_id/device_mac/nas_identifier/phone) is genuinely identical across gateways, not just Monnify-shaped. `PortalController::webhook()` gained a matching `paystackWebhookIsValid()` entry point alongside `monnifyWebhookIsValid()`, same "narrow, named method per migrated gateway" pattern as before — Squad/Stripe/Flutterwave still dispatch inline there until they're migrated too. Wallet-mode credential resolution (`GatewayCredentialResolver`) is now technically available to Paystack as well, but confirmed unreachable in practice: `Shop::paymentGateway()` only ever resolves to Paystack for a shop whose tenant is *not* wallet-enabled (wallet-enabled tenants always resolve through `PlatformPaymentSettingsService::walletGateway()`, which excludes Paystack from `walletCapableGatewayKeys()`), so this isn't a behavior change, just an unreachable code path that costs nothing to leave in place for consistency.

**Squad migrated the same day too** (also "proceed"), the third of five and the last of the three "simple" bearer-token gateways (Monnify, Paystack, Squad all needed no per-request OAuth exchange, unlike Flutterwave/Stripe). `App\Services\Payments\Gateways\SquadGateway` replaces `SquadService`/`PlatformSquadService`, both deleted outright (nothing else in the codebase depended on either, the same as Paystack), and `App\Services\Payments\Verification\SquadVerificationMatcher` replaces both confirmation services' duplicated Squad branches. This was close to a copy of the Paystack pattern with one genuine fix found along the way: `SquadService` (tenant) already stripped an optional `"Bearer "` prefix from a pasted secret key before using it, but `PlatformSquadService` (platform) never did — `SquadGateway::secretKey()` now does this unconditionally for both callers, closing a real (if minor) gap where a platform Squad key pasted with that prefix would have silently sent a broken bearer token. Squad's callback-URL handling needed no changes to generalize — `HotspotHostedCheckoutManager`'s existing `callbackUrl()`/`PlatformHostedCheckoutManager`'s existing `redirectUrl()` already special-cased Squad's own `?transaction_ref=...` convention (from the Paystack/Monnify pass), and the shared `startSharedGateway()`/`hotspotChargeRequest()` helpers already called through those unchanged. With Squad done, `HotspotHostedCheckoutManager`'s old `HotspotHostedGateway`-interface path (and its now-trivial `gatewayFor()` dispatch) serves only Stripe; `PlatformHostedCheckoutManager`'s equivalent serves only Flutterwave/Stripe. Flutterwave and Stripe remain, expected to be the hardest of the five for the reasons already noted above.

**Flutterwave went fourth ("proceed"), but only partially -- scoped down to "OPay only" after reading through its actual shape surfaced real complexity none of the first three gateways had.** Unlike Monnify/Paystack/Squad, Flutterwave is really three separate checkout flows sharing one class, not one: card (the v3 hosted `/payments` endpoint, its own Secret Key credential, already dispatched around the normal checkout path entirely by `PortalController::pay()`'s `elseif ($paymentMethod === 'card')` branch), bank transfer (creates a virtual account number/bank name -- a response shape that doesn't fit `ChargeResult` at all, unlike every other gateway's plain checkout URl), and OPay (the v4 orchestration `/orchestration/direct-charges` endpoint, the only one of the three whose result is a checkout URL and therefore the only one that actually fits `HostedGateway`). Asked the user how to scope it given this; the answer was "OPay only" -- migrate just that flow, leave card/bank-transfer/`banks()`/`resolveAccount()` on the existing `FlutterwaveService`/`PlatformFlutterwaveService` classes untouched. `App\Services\Payments\Gateways\FlutterwaveGateway` is the new OPay-only implementation, used only by tenant hotspot checkout (`HotspotHostedCheckoutManager::startFlutterwaveOpay()`, a narrow named method mirroring `startFlutterwaveOpay`'s webhook-entry-point siblings rather than going through `supports()`/`start()`, since Flutterwave was never in that gateway list to begin with -- card and bank transfer still need the controller to pick between them before any manager call happens). `ChargeRequest` grew four new optional fields (`customerPhone`/`addressCity`/`addressState`/`addressLine1`) purely for Flutterwave's v4 `customer.phone`/`customer.address` block, which none of the first three gateways need or read.

Flutterwave's credential storage turned out to be structurally different too, caught by reading `Shop.php` before writing `GatewayCredentialResolver`'s new branch: Monnify/Paystack/Squad's settings all live in one generic `Tenant::payment_gateway_settings` JSON blob, but Flutterwave's four credentials (`flutterwave_client_id`/`client_secret`/`secret_key`/`webhook_secret`) are four dedicated encrypted columns directly on `Shop` -- a pre-existing asymmetry from before this consolidation started, not something introduced by it. `GatewayCredentialResolver::forPayment()` normalizes this into the same `GatewayCredentials` shape with a Flutterwave-specific branch rather than teaching every caller about the difference.

Platform billing's own non-card Flutterwave flow turned out **not** to be a fit for the same "OPay only" migration, confirmed by a live test failure the moment it was tried: unlike the hotspot portal (where a customer explicitly picks one of three fixed checkout methods), `PlatformHostedCheckoutManager`'s non-card Flutterwave path sends whatever v4 `payment_method.type` `PlatformPaymentSettingsService::defaultPaymentMethod()` is currently configured to -- `opay` **or** `bank_transfer`, both through the same orchestration endpoint, a dynamic choice `FlutterwaveGateway`'s hardcoded `'opay'` type deliberately doesn't support. `test_platform_checkout_uses_database_payment_settings_before_env` (which sets `default_payment_method` to `bank_transfer` and asserts the request sent `payment_method.type === 'bank_transfer'`) caught this immediately when the platform side was first pointed at the new gateway class, so that half of the change was reverted -- `PlatformHostedCheckoutManager`/`PlatformBillingConfirmationService`/`PlatformFlutterwaveService` all stay completely untouched by this migration, unlike Monnify/Paystack/Squad where both tenant and platform sides moved together. Only `FlutterwaveService` (tenant) lost its now-redundant `initializeCheckout()`; everything else on both original classes -- `verifyPayment`, `webhookIsValid`, `createStandardHostedCheckout`, `createDynamicVirtualAccount`, `banks`/`resolveAccount`, all credential-source helpers -- is unchanged, and `HotspotPaymentConfirmationService::verifyProviderPayment()`'s Flutterwave branch now splits on `flutterwave_checkout_version === 'standard_v3'` (card, stays on the old service) vs. else (OPay, the new `FlutterwaveGateway`) to match.

Restructuring `PortalController::pay()`'s dispatch chain surfaced one more thing worth remembering: the original code gated *all* of card/bank-transfer/OPay behind one outer `elseif ($flutterwave->isConfiguredFor($payment))` check, so an incomplete credential set (e.g. a client ID saved with no client secret) always fell through to the generic "missing_credentials" message set at the top of the method, regardless of which sub-flow the customer picked. The first draft of the new `elseif ($paymentMethod === 'opay')` branch called `startFlutterwaveOpay()` unconditionally, which does its own narrower `client_id`+`client_secret` check and returns a different reason (`missing_gateway_secret_key`) on failure -- a real regression, caught by `test_incomplete_tenant_flutterwave_credentials_do_not_use_platform_account_for_customer_payments` expecting the original generic message. Fixed by gating the new branch on `$paymentMethod === 'opay' && $flutterwave->isConfiguredFor($payment)`, matching the original chain's semantics exactly rather than trusting the new method's own internal check to produce the same UX.

**Stripe completed the set the same day ("proceed")** — the fifth and last gateway, expected up front (alongside Flutterwave) to be one of the two hardest, since Checkout Sessions looked like a meaningfully different shape from every other gateway's plain "initiate, get a redirect URL back" flow. In practice it fit `HostedGateway`/`ChargeRequest`/`ChargeResult` cleanly with only two small additions to the shared DTO: `ChargeRequest::$cancelUrl` (Stripe is the only gateway that needs a `cancel_url` distinct from the success redirect -- every other gateway has just one redirect URL) and `ChargeRequest::$productName` (a bare product name distinct from the longer `description` line-item field the other four gateways already read, since Stripe's `product_data` wants both separately). Both are optional, default to `''`, and are silently ignored by Monnify/Paystack/Squad/Flutterwave, the same "opt-in extra field" pattern Flutterwave's own migration already established for `customerPhone`/`address*`. `App\Services\Payments\Gateways\StripeGateway` replaces `StripeService`/`PlatformStripeService`, both deleted outright — unlike Flutterwave, nothing else in the codebase depended on either beyond checkout, so there was no reason to keep a stripped remnant around. `App\Services\Payments\Verification\StripeVerificationMatcher` replaces both confirmation services' near-identical inline Stripe branches (`object === "checkout.session"`, `payment_status`, `client_reference_id`/`metadata.payment_reference`, `amount_total` in cents).

Because Stripe is a full migration (both tenant and platform sides move together, unlike Flutterwave's platform-side revert), `PlatformHostedCheckoutManager`'s old `gatewayFor()` dispatch — which used to pick between `PlatformFlutterwaveService`/`PlatformStripeService` — collapsed to nothing: only Flutterwave still reaches that fallback path at all now, so the method was deleted and its one remaining call site (`start()`'s non-shared-gateway branch) calls `$this->flutterwave` directly. `HotspotHostedCheckoutManager` similarly dropped its last direct `StripeService` dependency, and both managers gained a `stripeWebhookIsValid()`/explicit `STRIPE` webhook branch matching the pattern already established for Monnify/Paystack/Squad. All 99 tests in `HotspotPortalTest`/`PlatformBillingTest` passed on the very first run with no regressions -- a contrast with Flutterwave's migration, which needed two live-test-driven corrections along the way. With this, all five gateways (Monnify, Paystack, Squad, Flutterwave-OPay, Stripe) now share the same `HostedGateway` contract; the only carve-outs left are Flutterwave's card/bank-transfer/`banks()`/`resolveAccount()` methods (tenant `FlutterwaveService`) and its entire non-card platform-billing flow (`PlatformFlutterwaveService`), both documented above as deliberate, not oversights.

`PlatformPaymentSettingsCard`/its blade were rewritten to the same generic `gateway_settings.{field}` + `credentialFields()` loop `PaymentSettingsCard` already uses for tenants (the exact pattern whose absence caused the original "why does Monnify show Flutterwave fields" report) — each gateway now shows its own real fields, correctly labeled, and a single "Clear all saved {gateway} platform credentials" checkbox replaces the old two hardcoded ones (deliberately coarser than the tenant card's per-field clear checkboxes, since platform credentials are reconfigured rarely enough that clearing everything at once and re-entering is simpler than replicating field-level granularity for an arbitrary per-gateway field set). `PaymentGatewayCatalog::platformReadiness($gateway)` is the platform-side mirror of `tenantReadiness(Shop $shop)`'s generic per-field-badge rendering, applied uniformly to every platform gateway (including Flutterwave, which used to get a bespoke 2-channel "OPay/transfer + Webhook" shape) rather than special-casing Flutterwave's old field layout.

The hotspot captive portal's own "Pay with" picker (`resources/views/hotspot/portal.blade.php`, unrelated to platform billing above — this is the tenant/customer-facing Flutterwave method picker) switched from a 5-button radio grid to a plain `<select>` dropdown the same day, per direct request once USSD/NQR brought the option count to five and the button grid started wrapping awkwardly on the portal's narrow mobile-first layout.

All four online gateways (Squad, Monnify, Paystack, Stripe) carry an `environment` field in `PaymentGatewayCatalog`'s `select_fields` (`live`/`test`, defaulting to `test`) — a per-gateway field that renders as a `flux:select` in `PaymentSettingsCard` instead of a free-text credential input, is excluded from `tenantReadiness()`'s badges (it's a preference, not a "missing credential"), and is validated with a strict `Rule::in()` in `PaymentSettingsService` on top of the generic `gateway_settings.*` wildcard rule. It is only *functional* for Squad and Monnify, which have genuinely different API base URLs per mode: `SquadService`/`MonnifyService::baseUrl()` take `Payment $payment` and pick `config('services.<gateway>.live_base_url')` or `.base_url` (sandbox) based on the shop's saved `environment` — there's no platform-wide `.env`-only base URL forcing every tenant onto the same environment anymore.

Paystack and Stripe share ONE API host regardless of mode — the secret key's `sk_test_`/`sk_live_` prefix is the only thing that actually determines live vs test, so their `environment` field does not change any base URL; it's saved purely for the admin's own reference (2026-08-06, added after a user request for a consistent field across all four gateways). Because an independently-editable field can drift out of sync with the actual key (pick "Live" while a `sk_test_` key is still saved), `PaymentGatewayCatalog::detectedEnvironment(?string $secretKey)` derives the real live/test state straight from the key prefix, and `PaymentSettingsCard` shows it as a read-only badge ("Detected: Live key" / "Detected: Test key" / "Environment not detected") next to the Secret Key field, plus an inline warning under the Environment dropdown when the two disagree. `PaymentSettingsCard::KEY_DETECTED_ENVIRONMENT_GATEWAYS` is the list of gateways this detection applies to (currently `paystack`, `stripe`) — add a gateway there only if it shares this one-URL-plus-key-prefix shape.

`App\Livewire\Admin\PaymentSettingsCard` is the single place gateway credentials/environment are edited (2026-08-06) — it used to be duplicated as hardcoded Flutterwave-only fields on the separate Shops CRUD (`App\Livewire\Admin\ShopsIndex`'s edit flyout and `Admin\ShopController`'s full-page form), which had no way to configure Squad/Monnify/Paystack/Stripe at all despite letting you pick them as the active gateway. Both Shop edit surfaces now embed `<livewire:admin.payment-settings-card>` directly (as a sibling section after the shop-details `<form>`, never nested inside it — Livewire's own `<form wire:submit="save">` inside another `<form>` is invalid HTML) once the shop exists; `App\Services\ShopManagementService` was stripped down to just `tenant_id`/`name`/`location_city`/`is_active` accordingly. A shop must be saved once before its payment settings can be configured.

**Tenant Wallet** (2026-09-23) is a premium, plan-gated alternative to a tenant configuring their own gateway account: instead of the shop's own Flutterwave/Paystack/etc credentials, customer payments route through the *platform's own* Flutterwave account (`PlatformPaymentSettingsService`, the same credential store the tenant-pays-platform billing side already used), and the tenant's cut accumulates as an in-app wallet balance they withdraw manually. Gating is plan-level, reusing the existing subscription machinery rather than inventing new billing concepts: `billing_plans.supports_wallet`/`wallet_commission_rate` mark a plan tier as wallet-capable, and `BillingPlanLimits::assertCanEnableWallet(User $user)` (same shape as `assertCanCreateShop/Router/Package`) throws unless the tenant has an active/trialing subscription to such a plan. `WalletService::enable(Tenant $tenant)` is the actual opt-in — it force-sets `tenants.wallet_enabled = true` plus `billing_model = 'commission'` and `commission_rate` from the plan's `wallet_commission_rate`, so a wallet-enabled tenant just *is* a commission-billing tenant under the hood and `App\Support\PaymentCommission::forShop()` needed zero changes for its existing (non-wallet) callers.

`billing_plans.supports_wallet`/`wallet_commission_rate` had a real gap between schema and UI, confirmed 2026-09-23 during a direct request for a super-admin "manage plan features" screen: `App\Services\BillingPlanManagementService::rules()`/`normalize()` already fully validated and persisted both fields, and an orphaned full-page form (`resources/views/admin/billing/plan-form.blade.php`, reached only via the `admin.billing.plans.create/edit/...` routes, which are otherwise unlinked from navigation today but still real and covered by `tests/Feature/PlatformBillingTest.php`) already exposed them too — but the actual **live, linked** super-admin plan UI, `App\Livewire\Admin\BillingPlansManager` embedded on `admin/billing`, never had the two fields wired up at all. A super admin using the page they'd actually navigate to had no way to toggle wallet support for a plan. Fixed by adding `supports_wallet`/`wallet_commission_rate` as component properties (loaded in `edit()`, included in `save()`'s validated payload, reset in `resetForm()`) and a matching "Tenant wallet" section in the modal, mirroring the orphaned form's own fields/copy exactly. The orphaned full-page form/routes were deliberately left alone rather than deleted, unlike this codebase's usual "delete the superseded parallel implementation" precedent (e.g. the router wizard's old full-page form) — it still has real, passing test coverage exercising it directly over HTTP, so removing it would mean also deciding what to do with those tests, a separate decision from the one actually asked for here.

Credential *source* (tenant-owned vs platform-owned) turned out to be entirely separate from gateway *type* selection in the existing code — `HotspotPaymentConfirmationService::verifyAndGrant()` dispatches purely on `Payment.provider`, never on where the credentials came from — so wallet mode only needed two touch points: `Shop::paymentGateway()` returns `PaymentGatewayCatalog::FLUTTERWAVE` unconditionally when `$this->tenant->wallet_enabled`, and `FlutterwaveService`'s own credential-lookup methods (`clientId()`/`clientSecret()`/`credentialSource()`/`webhookIsValid()`) each gained one branch (`usesWalletCredentials()`) that pulls from `PlatformPaymentSettingsService` instead of `$payment->shop` when the shop's tenant has wallet mode on. No other gateway service and no dispatch logic anywhere needed to change — wallet mode is Flutterwave-only by design, since the platform billing side already had proven platform-credentialed Flutterwave infrastructure (`PlatformFlutterwaveService`) to model from. One deliberate gap: `PlatformPaymentSettingsService` has no hosted-checkout (card) secret key equivalent, only the v4 orchestration API's `client_id`/`client_secret` — so `hostedCheckoutSecretKey()`/`hostedCheckoutCredentialSource()` return unconfigured for wallet-mode payments rather than risk falling back to a stale tenant-owned card key a shop may have saved before switching to wallet mode; only opay/transfer/virtual-account checkout works for wallet-mode payments in this first pass, not card.

The ledger is deliberately two lines per payment, not one net figure — modeled on how a Nigerian bank statement shows a credit and a separate charge rather than opaque netting, per direct user request. `wallet_transactions` is append-only (never updated in place): `WalletService::creditForPayment()` writes a `credit` row for the full amount actually charged to the customer, then (only when the fee is non-zero) a separate `debit` row for the platform's commission — `Wallet.balance` after both rows nets to the same figure a single combined credit would have produced, but the two-line trail stays visible in the tenant's transaction history. Who actually pays that commission is the tenant's own per-tenant choice, changeable any time from the wallet page: `tenants.wallet_commission_bearer` (`tenant` default, or `customer`) is read by `PaymentCommission::forWalletCheckout(Shop $shop, float $packagePrice)` (left alongside the untouched, still-used-by-everyone-else `forShop()`) — `tenant` mode charges the customer exactly the listed package price and nets the wallet price-minus-commission; `customer` mode charges the customer package-price-plus-commission on top and nets the wallet the full listed price either way. `PortalController::pay()` calls `forWalletCheckout()` instead of `forShop()` only on the wallet-mode branch, and uses its `charged_amount` (a key `forShop()`'s snapshot has no equivalent of) as `Payment.amount` — i.e. what's actually sent to Flutterwave as the checkout total — so every non-wallet tenant's checkout amount is completely unaffected.

Withdrawals are manual/admin-fulfilled only in this pass — no payout API integration. `WalletWithdrawalService::request()` debits the wallet balance *immediately* at request time (not at final payout), specifically so two concurrent withdrawal requests can't both pass a sufficient-balance check and overdraw the wallet; `reject()` reverses that reservation (credits back, ledger row), and `markPaid()` makes no further balance change since the funds were already set aside — it's purely a status transition recording that a super admin has already sent the money outside the app. The tenant-facing page (`admin/wallet`, `App\Livewire\Admin\WalletIndex`) shows the enable-CTA-or-upgrade-message, balance, the commission-bearer choice, a withdrawal request form, and transaction/withdrawal history; the super-admin-only queue (`admin/wallet-withdrawals`, `App\Livewire\Admin\WalletWithdrawalsIndex`, gated the same `abort_unless($request->user()->isSuperAdmin(), 403)` way as `TenantController`/`SecurityController`) approves/rejects/marks paid across every tenant. Neither route has an entry in `App\Support\StaffPermissions::ROUTE_PERMISSIONS` — deliberately, matching the precedent that `admin.billing` itself isn't in that map either, so `tenant_staff` is denied by default with zero new permission-catalog entries needed. Wallet mode is tenant-wide, not per-shop, matching how `commission_rate`/`billing_model` already work tenant-wide — a tenant with multiple shops gets it for all of them at once.

**Monnify checkout's redirect URL was malformed, confirmed live 2026-09-25** from the first-ever full round-trip live Monnify payment (via wallet mode, immediately after the walled-garden fix above): the hotspot callback page showed "We could not match this payment return," with the transaction reference literally reading `HSF-...-VVJ93XRB?paymentReference=HSF-...-VVJ93XRB` — a doubled, malformed query string, not two separate values. Root cause: `HotspotHostedCheckoutManager::callbackUrl()`'s Monnify case pre-embedded `?paymentReference={tx_ref}` into the `redirectUrl` sent to Monnify's init-transaction call, but Monnify's own redirect behavior *also* appends `?paymentReference=...&paymentStatus=...` to whatever `redirectUrl` it's given, using a plain `?` rather than checking for an existing query string first — producing `...?paymentReference=X?paymentReference=X`, which PHP's query parser reads as one `paymentReference` key whose *value* is `"X?paymentReference=X"` (there's no `&` to split it into two params). Fixed by no longer pre-embedding anything for Monnify — `PortalController::callback()`'s tx_ref extraction already checked `paymentReference` as a fallback, so Monnify's own appended value alone is sufficient. The exact same pattern existed in `BillingController::checkout()` (platform billing, tenant-pays-platform) — never yet exercised through a real Monnify round trip, so undiscovered until this investigation surfaced it by inspection — fixed the same way, plus two related gaps in `BillingController::callback()` found in the same pass: its tx_ref extraction never checked `paymentReference` at all (only `tx_ref`/`reference`), and its early-exit "was this successful" gate only excluded Stripe from checking a plain `status` query param, which Monnify's redirect never sends (it sends `paymentStatus`, and this codebase deliberately doesn't trust that unverified redirect signal anyway) — meaning a Monnify platform-billing return would have been rejected as "not successful" before ever reaching real API verification, exactly mirroring the exclusion `PortalController::callback()`'s hotspot-side equivalent already correctly applies to Monnify/Paystack/Squad/Stripe alike.

**POS payment tracking** (2026-09-23) closes a gap `docs/current-project-status.md` had listed as planned-but-unbuilt: POS device registration/renewal used to be entirely free with zero `Payment` trail, unlike hotspot/PPPoE. **The same day, Staff/Management Wi-Fi trusted devices asked for the identical treatment** — a registered `TrustedWifiDevice` whose access expired hit the exact same generic portal for the exact same reason (`mms-staff-profile`/`mms-mgmt-profile` are MAC-auth-only too, with no `html-directory=` of their own). **That deferred effort was built the same week ("that would be better"), closing the gap for POS, Staff, and Management all at once.** `mms-pos-profile`/`mms-staff-profile`/`mms-mgmt-profile` each now get their own `html-directory=` (`flash/pos`/`flash/staff`/`flash/mgmt`, fixed names -- no admin-facing override needed the way `DEFAULT_HOTSPOT_DIRECTORY` needs one, since these three objects are always app-created, never a router-specific manual setup) in every place that creates them: `generatePosScript()`, `generateStaffScript()`, `generateFreshInfrastructureScript()`'s POS section, and the live-API `provisionPos()`/`applyMacAuthHotspotServer()` (the latter shared between Staff and Management, so it took one new `$htmlDirectory` parameter instead of two separate near-duplicate methods).

The actual mechanism, mirroring `hotspotLoginPageHtml()`/`pushHotspotLoginPage()` exactly rather than inventing a parallel system: `MikroTikProvisioningService::hotspotLoginPageHtml()` and `loginPageUrl()` both gained an optional `$network` parameter (`'pos'|'staff'|'mgmt'`, omitted entirely for the customer hotspot's own stub, which stays byte-identical to before). When set, the generated stub bakes an extra `&network={$network}` onto its own JS-built redirect target, and the URL the router fetches the stub *from* becomes `.../hotspot/login-page?network={$network}` -- one shared route (`PortalController::loginPage()`, now reading `$request->query('network')` and validating it against an allow-list) rather than three near-duplicate routes/controller methods. `RouterOsConnectionService::pushNetworkLoginPage(Router $router, string $network)` is the live-API sibling of `pushHotspotLoginPage()`, wired into `provisionPos()` and `provisionStaffWifi()` (both Staff and Management branches) the same way the customer hotspot's own push is wired into `provisionHotspot()` -- an admin who only pastes the generated script by hand still gets a correctly-directoried profile, just without the automatic fetch; the existing manual-copy fallback documented for the customer hotspot applies here too.

`PortalController::show()` now branches on the `network` query param *before* the legacy fallback chain: `network=pos` looks up a `PosDevice` and always renders `hotspot.pos-status` (with `device: null` for an unmatched MAC, a new third branch in that view -- "Not allowed on this network" / "not registered for POS access" -- instead of falling through to the generic portal); `network=staff`/`mgmt` does the identical thing against `TrustedWifiDevice` via `hotspot.staff-wifi-status`, now taking an explicit `$networkLabel` parameter (`'Staff'`/`'Management'`) rather than deriving it from `$device->network`, since there's no device row to read that from in the "not allowed" case. This is definitive, unlike the old MAC-lookup-only heuristic: since only these three networks' stubs ever send `network=`, an unrecognized MAC arriving *with* that param is unambiguously "wrong network," not "possibly a new hotspot customer." Requests with no `network` param at all (a router not yet re-provisioned with the new per-network stubs) fall through to the exact same legacy chain as before -- Subscription → PosDevice → TrustedWifiDevice → generic portal -- so this is purely additive; no router needs to be re-provisioned before continuing to work exactly as it did previously, it just doesn't get the sharper "not allowed" message until it is.

**Testing the above on a real L009 board (2026-09-26/27) surfaced a genuine RouterOS gotcha, unrelated to any app code**: after re-provisioning, "MMS Staff" started rejecting a password confirmed correct on the router itself (`/interface wifi security print` showed the right passphrase), while "MMS POS" and "MMS Mgmt" -- provisioned the exact same way -- worked fine. Diagnosis (the long way, since the symptom actively misled toward a config/password bug): `/interface bridge port print` showed `wifi-staff`'s port permanently `I` (inactive) and `/interface wifi registration-table print` showed it had *never* had a single client associate, even though its wifi security/configuration objects looked identical in shape to POS/Mgmt's. This turned out not to be a VLAN/bridge-vlan-untagged issue either (despite matching that exact symptom shape) -- `/interface wifi remove wifi-staff` + re-add got a client to associate for the first time, proving the interface itself had simply never come up correctly since its original creation (this board's known pattern of a virtual Wi-Fi interface needing an explicit kick to actually activate, same family as the "factory-default wireless interface stays administratively disabled" issue already documented for `StandalonePtpScriptGenerator` above -- confirmed here to also apply to `/interface wifi add`-created virtual/slave interfaces, not just the physical master radio).

That remove/re-add traded one bug for another, though: the client now associated but cycled connect→disconnect every ~15-20s (a DHCP-timeout-shaped symptom). Root cause: RouterOS's `/interface bridge port` entries bind to an interface's **internal ID**, not its name -- deleting `wifi-staff` orphaned the existing bridge port row (which still displayed a stale, no-longer-resolvable ID, e.g. `interface=*15`, instead of the interface name every other row showed), and creating a new `wifi-staff` object with the same name did **not** reattach it. The new interface was never actually a bridge member at all until a fresh `/interface bridge port add bridge=bridge-lan interface=wifi-staff pvid=30 ...` was run by hand -- confirmed live this was the final missing piece, after which the connection stopped cycling. **Worth remembering for next time**: if a virtual Wi-Fi (or any) interface ever needs to be removed and recreated as a troubleshooting step, its bridge port membership does not survive that and must be explicitly re-added afterward -- this is a RouterOS behavior this codebase's own script generator never has to handle (it only ever creates each object once, in the right order, on a router that's never had it before), so it only bites during manual live troubleshooting like this, not during normal provisioning.

The registration/renewal form's "Expires at" field (2026-09-24, direct request) used to be a blank input an admin either left empty — silently falling back to `PosDeviceManagementService::normalize()`'s `starts_at + package's limit_uptime_seconds` default — or filled in by hand-calculating the date themselves; the "leave blank to calculate" behavior existed but wasn't visible or automatic. `App\Livewire\Admin\PosDevicesIndex::updatedPackageId()`/`updatedStartsAt()` (both fields switched to `wire:model.live` for this) now reactively fill "Expires at" with that same starts_at-plus-uptime calculation the moment a package is picked or the start date changes, still a plain editable input afterward for a device that genuinely needs a custom expiry.

### Packages and RADIUS attribute mapping

Packages carry bandwidth, uptime, and optional data caps/FUP. When synced to RADIUS: `Mikrotik-Rate-Limit` = bandwidth, `Session-Timeout` = uptime (seconds), `Mikrotik-Total-Limit`/`Mikrotik-Total-Limit-Gigawords` = data quota. Data values are stored/compared in raw bytes (see unit table in `docs/roles-and-product-direction.md`). `NAS-Identifier` on the router must exactly match the router's stored identity — mismatches are the most common "router not registered" support issue.

### Expiry/cleanup model

Hotspot subscriptions, PPPoE subscribers, and POS devices are each revoked from RADIUS by a scheduled command (see Commands section) rather than by a live TTL in FreeRADIUS — the `Schedule::command(...)->everyFiveMinutes()` jobs in `routes/console.php` are what actually cut off expired access. If a feature depends on "access should end at time X," it needs a corresponding scheduled sync, not just an `expires_at` column.

### Free trial (customer promotion) vs "Start test access" (staff debugging) — two deliberately separate features

`shops.allow_test_access` (existing) shows a "Start test access" button inside every package's own expanded detail on the captive portal — pick a package, get its exact duration and bandwidth for free. No daily cap, no separate throttle: it's a staff/admin convenience for verifying a router/package actually works end-to-end, not something meant for a real customer. **`shops.trial_enabled`** (2026-09-27, direct request) is a second, genuinely independent feature: an admin-configured **customer-facing promotion** — a standalone "Free trial" option, decoupled from any specific package, with its own `trial_duration_minutes`/`trial_max_uses_per_day`/`trial_speed_limit_profile` and a real per-device daily cap. The two coexist (a shop can have either, both, or neither) and were kept deliberately un-conflated end to end: separate toggles in the admin form, separate route (`hotspot.trial.start` vs `hotspot.grant`), separate controller method (`PortalController::startTrial()` vs `grant()`), and a separate portal UI item positioned last, after every package.

The free trial reuses `RadiusProvisioningService::grantSubscriptionAccess()` — the exact same RADIUS path every paid package already uses — rather than inventing a parallel package-less provisioning mechanism, since that method (via `syncPackageProfile()`) needs a real `Package` row to read `Mikrotik-Rate-Limit`/`Session-Timeout` from and to derive a RADIUS group. `Shop::ensureTrialPackage()` auto-creates one hidden `Package` per shop (`is_active=false`, so it never appears in the customer-facing package grid, which already filters `is_active` everywhere) and keeps it in sync with the shop's current trial settings on every single call — an admin's settings change takes effect on the very next trial grant, no separate push/sync step needed. This hidden package also needed a **second** exclusion: `is_active=false` alone doesn't keep it out of the admin's own Packages management screen, which deliberately lists inactive packages too (that's the point of a management view) — so `packages.is_system` (new column, default `false`) marks it explicitly, and `PackagesIndex`'s listing/summary queries exclude `is_system=true` rather than matching on the fragile package name string "Free Trial".

Per-device daily-use counting needed its own append-only `trial_redemptions` table (`shop_id`, `mac_address`, `created_at`) rather than counting `Subscription` rows directly — `PortalController::grant()`/`startTrial()` both `Subscription::updateOrCreate()` keyed on `['shop_id','mac_address']`, so a second same-day trial grant would silently overwrite the first row rather than leaving a countable history. `Shop::trialUsesRemainingToday(string $mac)` counts `trial_redemptions` for that shop+MAC within the current calendar day (`whereDate('created_at', today())`) and subtracts from `trial_max_uses_per_day`; `PortalController::startTrial()` checks this before granting and throws a `ValidationException` (keyed `trial`, redirecting back to the portal with the error flashed) once exhausted, rather than silently no-opping.

A genuinely close call caught before shipping: the first draft gave the free trial its own distinct RADIUS password constant (`FREE_TRIAL_PASSWORD`), reasoning that a radcheck row's password value would then tell you which flow granted a device access. This would have been a real, live bug — `PortalController::show()`'s "you already have an active subscription" re-display branch hardcodes `self::TEST_ACCESS_PASSWORD` as the password it resubmits to MikroTik's login endpoint, **regardless of which flow originally granted access** (every one of paid checkout, voucher redemption, and the debug button already converges on this one shared literal value, confirmed by grep across `HotspotPaymentConfirmationService`/`VoucherManagementService` — each just re-declares its own private constant with the identical string). A device that got its RADIUS row from a different password value would have had its mid-trial re-visit's auto-submitted login rejected by RADIUS as a password mismatch. Fixed by having the free trial reuse the exact same shared constant instead of inventing a second one — worth remembering the next time a new grant flow is added here: this password is a single, deliberately-shared invariant across every grant path, not something to fork per feature.

The portal's package/voucher cards were converted from a hand-rolled Alpine `x-data="{ selectedPlan: null }"` single-open mechanism to Flux Pro's real `<flux:accordion>` component in the same pass (direct request: "make the voucher card collapsible and only one card should be open at a time") — confirmed by reading the compiled `vendor/livewire/flux-pro/dist/flux.js` directly rather than assuming: `<ui-disclosure-group>` (the `<flux:accordion>` wrapper) only enforces mutual exclusivity when it carries an `exclusive` attribute (`UIDisclosureGroup.boot()` checks `this.hasAttribute("exclusive")` and force-closes sibling `<ui-disclosure>` elements on a `lofi-disclosable-change` event only in that mode) — it is **not** the default, unlike what the admin dashboard's own accordion (shipped just before this, several sections legitimately expanded at once) might suggest. `<flux:accordion exclusive transition>` is the one place in this codebase that needs it. Every item's `heading=""` is passed as a plain string prop (not a manually-composed slot), deliberately — `item.blade.php` echoes a string `heading` through `{{ }}` (HTML-escaped, correct for plain text) but echoes the child `{{ $slot }}` unescaped (a `ComponentSlot` implements `Htmlable`, which Blade's `{{ }}`/`e()` special-cases to skip escaping) — mixing rich HTML into the `heading` prop itself would have been silently double-escaped. Converting to a collapsible-by-default layout surfaced one small regression risk fixed in the same pass: both the pre-existing voucher-redeem error (`@error('voucher_code')`) and the new trial daily-limit error (`@error('trial')`) now need `:expanded="$errors->has(...)"` on their own accordion item, or a validation error redirected back to the page would render inside a collapsed, invisible card.

**None of the accordion items actually opened on click, confirmed live 2026-09-27 immediately after shipping**: the admin layout (`components/layouts/admin.blade.php`) emits `@fluxScripts` right before `</body>`, which is what actually prints the `<script>` tag loading Flux Pro's compiled JS bundle (`flux.js`, the file that defines the `<ui-disclosure>`/`<ui-disclosure-group>` custom elements this whole accordion mechanism depends on) — `resources/views/hotspot/portal.blade.php` is a standalone Blade view that never extends that layout (it's the customer-facing captive portal, deliberately its own fixed dark-brand document per the Dark Mode section above), so it never had this directive at all. Alpine itself was never the problem (it's bootstrapped separately via `resources/js/app.js`, already proven working by this same page's pre-existing spinner/`x-data` states) — without `flux.js`, the accordion's heading `<button>` elements simply had no click behavior wired up, and nothing had an `open` state to react to regardless of any `:expanded` prop. Fixed by adding `@fluxScripts` to `portal.blade.php` right before `</body>`, matching the admin layout's own placement. The voucher card (the first item) also switched from a conditional `:expanded="$errors->has('voucher_code')"` to a bare `expanded` — always open by default, per direct request — which subsumes the error-visibility case for free, since an always-open card can never hide a validation error inside a collapsed body.

**A round of portal polish the same day** (direct request, four items): (1) the accordion's outer container had `px-3 sm:px-5` (horizontal only, no vertical padding at all) — combined with Flux's own `accordion.item` classes deliberately zeroing the first item's top padding and the last item's bottom padding (`pt-4 first:pt-0 pb-4 last:pb-0`, meant for a container that already supplies its own vertical padding), the very top of "Have a voucher?" and the very bottom of "Free trial" sat flush against the card edges with zero breathing room. Fixed by `npm install @alpinejs/collapse` and registering it in `resources/js/app.js` (`Alpine.plugin(collapse)`, before `Alpine.start()`) — this benefits the admin dashboard's own accordion too, since it shares the same missing-plugin gap and was never actually animating either. (3) The voucher card's own copy was cut down to a single short line ("Enter your voucher code.") from a longer explanatory sentence, per direct request. (4) A "Don't have a code? Call {number} to get one." `tel:` link was added inside the voucher card, initially reusing `Tenant::contact_phone` directly (a field that already existed and was already editable via the tenant's own Brand settings and the super-admin Tenants screen, already used identically on the tenant's own public site). **Corrected the same day**, direct follow-up: a tenant with several shops may staff each one with a different attendant, so a single tenant-wide number isn't always right. Added `shops.contact_phone` (nullable) and `Shop::contactPhone()` (`$this->contact_phone ?: $this->tenant?->contact_phone`) — a shop-level override that falls back to the tenant's own number when unset, editable on both shop edit surfaces right alongside the existing City field. **"Powered by HotspotFreeRAD" in the portal footer is no longer a hardcoded string** — `PortalController::show()` now passes `config('app.name')` through as `poweredByText`, so it already tracks whatever `APP_NAME` is set to in `.env` (`HotspotFreeRAD` on this install) with zero new settings surface. A first pass built a whole dedicated super-admin-only settings page for this (a `PlatformSetting`-backed service, a Livewire component, a new `admin/platform-branding` route, a sidebar entry) before a direct follow-up ("the powered by can just be the .env application name") replaced all of it with this one-line config read — worth remembering as a small instance of this file's own recurring lesson: check for an existing, simpler mechanism (here, a config value literally every Laravel app already has) before building new settings infrastructure for something that doesn't need its own database-backed toggle.

### Dark mode

The admin panel (`resources/views/components/layouts/admin.blade.php`) has a manual Light/Dark/System toggle using Flux's built-in `@fluxAppearance` directive/dropdown pattern (`$flux.appearance`, `x-on:click="$flux.appearance = '...'"` in the header) — `@fluxAppearance` already handled `.dark` class toggling, localStorage persistence, system-preference following, and flash-of-wrong-theme prevention before this work; it just had zero `dark:` classes anywhere to make any of that visible. Auth pages (login, forgot-password, reset-password, two-factor-challenge, force-password-change), `welcome.blade.php`, and `tenants/public-site.blade.php` follow system preference only, via the same directive with no toggle UI rendered — these are quick/standalone documents where a visible toggle isn't worth the UI real estate. The customer-facing hotspot captive portal (`resources/views/hotspot/*.blade.php`) is deliberately excluded entirely — it's already a fixed `bg-zinc-950 text-white` dark brand aesthetic, not a light-mode page needing a dark counterpart.

Elevation hierarchy used throughout: body (darkest, `dark:bg-zinc-950`) → card/sidebar/header panels (`dark:bg-zinc-900`) → subtle backgrounds/hover/badge surfaces (`dark:bg-zinc-800`) → borders (`dark:border-zinc-700`, or `dark:border-zinc-800` for very subtle dividers). Separately, several UI patterns use `zinc-950` as a light-on-dark **accent** (selected cards, active tabs, primary CTA buttons, progress-bar fills, file-input buttons, avatar chips) rather than a body/surface tone — these need **inversion** (`dark:bg-zinc-100 dark:text-zinc-900` or similar) instead of the elevation rule, since a near-black accent against an already-near-black dark body has poor contrast. When adding new UI, classify which bucket a `zinc-950`/`bg-white`/`bg-zinc-100` token falls into before picking its `dark:` pair rather than applying the elevation rule uniformly.

### Collapsible filter overlay (2026-09-28)

The 14 admin index pages that share the "search + selects + Reset" filter-bar shape (`clearFilters()` convention: Shops, Routers, Packages, POS Devices, PPPoE Subscribers, Payments, Subscriptions, Trusted Wi-Fi Devices, Tenants, Users, Vouchers, Expenses, Expense Categories, Security Activity) had that filter bar always on-screen, sometimes taking up nearly half the viewport on mobile — direct request to collapse it behind an icon, auto-close on apply, and surface active filters as removable chips instead. `resources/views/components/admin/filter-bar.blade.php` is the one shared component: a "Filters" button (funnel icon, badge showing the active count) opens a `<flux:modal>` containing the actual fields (unchanged markup, just relocated into the component's slot); picking a select option or a date auto-closes the modal via a plain `x-on:change="$flux.modal('{name}').close()"` on the fields wrapper (native `<select>`/`<input>` elements — confirmed by reading `flux/select/variants/default.blade.php` directly — so a real DOM `change` event bubbles up to it with no Livewire round-trip needed to close); the debounced free-text search field is deliberately excluded from that listener (closing on every keystroke would be unusable) and closes only naturally on blur like any other browser field. Regardless of whether the modal is open, every currently-active filter renders as a small pill outside it with its own value and an `x-mark` icon (`tooltip="Clear this filter"`, Flux's built-in tooltip support via any `tooltip=` prop) wired to `wire:click="$set('field', '')"` — so a filter's state is always visible at a glance without opening anything, matching the direct request that chips stay visible even though the fields themselves are hidden by default. A "Clear all" ghost button (calling the same `clearFilters()` every page already had) appears only once more than one filter is active. Each page computes its own `$xActiveFilters` array inline via a `@php` block in the view (mapping raw values to human labels, e.g. `status === 'online' ? 'Active/recent' : ...`) — no PHP/Livewire class changes anywhere, this is a pure view-layer reshuffle reusing each component's pre-existing public properties and `clearFilters()` method. Fields whose blank state doesn't mean "no filter" (date-range pairs already driven by a preset-button row above the filter bar, e.g. Payments'/Subscriptions' `from`/`to`) are deliberately left out of the active-filter count, since the preset row already shows that state and counting them would make the badge permanently non-zero.

**Converting `vouchers-index.blade.php` surfaced a genuine, previously-latent Blade compiler bug, unrelated to the feature itself.** The page failed with `syntax error, unexpected end of file` the moment the new `@php ... @endphp` block was added — tracked down (via `Illuminate\Support\Facades\Blade::compileString()` + `php -l` on the raw compiled output, then `token_get_all()` scanning for an anomalously long `T_INLINE_HTML` token to find where the parser actually went off the rails) to Blade's handling of the **inline** `@php(expr)` directive vs the **block** `@php ... @endphp` form: this file's pre-existing stat-card loop already had `@php($isActiveStat = ... deeply nested boolean expression ...)` on one line (present before this work, never a problem on its own), and Blade's directive matcher mis-detected where that inline call's argument list closes once a real multi-line `@php ... @endphp` block existed anywhere later in the *same* compiled file — it then swallowed everything between the two as unprocessed literal text (visible in the compiled output as one giant un-compiled `T_INLINE_HTML` chunk spanning from the stat-card loop through several `<flux:*>` component tags that never got compiled at all). Confirmed by isolating the new block into its own file (compiled cleanly alone) and bisecting the real file's "before"/"after" content around it (removing just the new block fixed the file; simplifying the *other* directive didn't, isolating it to the co-existence of the two `@php` forms specifically). Fixed by writing this file's new block with raw `<?php ... ?>` tags instead of `@php`/`@endphp` — bypassing Blade's directive matching for this block entirely, since raw PHP tags pass through Blade untouched. A second, subtler round of the same failure recurred immediately after that fix: the explanatory Blade **comment** (`{{-- ... --}}`) added directly above the fix, which mentioned the literal strings `@php`/`@endphp`/`@php(...)` in its prose, retriggered the identical mis-detection — Blade's directive-matching regex runs against the raw source text and isn't guaranteed to have stripped comment regions first. Fixed by rewording the comment to describe the directives without spelling out their `@`-prefixed literal names. Worth remembering for any future edit to this specific file (or any other file that ever gains its own inline `@php(...)` one-liner): a second real `@php...@endphp` block anywhere else in that same file is not safe to assume compiles independently, and literal directive-name text inside a Blade comment is not guaranteed to be inert either.

All 14 conversions were verified regression-free by running the full affected test surface (`AdminIndexFilterTest`, `AdminPosDeviceTest`, `AdminPppoeSubscriberTest`, `AdminSubscriptionIndexTest`, `AdminTrustedWifiDeviceTest`, `AdminPaymentIndexTest`, `AdminExpenseCategoryTest`, `AdminExpenseTest`, `AdminTenantManagementTest`, `AdminUserManagementTest`, `AdminVoucherTest`, `SecurityActivityReportTest`, `StaffPermissionAuthorizationTest`, `TenantScopeTest`) both with and without each changed view (via `git stash push -- <file>`) to separate real regressions from pre-existing failures. ### Wallet withdrawal fee + transaction/withdrawal filters (2026-09-28)

**A tenant could request a withdrawal for their entire wallet balance with nothing held back for the platform's own bank-transfer charges** — direct report: "there should be bank charges for every transaction... to prevent mystery the tenant should see the charges before proceeding." `WalletWithdrawalService::request()` already validated `amount <= wallet.balance` (confirmed correct, not itself a bug — a tenant could never literally overdraw under the old fee-less model), but there was no fee concept anywhere in the withdrawal lifecycle at all, so introducing one meant the *existing* balance check was exactly the gap: once a fee exists, the amount that actually needs to fit under the balance is `requested amount + fee`, not the requested amount alone.

New `App\Support\WalletWithdrawalFee::calculate(float $requestedAmount, array $setting): array` is the pure calculation helper (mirroring `PaymentCommission`'s static/array-returning style) — the requested amount is always the **net** figure the tenant wants paid into their bank account; the fee is computed on top (`'fixed'` — flat naira amount regardless of size — or `'percentage'` — scales with the requested amount, satisfying the "depending on the amount" ask) and returns `fee_amount`/`net_amount`/`gross_amount` (`net + fee`). New `App\Services\WalletWithdrawalFeeSettingsService` is the super-admin-configured setting backing it, following `PlatformPaymentSettingsService`'s exact `PlatformSetting`-row-per-key + `Cache::remember`/`Cache::forget` pattern (key `wallet.withdrawal_fee`) — plain unencrypted JSON, since a fee type/value pair isn't a credential. A new "Withdrawal fee" card on the super-admin `admin/wallet-withdrawals` queue page (already super-admin-gated) lets them pick fixed-vs-percentage and set the value.

`WalletWithdrawalService::request()` now validates `gross_amount <= wallet.balance` (not just the net amount) and, mirroring `WalletService::creditForPayment()`'s existing "two ledger lines, bank-statement style" idiom exactly, writes **two** debit lines when requesting — one for the net amount (unchanged wording), one for the fee (`'Withdrawal fee'`) — both tagged to the same `wallet_withdrawal_id`. `reject()` was updated to refund **both** lines (a tenant's rejected request must return the full amount that was actually reserved, fee included) rather than just the original `amount`. New `wallet_withdrawals.fee_amount` column (migration, decimal 12,2 default 0 — existing rows are unaffected/backward-compatible, they simply have no fee) plus `WalletWithdrawal::grossAmount()` (net + fee) for display. The withdrawal request modal shows a live-updating "You receive / Withdrawal fee / Total deducted from wallet" breakdown (computed in `render()` from the same `WalletWithdrawalFee::calculate()` helper the real charge uses, so the preview can never silently disagree with what actually happens) as the tenant types the amount, with an inline warning the moment the total would exceed their balance — directly closing the "should see the charges before proceeding" ask.

While building this, a **separate, pre-existing bug** was found and fixed in the same pass: `WalletWithdrawalService::request()`'s `ValidationException` used message key `'amount'`, but the Livewire property (and the view's `<flux:error name="withdrawAmount">`) is named `withdrawAmount` — the mismatched key meant a genuinely-rejected over-balance request never actually showed *any* error to the tenant (Livewire's exception-to-error-bag mapping still worked correctly key-for-key, it just landed under a key nothing in the view ever displayed), which is likely what the original "one can withdraw more than what they have" report was actually describing — the DB-level check was already correct, the failure was silently invisible. Fixed by using `'withdrawAmount'` as the key going forward.

**"Wallet transaction don't have filters"** — the Transaction History and Withdrawal Requests lists on `admin/wallet` had no filtering at all. Reused the same `<x-admin.filter-bar>` overlay component from the admin-index-pages rollout (see above) for both: Transaction History filters by type (credit/debit) + date range; Withdrawal Requests filters by status. Since a single page now has two independent filter groups needing two independent "Clear all" actions, `<x-admin.filter-bar>` gained a `clear-all` prop (default `'clearFilters'`, matching every other existing usage unchanged) so a caller can point it at its own clear method (`clearTransactionFilters()`/`clearWithdrawalFilters()`) instead of assuming one global method name. Withdrawal Requests also switched from an unpaginated `->get()` to `->paginate(10, pageName: 'withdrawalsPage')` (Livewire's `WithPagination` trait supports multiple independent paginators via distinct page names) to match Transaction History's existing pagination and stay usable once a tenant has more than a handful of requests.

### A hotspot customer could reach and log into the router itself, not just the captive portal (2026-09-28)

**Live report**: after connecting to the open customer hotspot Wi-Fi, a phone could discover and log into the router via mobile Winbox using its IP -- confirmed this should only ever be possible from the management network. Investigated and found the gap is real and specific: `apiServiceAddressRestriction()` (see the API-service story elsewhere in this file) has only ever restricted the RouterOS `api` service (port 8728, used only by this app's own automated calls) to the WireGuard/ZeroTier tunnel subnets -- `winbox`, `www`, `www-ssl`, and `ssh` were never restricted anywhere on the real tenant-router path, left at RouterOS's own defaults (`address=0.0.0.0/0`, reachable from every interface the firewall doesn't otherwise block). Compounding this: the hotspot VLAN's own firewall accept rule (`chain=input in-interface=vlan-hotspot protocol=tcp dst-port=80,443,...`, needed so hotspot clients can reach the login page RouterOS itself serves) opens exactly the ports `www`/`www-ssl` listen on -- so with those two services unrestricted, that same accept rule doubles as an open door straight to RouterOS's own WebFig admin interface. This is a different, IP-level gap from the earlier MAC-Telnet/Winbox-"Neighbors" Layer 2 bypass fix (`MGMT-ACCESS` interface list + `/tool mac-server` restriction, confirmed live 2026-09-20) -- that fix never touched `/ip service` at all, and a plain "type the IP, log in" Winbox/WebFig session doesn't go through MAC-Telnet in the first place. The one place in the codebase that *did* already restrict these four services correctly is `StandaloneHotspotScriptGenerator` (the unrelated standalone tool) -- it was simply never ported to the real `Router`-based provisioning path.

Fixed by adding `MikroTikProvisioningService::managementServiceAddressRestriction(Router $router, array $settings): string` (public, mirroring `apiServiceAddressRestriction()`'s exact shape and its "kept public so the live sync can reuse it" reasoning) -- unlike the API service (only ever reached over the tunnel by this app's own calls), a human admin needs to reach Winbox/WebFig/SSH directly, so this trusts the tunnel subnets *and* the router's own configured `mgmt_network`. `generateFreshInfrastructureScript()` emits `/ip service set winbox|www|www-ssl|ssh address=...` right after the existing `MGMT-ACCESS`/mac-server section (the natural continuation of the same "lock down admin access" concern), and `RouterOsConnectionService::syncManagementServiceRestriction()` mirrors `syncApiServiceRestriction()` exactly (list-then-diff across all four service names against one desired address list) so an already-provisioned router gets this pushed the moment a super admin clicks "Provision via API" -- the safe remediation channel here, since Fresh Infrastructure Script itself isn't safe to re-paste. Wired into `provisionHotspot()`/`provisionPppoe()` alongside the existing `syncApiServiceRestriction()` call. Not yet confirmed against real hardware that this fully closes the gap (in particular, whether `/ip/service/print` reliably has all four entries on every RouterOS version) -- matching this codebase's honesty pattern for other freshly-added restrictions elsewhere in this file.

### A hotspot customer had no idea their plan expired -- their phone just silently stopped passing traffic (2026-09-28)

**Live report**: once a hotspot package expires, the customer's phone stays connected to Wi-Fi with a working IP, but no data passes -- they have to manually disconnect and reconnect before the login/payment screen reappears, and until then it just looks like a bad network. Root cause: `hotspot:sync-expired-hotspot` only ever called `RadiusProvisioningService::revokeMacAccess()` -- a RADIUS-database-only operation. RouterOS's hotspot only consults RADIUS at login/session-renewal time, never on every packet, so revoking the `radcheck`/`radusergroup` rows does nothing to an *already-authenticated* session -- the device keeps its Wi-Fi association and DHCP lease exactly as before, and most phones don't spontaneously re-open their captive-portal login screen once they've already decided they have working internet (that check typically only fires once, right after first connecting).

Fixed with `RouterOsConnectionService::disconnectHotspotUser(Router $router, string $macAddress): array` -- looks up the device's `/ip/hotspot/active` entry (RouterOS's live table of authenticated hotspot sessions) and removes it, which is the actual mechanism that ends the session and makes RouterOS intercept the device's very next request with a fresh login page; it also removes the matching `/ip/dhcp-server/lease` entry as a second layer (forcing a clean DHCP renegotiation on reconnect, matching the live report's own suggested fix) -- but the active-session removal is what actually solves "customer has no idea they need to log in again," the lease alone would not have. A mac not currently active on a given router is a no-op, not a failure -- the common case, since most expiries happen well after a device already went idle on its own. `hotspot:sync-expired-hotspot` now groups expired subscriptions by `mac_address` (previously a flat `pluck()`, losing the `shop_id` needed to know which router(s) to check) and, after the existing RADIUS revocation, best-effort calls this for every router belonging to the mac's now-expired subscription's shop(s) -- an unreachable router is tolerated and reported honestly (the command's own summary line now reports both counts), never something that stops the RADIUS revocation itself or crashes the scheduled sync. Deliberately scoped to hotspot expiry only for now (matching the exact live report) -- POS uses the identical `/ip hotspot active` mechanism and could reuse this same method later, but that's a separate ask, not bundled in here. PPPoE is architecturally different (PPP sessions, not hotspot ones) and would need its own `/ppp active remove` equivalent, out of scope here too.

### Profile page overflow, round three -- a shared CSS Grid column, not the header (2026-09-28)

The header flex-wrap fix above resolved the first two overflow reports, but a third, more specific report followed: content strictly *inside* the profile form (the Account section's "Tenant Admin" badge, the avatar/"Choose file" area) was still bleeding past the visible edge on mobile, clipped by the admin layout's own `overflow-x-hidden` content wrapper -- and only on this one page. ### A customer on the free trial couldn't browse or buy a real package until the trial itself expired (2026-09-30)

**Direct report**: the whole point of the free trial is to let someone try the hotspot and then pick a package while they're already connected -- but once activated, the trial's 10-minute window locked the customer out of the package grid entirely, showing only the "Access provisioned" screen until the trial ran out. Root cause: `PortalController::show()`'s active-subscription check treats any `Subscription` row with a future `expires_at` identically, whether it came from a real paid package, a voucher, or the trial's own hidden `Shop::ensureTrialPackage()` package (`is_system=true`) -- so every portal reload during the trial hit the same `access-granted` short-circuit a real subscriber gets, with no way back to the packages. The fix only needed one distinction, not a new mechanism: `show()` now checks `$activeSubscription->package->is_system` and, when true, skips the `access-granted` redirect and falls through to render the normal portal instead (passing `activeTrialSubscription` to the view for a small banner -- "Free trial active — ends Xm ago/from now... pick a package below any time to continue seamlessly"). A genuinely real active subscription is unaffected -- there's nothing to upsell there, so it still shows `access-granted` exactly as before. Upgrading mid-trial needed no other plumbing at all: `Subscription::updateOrCreate()` is already keyed on `shop_id`+`mac_address` everywhere it's called (trial grant, paid checkout, voucher redemption, the debug test-access button), so buying a real package while the trial's row is still active just overwrites it in place -- the "seamless upgrade" was already there, the only gap was ever reaching the package list to trigger it.

**That fix alone wasn't enough, confirmed live the same day**: the customer never actually saw the package grid during the trial at all -- two distinct reasons, both real. First, `startTrial()`'s access-granted screen auto-submits its MikroTik login form 1.8s after rendering, and that form's `dst` field (the post-login redirect target) was still `$validated['link-orig']` -- wherever the customer had originally been trying to browse before the captive portal intercepted them (Google, Facebook, whatever). So the instant trial access was granted, MikroTik's own redirect whisked the browser straight off to that original destination, not back to the portal -- "it connects me automatically and closes the package page," exactly as reported. Fixed by pointing `dst` at our own portal URL instead (`MikroTikProvisioningService::portalUrl()`, the same host-resolution helper `loginPageUrl()` already uses rather than a naive `route()`/`APP_URL` call, so this stays correct if `HOTSPOT_PORTAL_URL` differs from `APP_URL`) -- only for the trial grant specifically, not `grant()`'s debug button or a real paid/voucher grant, both of which should still send a customer on to what they actually wanted to reach.

Second, and separately: toggling Wi-Fi off and back on still auto-connected with no portal page at all -- this turned out to be expected RouterOS behavior, not a bug in this app. Once a device is authenticated, RouterOS's own mac-cookie/cookie session recognizes it on reconnect and lets it straight through without ever redirecting the browser back through `/hotspot/portal` -- which is the normal, desired shape of a captive portal (nobody wants to re-login every time Wi-Fi blips), but it does mean the portal's own active-subscription branch (the fix above) is only reachable when the browser is actually sent back through it, which is exactly what the `dst` fix above now guarantees happens once, right after the trial itself is granted.

That "once" was the remaining gap, confirmed by a direct follow-up question -- a customer who navigates away from that first landing (taps a search result, switches apps) had no way back to the packages for the rest of the trial, since the portal URL needs `mac`/`nasid` query params nobody would know to type by hand. `hotspot/access-granted.blade.php` now shows a persistent "View packages" link, reusing the exact same `$originalUrl` the `dst` fix above already builds -- gated on `$package->is_system` rather than a separate flag, since that's already the one signal that distinguishes "this is the trial's hidden package" from a real paid/voucher grant (which has nothing to upsell, and whose own `$originalUrl` is genuinely the customer's destination, not the portal, so the link only ever appears where it's actually correct).

**The `dst` redirect itself turned out to never reliably reach a real phone, confirmed live 2026-09-30**: the observed flow was Connecting → "Access Provisioned" → a "You are connected" screen, with no package grid at any point -- and reconnecting reproduced it every time. Root cause was two-layered. First, `MikroTikProvisioningService::portalUrl()` falls back to `config('app.url')` when `HOTSPOT_PORTAL_URL` is unset, and the Pi's `.env` had this gap too (flagged as "not yet confirmed set" in `.local-notes/infra-settings.md`, the exact caveat that turned out to matter) -- with `APP_URL` pointing at a loopback/dev host, the `dst` value was simply unreachable from a phone on the hotspot network, and the OS's captive-portal checker just gave up and dropped the customer back wherever they'd been, indistinguishable from the original pre-fix bug. Fixing `HOTSPOT_PORTAL_URL` on the Pi closed that half, but a second, independent bug remained: the trial's login form (same shape every grant uses) POSTs with `popup=true`, which tells RouterOS to open its own post-login status window -- suspected (never actually confirmed) to be intercepting the flow with RouterOS's own stock "you are connected" page instead of ever following `dst` back to the portal.

Acting on that unconfirmed suspicion, the trial grant was given a completely different submission mechanism: POST the login into a hidden, named `<iframe>` instead of the main window, with no `popup`/`dst` fields at all, so the tab never navigates away and there's nothing for RouterOS's own status page to interrupt. **This made things worse, confirmed live 2026-10-02**: the page now showed "Free trial is ready," "You're connected," and the "View packages" link -- while the device genuinely had no internet at all. The "You're connected" text was never a real confirmation, just a fixed 2-second Alpine timer with zero awareness of whether the iframe's POST actually succeeded -- and a captive-portal mini-browser (iOS's Captive Network Assistant, Android's equivalent) is a known, heavily locked-down WebView that can silently refuse an iframe's *mixed-content* form submission (our HTTPS portal page posting to MikroTik's own plain-HTTP local login endpoint) with no visible error at all. `HOTSPOT_PORTAL_URL` was independently confirmed already correctly set on the Pi by this point, ruling out the first bug as a factor here -- this was purely the iframe mechanism itself failing silently.

Reverted to the exact same main-window `<form method="POST">` the paid/voucher/debug flows already use in production (proven to actually authenticate a device, unlike the unproven iframe) -- just with `dst` pointed at the portal (not the customer's original destination) and `popup` dropped entirely, since that field was only ever a suspicion, never confirmed, and removing it is strictly the smaller, safer change compared to inventing an entire second submission mechanism. No fake "connected" text either: the browser only ever reaches the portal (showing real packages) once MikroTik has actually processed the login and redirected it there, so landing on it is itself the only confirmation that matters. Paid/voucher/debug grants are completely untouched throughout all of this -- they still navigate the main window to `dst` = the customer's real destination, which is the correct UX there and was never reported broken. **Not yet confirmed whether dropping `popup` alone actually fixes the original RouterOS-status-page interception** -- that specific mechanism was never isolated/proven, only ruled out as *not* needing an iframe to work around; if the status-page interception recurs after this revert, it needs its own fresh live investigation rather than another guess.

### Customer self-service "scan to view packages" link (2026-10-02)

A live report confirmed the real-internet version worked, but still "closed the login page" and couldn't get back to packages, with the OS "usually show[ing] one default mikrotik login confirmation page before closing the view" -- this confirmed the root cause suspected two entries above: both iOS's Captive Network Assistant and Android's equivalent auto-close their own locked-down sign-in browser the instant real internet is confirmed, *regardless* of what page is showing. That's standard behavior on every captive portal (hotels, airports), not something any `dst`/redirect trick can out-race -- there is no server-side override for it. Direct request: build a QR code/link customers can use to view packages (or buy a voucher) from their own normal browser once connected, during or after the trial.

The one hard constraint shaping the whole design: **a device's own request IP is useless for identification here**, since every customer at a shop shares the router's one NATed WAN IP by the time a request reaches this app -- Laravel would see the same source IP for every device at that location, making IP-based lookup collide immediately. Built around a signed cookie instead: `PortalController::show()` (every normal captive-portal visit) now queues a `hotspot_device` cookie (`{shop_id, mac}`, Laravel's default per-cookie encryption, 90-day expiry) via `Cookie::queue()`. A new `GET /hotspot/go/{router->public_token}` route (`PortalController::connect()`) reads that cookie instead of mac/nasid query params, and -- if the shop_id matches this router's -- renders the exact same package/trial/voucher view `show()` would, now extracted into a shared private `renderForMac(Router $router, string $mac, ?string $network, ?string $loginUrl, ?string $originalUrl): View` both methods call (a pure refactor of show()'s existing branching logic, not a behavior change -- confirmed by the full pre-existing portal test suite passing unmodified). No cookie recognized (new browser/device, cleared cookies, or a cookie set at a *different* shop's hotspot) falls back to a plain "Connect to Wi-Fi first" page rather than guessing.

`routers.public_token` (new column, a random 22-char string, auto-generated in `Router::creating()` the same way the WireGuard keypair/API credentials already are, backfilled for existing routers in the migration itself) is what the link/QR actually encodes -- deliberately not `nas_identifier` (already semi-public via the captive-portal redirect, but no reason to make it trivially enumerable in a printed QR code) or the numeric id. `MikroTikProvisioningService::connectUrl(Router $router)` builds the link from the same base as `portalUrl()` -- but as a **plain string replace** of the trailing `/hotspot/portal` suffix, not `parse_url()`-ing it apart into scheme+host and reassembling the way `loginPageUrl()` does: a first version copied that exact pattern and silently dropped a non-default port (`parse_url(..., PHP_URL_HOST)` never includes one), caught immediately by a test against this local dev environment's `http://127.0.0.1:8000` `APP_URL` -- invisible against a real production domain on standard https, which is exactly the kind of gap this file has hit before when a fix is only ever checked against the "happy path" host. Deliberately does **not** reuse `loginPageUrl()`'s `hotspot_dns_name` fallback either -- that name only ever resolves via MikroTik's own local DNS interception for a still-unauthenticated device on this one router's network, never real public DNS, so it would be the wrong host for a link meant to be scanned or bookmarked from anywhere.

Surfaced in two places: the router's own admin page gets a new "Customer Self-Service Link" card (QR + copyable link, `window.copyText()`, the same pattern already used for 2FA/recovery codes) for a tenant to print and post at the physical location; the trial's own access-granted screen shows the identical QR/link right below the (still-kept, now best-effort) `dst`-based "View packages" redirect, so a customer who's paying attention in the few seconds before the OS closes the sign-in browser can save it before that happens. `App\Support\QrCodeSvg::render()` is a small extraction from `TwoFactorService::qrCodeSvg()` (which had zero 2FA-specific logic in its body) purely so this feature didn't have to reach into an unrelated-sounding service for a generic "string to QR SVG" utility -- `TwoFactorService::qrCodeSvg()` now delegates to it, unchanged behavior, confirmed by the existing 2FA test suite passing unmodified.

Deliberately out of scope here: whether buying a real package *while already on an active trial hotspot session* needs a fresh MikroTik login to pick up the new RADIUS group's rate-limit/timeout, or whether RouterOS applies it to the already-authenticated session without one (a CoA/`Disconnect-Message` question this app doesn't send today) -- that's a pre-existing architectural question for *any* mid-session package change, trial-driven or not, not something this link feature introduces or needs to solve to be useful.

**The self-service link grew a real "check your balance" use case, a working copy button, and print/download, the same day** (2026-10-02, direct feedback from laptop testing) -- three separate things. First: `renderForMac()`'s active-(non-trial-)subscription branch always rendered `access-granted.blade.php` with just a static expiry timestamp, assuming the visit was always "fresh grant, about to log in" -- but `connect()` reaching this exact branch (no `loginUrl` at all, since there's nothing left to log in to) is really "already connected, just checking in," and the view's own `@else` copy ("reopen a website...") was actively wrong for that case. New `App\Support\SubscriptionBalance::compute(Subscription $subscription)` computes real remaining time (plain subtraction) and real remaining data (`radacct` usage for this mac, `acctinputoctets + acctoutputoctets` summed -- the same convention `RadiusAccountingStats` already uses -- scoped to `acctstarttime >= starts_at` so a mac's *previous*, already-expired subscription's usage never bleeds into the current one's balance), passed into the SAME view and rendered as a "Your balance" section regardless of context; the `@else` branch gained its own `@elseif ($balance ?? null)` case with copy that's actually true for a connect()-reached visit.

Second, confirmed live: the admin page's "Copy link" button didn't copy anything. Root cause never fully pinned down (likely a non-secure-context `navigator.clipboard` rejection in whatever this was tested against) but fixed defensively either way -- the link now also sits in a plain readonly `<input>` the customer/admin can tap-and-select manually regardless of what the clipboard API does, and the copy button's handler now explicitly falls back to `$refs.connectUrlInput.select()` on any failure (`try`/`catch` around `window.copyText()`) instead of silently doing nothing.

Third: Print and Download buttons were added to the same card. Print uses the standard "hide everything, reveal one subtree, pull it to the page origin" CSS trick (`visibility: hidden` on `body *`, `visibility: visible` + `position: absolute` on the one target id) rather than a dedicated print route, since the target card is nested deep inside the admin layout's own wrappers, not a direct `<body>` child. Download rasterizes the server-rendered QR SVG to a PNG client-side (`window.downloadSvgAsPng()`, new in `app.js` -- draw an `Image` loaded from a `Blob` URL onto a `<canvas>` at a fixed upscale factor, then `canvas.toBlob()`) rather than adding a server-side PNG-rendering dependency just for this one button.

**Building the download button surfaced a real Blade/Livewire compiler bug, confirmed by reproducing and resolving it directly**: passing the QR SVG string through a Blade `@js()` call embedded inside a long, multi-line Alpine `@click` expression on a `<flux:button>` (a Blade *component* tag, not a plain HTML element) crashed the whole page with `preg_match(): Compilation failed: regular expression is too large`, thrown from Livewire's `SupportMorphAwareBladeCompilation` feature -- which scans compiled template source for Blade directives that appear *inside* an HTML tag's attributes (to handle them specially for DOM-morphing purposes) and apparently chokes when a `@js()` call's position is deeply embedded in a sizeable multi-line attribute value this way. Fixed by never routing the SVG through `@js()`/PHP-to-JS injection at all: the download handler now reads the already-rendered SVG straight back out of the DOM (`$refs.qrSvgHolder.innerHTML`), and the (short) connect URL + filename moved from inline `@js()` calls into plain `data-*` attributes on the component's own `x-data` root element, read via `$root.dataset.*` -- sidestepping the whole directive-inside-attribute scanning path for both values, not just the one that happened to overflow it first. Worth remembering generally: don't pipe a large PHP string through `@js()` inside a multi-line Alpine attribute on a Blade *component* tag -- prefer a `data-*` attribute (for a value Blade should render) or reading straight from the DOM (for a value that's already rendered there anyway).

### A second WAN link never actually got an IP address (2026-10-03)

**Live report**: after wiring a genuine second Starlink/ISP uplink into the router's configured `wan2` port (with `enable_second_wan` on), `/ip dhcp-client print` only ever showed one entry. Root cause: `generateFreshInfrastructureScript()`'s `enable_second_wan` branch added `$wan2` to the `WAN` interface list and gave it a NAT masquerade rule, but never created a DHCP client for it at all -- the two existing `$secondWanMember`/`$secondWanNat` conditional lines had no third sibling for the DHCP client, so WAN2 could reach the switch electrically but could never actually obtain an IP address, gateway, or route. Confirmed by direct code inspection (grepping the whole file for `dhcp-client` turned up only the pre-existing `$wan1` lines) rather than guessed at.

Fixed by adding a third conditional, `$secondWanDhcp`, mirroring `$secondWanMember`/`$secondWanNat`'s exact enabled/disabled-placeholder shape. Getting the *routing* right needed a second round, though: the first version gave `$wan2` `default-route-distance=2`, making it a pure backup RouterOS would only ever install once `$wan1`'s own route was withdrawn -- reasonable-sounding, but wrong for what was actually wanted, confirmed by a direct same-day follow-up ("hope it would still distribute load when the 2 WAN is up at same time"). Reverted to giving both DHCP clients `add-default-route=yes` at RouterOS's *implicit, equal* distance (no explicit `default-route-distance` on either) -- this is RouterOS's standard ECMP (Equal Cost Multi-Path) shape: two 0.0.0.0/0 routes at equal distance but different gateways/interfaces load-balance new connections across both links automatically, no PCC/mangle rules needed. `check-gateway=ping` on both clients (added to `$wan1`'s own line too, which never had it before) is what layers failover on top of that balancing -- when one gateway stops answering pings, RouterOS withdraws *that one* route from the table, leaving only the surviving link's route active until the dead one comes back, rather than silently routing traffic into a dead gateway. No live-API equivalent needed here -- per the existing "Bootstrap Script/auto-provisioning loop" scope note elsewhere in this file, WAN/DHCP-client setup only ever lives in the paste-by-hand Fresh Infrastructure Script, never in `RouterOsConnectionService`.

### A router offline for two days still showed "Recently seen ... 3 minutes ago" (2026-10-05)

**Live report**: a router confirmed down for two full days was displayed as "Recently seen" with a "3 minutes ago" timestamp -- not "Online" (so the heartbeat-reachable/active-session OR check was correctly returning false), but also not "Idle"/stale the way a genuinely dead router should read. Root cause, found by direct code inspection rather than guessed at: `RadiusAccountingStats::refreshRouterHealth()` used the single latest `RouterMetricSample`'s own `sampled_at` as a "last seen" candidate *unconditionally* -- but `RouterMetricSamplingService::sample()` writes a row every 5 minutes regardless of whether the ping actually succeeded (`latency_ms` is simply `null` on failure, per that method's own "always store a row, even if every value comes back null" docblock). `sampled_at` means "the last time we checked," not "the last time it actually responded" -- so a router that's been dead for days, but still being faithfully re-checked (and failing) every 5 minutes by the scheduler, produced a steady stream of recent samples that made it look perpetually "recently seen," with the displayed timestamp just drifting forward with each failed check.

Fixed by separating two different questions this code was conflating: `$sample` (the single latest row, used for the freshness/reachability check that drives `Online` status and the displayed current latency) stays exactly as before, but the last-seen candidate now comes from `$lastReachableSample` -- the most recent sample *where `latency_ms !== null`*, found via `Collection::first()` with a predicate over the already-fetched, already-`sampled_at`-descending group of samples per router (no extra query -- the rows were already being fetched, just discarding everything but the single newest one before). For a router that's actually dead, this correctly falls back to whatever the last *genuinely successful* ping was (hours or days ago, or `null` if there's never been one), landing on `'Idle / no recent sessions'` (or `'No data yet'`/`'Monitoring unavailable'`) instead of a falsely-reassuring `'Recently seen'`. Accounting-based last-seen (`acctupdatetime`/`acctstarttime`) was never part of this bug -- that's a real activity timestamp from FreeRADIUS, not a "did we attempt to check" one -- so only the heartbeat half of the `last_seen_at` computation needed to change.

**The self-service QR card became a real printable flyer, not just a code, the same week** (2026-10-05, direct request: "add some instruction to the print QR code, the steps from connecting to the ssid and make it ready to print like A4 portrait or landscape"). The card's markup is now the SAME box shown on screen and printed -- an admin previews exactly what will post at the shop before printing it, rather than a compact admin-only widget that only grows into a flyer at print time. It leads with the tenant/shop name, four numbered steps (connect to `{{ $router->provisioning_settings['hotspot_ssid'] ?? 'MMS Hotspot' }}`, open a browser for the sign-in page, pick a package or start the trial, scan the code anytime after to check balance/buy more/get a voucher), the QR itself (enlarged for print via `print:` Tailwind variants on the same `x-ref="qrSvgHolder"` element the download button already reads from -- no duplicate SVG markup), the link as text, and the shop's `contactPhone()` if one's saved. The print CSS gained `@page { size: A4 portrait; margin: 1.5cm; }` -- a hint, not a hard lock: every browser's own print dialog still offers a portrait/landscape toggle the user can override with one click, which is why no second custom landscape layout or JS orientation switcher was built -- the native dialog already solves that more reliably than CSS media-query tricks would.

### Admin staff can now retarget a subscription's MAC address when a phone's randomized MAC changes (2026-10-09)

**Direct report**: "I have issues of device mac randomize after connecting... Mostly i choose phone mac, then it'll take me to pay again." iOS/Android's per-network "private Wi-Fi address" feature can present a genuinely different MAC on a later reconnect than the one a customer originally paid under -- `PortalController::show()` finds no active `Subscription` for that new MAC and sends the customer straight back to the payment page for access they already bought. There's no way to prevent the OS from randomizing in the first place, so the fix is giving staff a way to retarget the existing paid subscription at the device's new MAC instead of the customer paying twice.

Added directly to the already-existing "Access Activity" inspect modal on `admin/subscriptions` (`App\Livewire\Admin\SubscriptionsIndex`) rather than a new page -- a "Change device" button next to the subscription's MAC/shop display switches it to an inline `flux:input` + Save/Cancel, mirroring this codebase's established inline-edit convention. `RadiusProvisioningService::changeSubscriptionMacAddress(Subscription $subscription, string $newMacAddress)` (new) does the actual work: normalizes the new MAC via the service's own `normalizeMacAddress()` (widened from `private` to `public` for exactly this reuse), updates the subscription row, re-grants RADIUS access to the new MAC via the same `grantSubscriptionAccess()`/`syncPackageProfile()` path a fresh purchase already uses -- but only when the subscription hasn't already expired, since there's nothing live to grant otherwise -- then revokes the old MAC's RADIUS rows via the existing `revokeMacAccess()`. That revoke already routes through `macStillClaimedElsewhere()` (the guard built for the POS/TrustedWifiDevice MAC-collision story elsewhere in this file), so if the old MAC happens to still be legitimately claimed by an active `PosDevice`/`TrustedWifiDevice`/another subscription, those rows are correctly left alone rather than wiped as a side effect of this change.

Since `subscriptions` has only a plain (non-unique) index on `[shop_id, mac_address]`, not a DB constraint, `SubscriptionsIndex::changeMacAddress()` explicitly guards against creating an ambiguous duplicate before saving: rejects a malformed MAC (after normalization, anything other than exactly 12 hex characters) with a clear validation error, and separately rejects a MAC that collides with *another* currently-active subscription at the same shop -- both checked before `changeSubscriptionMacAddress()` is ever called, and both scoped with `TenantAccess::assertSubscription()` so staff can't retarget a MAC on a subscription outside their own tenant.

### A paid-successful payment with no actual login record -- generate a recovery voucher, not a duplicate sale (2026-10-09)

**Direct follow-up the same day as the MAC-change feature above**: "mostly you see payment with mac address but no login record on access" -- the admin-reported pattern isn't a customer in front of staff with their new MAC in hand (that's `SubscriptionsIndex::changeMacAddress()`'s case), it's a **remote support call**: the Payment row is `successful`, the Subscription shows "Provisioned" with a future `expires_at`, but the device never actually authenticated under that MAC -- the same randomization story, except here nobody on the call knows the device's current MAC to retarget it directly. The explicit ask: "invalidate the mac address that made the payment and expect another mac to use voucher but still link to the payment" -- without creating a duplicate payment/sale record.

The existing voucher machinery already fit this almost exactly, once read closely: `Voucher::payment()` is a `hasOne`, `payments.voucher_id` is unique, and `VoucherManagementService::redeem()` already special-cases a voucher with a linked payment -- it reuses that **same** payment's id as the new Subscription's `payment_id` and updates that payment's own payload rather than ever creating a second one. So linking a brand-new one-off voucher to an *already-existing* successful payment (rather than a voucher driving the creation of a new payment, the only path that existed before) gets the "redeem under a new MAC, same payment, no duplicate" behavior for free from code that already works.

`VoucherManagementService::generateRecoveryVoucher(Payment $payment, User $user): Voucher` (new) validates the payment is `successful`, has no voucher already linked (the unique-constraint case surfaced as a clear validation message rather than a raw SQL error), has a linked `Subscription` at all, and that subscription hasn't already expired naturally (an already-expired one has nothing to "recover" -- generating a fresh full-duration voucher for it would hand out a second paid period for free). It then creates a 1-quantity `VoucherBatch` (prefixed `RCV-` so it's visually distinct from a normal pre-printed batch in every voucher list/report), a single `unused` `Voucher` in it, links it to the payment (`$payment->update(['voucher_id' => $voucher->id])`), and -- the "invalidate the old MAC" half of the ask -- expires the stuck subscription immediately and revokes its RADIUS rows via the existing `macStillClaimedElsewhere()`-guarded `revokeMacAccess()`, so a MAC that happens to still be legitimately claimed elsewhere (another active subscription, a PosDevice, a TrustedWifiDevice) is left alone exactly like every other revoke path in this codebase.

Surfaced on `admin/payments` (`PaymentsIndex::generateRecoveryVoucher()`) as a new "Recover access" button in the Action column, alongside the existing Confirm/Verify actions -- shown only when a payment is `successful`, has a subscription that's still within its paid window, and has no voucher linked yet (so it can't be clicked twice; a second attempt is also rejected server-side by the service, not just hidden client-side). The resulting code is shown in a copyable `<flux:modal>` (mirroring the 2FA recovery-codes `window.copyText()` pattern already used on the profile page) for the admin to read out over the phone -- the customer then redeems it themselves from the portal's own "Have a voucher?" box under whatever MAC their device actually presents, through the exact same `redeem()` path every other voucher already uses, no new redemption mechanism. One caught-early naming trap: `icon="life-buoy"` isn't a real Flux/Heroicon name here -- it's `lifebuoy`, no hyphen -- confirmed by checking `vendor/livewire/flux/stubs/resources/views/flux/icon/` directly rather than guessing, after the hyphenated version broke every page that renders the shared Livewire icon component (a `Flux component [icon.life-buoy] does not exist` exception at render time, not something caught by Pint or `php -l`).

### admin/subscriptions gained sortable date columns (2026-10-09)

Direct follow-up, same day as the ordering fix above: "sort by date ASC or DEC for Access window, Created." `SubscriptionsIndex` had no sortable-column precedent anywhere in the admin panel to copy, so this is a small, self-contained implementation rather than a new shared component -- there are exactly two date columns on this table (`expires_at` behind "Access window", `created_at` behind the "Created ..." sub-line on "Device"), and the allow-list in `sortByColumn(string $column)` is deliberately exhaustive for just those two, not a placeholder for more. Both the "Device" and "Access window" `<th>` headers are now clickable buttons with a `chevron-up`/`chevron-down`/`chevron-up-down` indicator (the neutral one shown on whichever column isn't currently active); clicking the already-active column toggles its direction, clicking the other one always starts descending (newest-created or furthest-expiring first) -- matching the convention most admins expect from a first click on a date column. `sortBy`/`sortDirection` are both added to the Livewire `queryString` map alongside the existing filters, so a sorted view is bookmarkable/shareable the same way a filtered one already is.

### Click-to-sort columns rolled out across every admin data table (2026-10-09)

Direct follow-up to the Subscriptions-only version above: "can we have those kind of sorting across all the data table." `App\Livewire\Concerns\SortsTable` is the new shared trait (`sortByColumn(string $column)` -- allow-list check, toggle direction on the already-active column, default to descending when switching columns, `resetPage()` if the component paginates) and `resources/views/components/admin/sortable-th.blade.php` is the matching `<x-admin.sortable-th column="..." :sort-by="$sortBy" :sort-direction="$sortDirection">` component (a clickable `<th>` with a `chevron-up`/`chevron-down`/`chevron-up-down` indicator) -- `SubscriptionsIndex` itself was refactored onto both first, as the proof that extracting them didn't change its already-shipped, already-tested behavior, before rolling out further.

Applied to every remaining admin index page that's an actual `<table>` (13 more: Shops, Routers, Packages, POS Devices, PPPoE Subscribers, Payments, Trusted Wi-Fi Devices, Tenants, Users, Vouchers, Expenses, Expense Categories, Security Activity) -- each component declares its own `$sortBy`/`$sortDirection` defaults (preserving that table's pre-existing order exactly, so a page nobody ever clicks a header on keeps behaving identically) and a `sortableColumns()` allow-list, since a column name gets interpolated directly into `orderBy()` and this is validated once in the trait rather than trusted per call site. Only *visibly rendered* columns were wired up -- e.g. Packages exposes name/price/limit_uptime_seconds/data_limit_bytes (all shown as their own header) but not the hidden default `created_at` sort some tables still fall back to; POS Devices/PPPoE Subscribers/Trusted Wi-Fi Devices all share the same shape (their "Status" column already showed an `expires_at` sub-line, so that's what became sortable, while their first column's hidden `created_at` default stays click-free since nothing in the row displays it). `Wallet`/`Wallet Withdrawals` were deliberately left out -- both are card lists, not `<table>`s, so there's no column header to attach a sort control to; forcing the pattern onto a layout shape it doesn't fit wasn't worth it.

A few tables needed a judgment call on *which* column represents a table's existing default order so the click target lines up with what was already happening: `ExpenseCategoriesIndex` keeps its platform-categories-first `orderByRaw('tenant_id is not null')` as a fixed primary sort, with the user's chosen column only ever breaking ties within that group (so switching "This Month"/"Expenses" sort never mixes platform and tenant-owned categories together); `VouchersIndex`'s withCount aliases (`vouchers_count`, `used_vouchers_count`, etc.) are valid `orderBy()` targets since Eloquent's `withCount`/`withSum` add them as real selected columns, so "Sold"/"Used"/"Unused"/"Voided" each sort correctly with no extra query changes; `RoutersIndex`'s "Status" header sorts by the same `is_online` boolean column its status filter already reads. Every page's regression test file (13 files, ~140 tests) passed unmodified, confirming the defaults genuinely didn't change for a page nobody interacts with the new headers on.

### Automated MAC-change recovery, opt-in per shop (2026-10-09)

Direct follow-up to the MAC-change/recovery-voucher features above: "since cookie or token survives what breaks the mac can we use that as automated recovery option... just to improve customer experience, so they don't have to contact support." The `hotspot_device` cookie (see the self-service QR-link feature above) already gets queued on every normal captive-portal visit, keyed to whatever MAC the device had *at that moment* -- and since it lives in browser storage, not the Wi-Fi radio, it survives exactly the event that breaks MAC-based identity (an OS randomizing the connected MAC for that SSID). That's the one signal available to bridge old-mac to new-mac automatically, with no admin or support involvement at all.

`PortalController::show()` now reads that cookie's MAC (the "previous" one) *before* re-queuing it with the current request's MAC, and `renderForMac()` -- right before its existing "does this MAC have an active subscription" check -- calls a new `attemptAutomaticMacRecovery()`: if the previous MAC still has a currently-active subscription, and the new MAC doesn't already have one of its own, it calls the exact same `RadiusProvisioningService::changeSubscriptionMacAddress()` the admin-facing "Change device" action uses, then logs the event. Since this updates the subscription's `mac_address` in place before the existing active-subscription query runs, the rest of `renderForMac()`'s logic (including the trial-vs-real-subscription branching) needed no changes at all -- it just finds the row under its new MAC as if nothing happened.

Gated behind a new `shops.auto_recover_mac_changes` column (default `false`), matching the exact "capability toggle, not forced on" pattern `allow_test_access`/`trial_enabled` already established for anything that changes the hotspot's access posture -- this is a real trust-model decision (automatically moving live RADIUS access based on an unauthenticated cookie claim) that a tenant should consciously opt into, not a silent behavior change for every shop. The abuse surface is bounded deliberately: Laravel signs/encrypts every cookie by default, so a client can't forge an arbitrary `{shop_id, mac}` pair without the app key; at most, a leaked cookie could move the single active-subscription slot to whoever holds it next -- the same bounded risk the manual "Change device"/recovery-voucher admin actions already carry today, not a new class of risk introduced by automating it. The "don't clobber a device that already has its own active subscription" guard is what keeps this from ever taking access away from a device that's already fine. Not yet confirmed against a real device's MAC rotation in production, matching this codebase's honesty pattern for other freshly-added behavior.
