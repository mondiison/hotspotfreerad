# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

HotspotFreeRAD (a.k.a. MMS Radius) is a multi-tenant SaaS for MikroTik hotspot/PPPoE billing built on Laravel 12 + Livewire 4 + Flux/Flux Pro, backed by FreeRADIUS 3 over a shared MySQL/MariaDB `radius` database. Tenants (ISPs/hotspot shop owners) manage shops, routers, packages, customers, vouchers, PPPoE subscribers, and POS devices; customers pay through a MikroTik captive portal to get provisioned into FreeRADIUS.

Read `docs/current-project-status.md` first in any new session — it is the up-to-date handover doc (stack, local dev quirks, deployment steps, "next good work"). `docs/roles-and-product-direction.md`, `docs/deployment-architecture.md`, `docs/router-onboarding.md`, and `docs/raspberry-pi-deployment.md` cover product rules and infra in depth. `README.md` and the root blueprint markdown are older/less current than `docs/current-project-status.md` — prefer the docs folder when they conflict.

## Commands

Local dev runs on port **8001** (other local projects use 8000):

```bash
php artisan serve --host=127.0.0.1 --port=8001
npm run dev            # Vite
```

Or run everything (server, queue listener, logs, vite) at once:

```bash
composer run dev
```

Tests:

```bash
php artisan test                                  # full suite
php artisan test --filter=AdminPaymentIndexTest    # single test class
php artisan test tests/Feature/HotspotPortalTest.php
```

Test env uses in-memory SQLite (`phpunit.xml`), not the real `radius` MySQL DB — safe to run anytime.

Build/lint:

```bash
npm run build          # production assets
vendor/bin/pint         # Laravel Pint code style (composer require-dev)
```

Useful recovery/maintenance commands (see `docs/current-project-status.md`):

```bash
php artisan optimize:clear
php artisan migrate
```

Custom Artisan commands live inline in `routes/console.php` (there is no `app/Console/Commands` directory — this is a Laravel 12 skeleton app). Notable ones: `hotspot:create-super-admin`, `hotspot:create-tenant-admin`, `hotspot:sync-expired-hotspot`, `hotspot:sync-expired-pppoe`, `hotspot:sync-expired-pos`, `hotspot:prune-security-activity`, `hotspot:backfill-voucher-payments`, `hotspot:scheduler-heartbeat`, `hotspot:sync-wireguard-peers`, `hotspot:sync-wireguard-routes`, `hotspot:sync-zerotier-members`, `hotspot:resync-walled-garden`. All but the first three are also registered on `Schedule::` in the same file (5-minute RADIUS expiry sync, 5-minute WireGuard peer sync, 5-minute WireGuard route sync, 5-minute ZeroTier membership sync, daily audit-log prune, per-minute scheduler heartbeat used by the Setup Center health check) — `hotspot:backfill-voucher-payments` and `hotspot:resync-walled-garden` are the exceptions, both on-demand-only (a one-off backfill and a manual remediation tool, respectively).

`hotspot:resync-walled-garden {router?} {--all}` re-pushes a router's walled-garden allow-list live over the RouterOS API, synchronously (unlike `SyncRouterWalledGarden` below, it doesn't need a queue worker running) — useful for immediately fixing an already-provisioned router without waiting on a gateway change to trigger the automatic job, or when `QUEUE_CONNECTION=database` locally and no worker is running to drain it.

## Architecture

### Two separate traffic paths — keep them mentally distinct

1. **Customer captive-portal path**: customer device → MikroTik → HTTPS redirect → `App\Http\Controllers\Hotspot\PortalController` (`routes/web.php`, `/hotspot/*`) → payment gateway → RADIUS provisioning.
2. **Router auth/accounting path**: MikroTik → WireGuard tunnel (or, per-router, an optional ZeroTier fallback tunnel — see the `tunnel_mode` note below) → FreeRADIUS 3 → the same MySQL `radius` database (`nas`, `radcheck`, `radreply`, `radacct`, `radusergroup`, `radgroupreply`, `radgroupcheck` tables). Laravel never proxies RADIUS traffic itself — it only writes rows FreeRADIUS reads. When both tunnels are active, RouterOS's own RADIUS client fails over between them by priority natively — the app never has to detect or route around a dead tunnel itself.

`App\Services\RadiusProvisioningService` and `App\Services\MikroTikProvisioningService` are the bridge: package/subscriber changes in the app get mirrored into the `radcheck`/`radusergroup`/`radgroupreply`/`nas` tables, and router onboarding generates a RouterOS script from stored provisioning settings.

`App\Services\StandaloneHotspotScriptGenerator` (2026-08-07, revised 2026-08-08) is a deliberately separate, unrelated code path — the "Script Generator" tool at `admin/tools/script-generator` (super admin only, gated by `abort_unless($request->user()->isSuperAdmin(), 403)` in `StandaloneScriptGeneratorController` the same way `TenantController`/`SecurityController` are). It generates a MikroTik hotspot config for routers that are **not**, and don't need to become, a `Router` record on this platform: no WireGuard, no HotspotFreeRAD RADIUS server, no API user, no shop/tenant binding. It branches on RouterOS 6 vs 7 wireless syntax (`/interface wireless` vs `/interface wifi`/wifiwave2) and wireless-vs-wired-only hardware via plain capability toggles in the wizard (`App\Livewire\Admin\StandaloneScriptGenerator`, a 5-step form) rather than a hardcoded router-model catalog — deliberately, since a real model database would need ongoing upkeep as new MikroTik boards ship. Every Ethernet port except the WAN port is bridged into the hotspot automatically (`ethernet_port_count` wizard field, parsed against `wan_port`'s trailing number), and "Router identity" (`/system identity`) is a separate wizard field from "Hotspot name" (the SSID/portal branding) since they're not always the same string. The whole flow is stateless: nothing is persisted, the wizard's Livewire state holds everything, and the result page renders both the copyable/downloadable `.rsc` script and a printable voucher sheet (`voucher_template`: `grid`, `compact`, or `receipt`) in one response via `@media print` CSS — there was no reason to add a database table for something meant to be filled in, generated, and printed/copied in one sitting.

Voucher validity is designed to start counting from a customer's **first login**, not from when the voucher was created — a real gap in the original version, fixed after specific network-engineer feedback plus MikroTik doc research. RouterOS 7 uses the built-in User Manager (`/user-manager`) as a **self-hosted local RADIUS server** pointed at `127.0.0.1` (never leaves the router, so this doesn't reintroduce a platform dependency) — its `profile.starts-when=first-auth` is the officially documented way to do this, and User Manager's richer object model (`limitation` / `profile` / `profile-limitation` / `user-profile` / `user` are five distinct objects, not one) is used deliberately instead of classic `/ip hotspot user profile`. RouterOS 6 has no equivalent, so classic hotspot users are used with an `on-login` script (`StandaloneHotspotScriptGenerator::onLoginExpiryScript()`) bound to the hotspot server profile that creates a one-time scheduler on a user's first login and removes the account when their validity window elapses — a well-established community pattern, not an official RouterOS feature, so it's commented as best-effort the same way other unverified RouterOS syntax is elsewhere in this codebase. Voucher codes support an optional prefix, configurable length, a choice of character set (`StandaloneHotspotScriptGenerator::CHARACTER_SETS` — safe alphanumeric, numeric-only, letters-only, or full case-sensitive), and whether the username and password should be the same or independently generated (`voucher_prefix`/`voucher_code_length`/`voucher_character_set`/`voucher_username_password_same`, all per profile) — mirroring MikroTik's own "Make Vouchers"/batch-user dialog shape (which has separate username-characters/password-characters options). `generateVoucherCodes()` returns `username`/`password` per voucher rather than a single `code`, and both script paths (`userManagerLines()`/`classicHotspotLines()`) and the print templates were updated accordingly — a print card shows one combined line when they're equal, or separate "User:"/"Pass:" lines when they're not.

When the management network is enabled, the generated script also restricts the router's own `www`/`www-ssl`/`winbox`/`ssh` services to that subnet (`/ip service set ... address=<mgmt-cidr>`) — this was originally going to be a custom "web Winbox" page built into this platform, but RouterOS's REST API sends no CORS headers (so a browser can't call it cross-origin from another domain) and a standalone router with no WireGuard tunnel isn't reachable from this app's backend at all. The better, lower-maintenance answer is to properly lock down and point admins at RouterOS's *own* built-in web tools (WebFig, and on v7 the User Manager page at `https://<router-mgmt-ip>/userman`) rather than rebuild them.

`App\Services\StandalonePtpScriptGenerator` (2026-08-08) is a second, equally self-contained standalone tool — the "PTP Radio Generator" at `admin/tools/ptp-generator` (super admin only, same `abort_unless($request->user()->isSuperAdmin(), 403)` gate in `StandalonePtpGeneratorController`, plus the same check again in `App\Livewire\Admin\StandalonePtpGenerator::mount()`). It configures a MikroTik point-to-point wireless bridge/backhaul link — unlike the hotspot tool's one router/one script, a PTP link inherently has two radios that must match (same frequency, channel width, SSID, security), so the 5-step wizard produces **two** scripts in one session (`generate()` returns `['script_a' => ..., 'script_b' => ...]`), one AP/master end and one Station end, either of which can independently be RouterOS 6 or 7. "Bridged" link mode uses `station-pseudobridge` rather than true `station-bridge`, deliberately — pseudobridge works across the widest range of MikroTik wireless chipsets, where true station-bridge needs matching driver support on both ends. `distance_km` sets RouterOS's `distance=` property (ACK-timeout auto-tuning for long links) — like the hotspot tool's on-login script, this is flagged in-script as best-effort/unverified against real hardware rather than presented as guaranteed-correct. The point-to-point subnet (`ptp_subnet`, e.g. a `/30`) is resolved with real CIDR bit math (`ptpSubnetParts()`, using `ip2long`/`long2ip` — deliberately not reusing `StandaloneHotspotScriptGenerator::networkParts()`, which assumes a gateway-first `/24` LAN input, not a narrow point-to-point subnet) to assign the first two usable host addresses to each radio; an optional per-radio route (`add_remote_route`/`remote_network`) points at "whatever's behind the other end" — intentionally scoped to that one static route rather than a routing protocol like OSPF. "Bridged" link mode was initially a real bug — it only flipped the wireless station mode to `station-pseudobridge`/`bridge` without ever creating a RouterOS bridge interface, so an admin using it would get no actual bridge to attach a LAN port to. Fixed via `bridgeLines()`: bridged mode now creates `bridge-ptp`, adds the wireless interface as a port, and addresses the *bridge* (not the raw wireless interface); routed mode is unaffected (no bridge, address stays directly on the wireless interface, each end keeps its own subnet). A bridge with only the wireless interface as a member still extends nothing, though — real feedback on a physical SXTsq Lite5 (single-Ethernet-port CPE hardware, where that one port *is* the LAN connection, not a spare) surfaced this — so each radio also gets an optional `lan_port` (default `ether1`, wizard step 2, shown only when bridged): when set, `bridgeLines()` adds it as a second bridge port and explicitly `/interface ethernet set <port> disabled=no` (belt-and-braces even though Ethernet ports are enabled out of the box). Left blank, the script instead emits a comment telling the admin to add one manually, rather than silently shipping a bridge that does nothing.

A factory-default wireless interface is administratively disabled, and RouterOS can reject `mode=`/`frequency=`/etc changes on a still-disabled interface even when `disabled=no` is in the *same* `set` command as those changes -- confirmed missing from a real script (the interface stayed down). `wirelessLines()` now issues an explicit `/interface wireless enable <interface>` (RouterOS 6) or `/interface wifi enable [find default-name=<interface>]` (RouterOS 7) as its own command *before* the `set`/`configuration=` line that changes mode/frequency, rather than relying on the inline `disabled=no` alone (kept anyway as a second safeguard).

A live "bad band or frequency" rejection (RouterOS 6, a genuinely valid frequency well inside the card's own hardware range) traced to `band`/`country`/`frequency-mode` never being set at all -- RouterOS validates a requested `frequency=` against the *currently-configured* band/country/frequency-mode, and a factory-default interface's `country` (default `etsi`) plus an unset `band` can reject an otherwise-fine frequency outright. Fixed by adding `country` (shared, required, free-text RouterOS country name, e.g. `no_country_set`), per-radio `band` (required, options depend on that radio's own `ros_version` -- `StandalonePtpGenerator::ROS6_BANDS`/`ROS7_BANDS`, since the two ends can be different RouterOS versions with different valid band strings), and `frequency_mode` (`regulatory-domain` default; `superchannel` bypasses country limits entirely and is flagged in-script as a compliance decision the operator is making deliberately) -- all set in the *same* `/interface wireless set` command as `frequency=`, since RouterOS validates a `set`'s properties against the resulting state, not the prior one. Also added, from the same "ask like a pro network engineer" pass: `wireless_protocol` (`802.11` default, `nv2` offered only when both radios are RouterOS 6 -- MikroTik's proprietary TDMA link protocol, no CSMA hidden-node contention or distance throughput penalty, only works between two MikroTik radios which is always true here); `hide_ssid` (default on -- no customer-facing reason to broadcast a backhaul link's SSID); `skip_dfs_channels` (RouterOS 7 only, default on -- avoids channels needing radar-detection CAC delays, better for a fixed link); and per-radio optional `antenna_gain_dbi` (RouterOS 6 only -- the equivalent RouterOS 7 `/interface wifi` property path couldn't be confirmed from documentation across the legacy `wifiwave2`/newer unified `wifi` packages, so it's deliberately left unset there rather than guessed). Separately, RouterOS 7's station role for a *bridged* L3 link was wrongly using plain `station` -- MikroTik's own docs say `station-bridge` is what "enables support for a 4-address frame format, so the interface can be used as a bridge port," which plain `station` doesn't; fixed to match RouterOS 6's existing `station`/`station-pseudobridge` split for the same distinction.

The AP end's RouterOS 6 legacy-wireless master mode is picked by `link_topology` (`'ptp'` default, or `'ptmp'`), not hardcoded — `ap-bridge` (RouterOS's true multi-client AP mode) needs a higher wireless license tier / AP-capable hardware, while `bridge` (single-peer master mode) is included in MikroTik's base/CPE license tier that ships on cheaper dish hardware like the SXTsq. The tool originally always used `ap-bridge`, which is why AP mode was rejected as "not supported" on a real SXTsq Lite5 (confirmed 2026-08-08) — a genuine point-to-point link only ever has one peer, so `ap-bridge` was never the right mode regardless of hardware. `'ptp'` now uses `bridge`; `'ptmp'` uses `ap-bridge` for a hub end meant to serve multiple stations (the wizard still only configures one AP + one Station script per session — a PtMP hub is just re-running the wizard once per additional station against the same AP). RouterOS 7's `/interface wifi` package has no equivalent split (`mode=ap` covers both topologies there, since that driver has no separate single-peer master mode).

Rather than teach the *service* about hardware models (which this codebase deliberately avoids — see the router wizard's rejection of hardcoded presets below), each radio in the wizard gets a `cpe_only` toggle whose meaning is topology-dependent: a CPE-only radio can still be the `'ptp'` AP end (bridge mode is base-tier), just not the `'ptmp'` AP end (ap-bridge needs the higher tier). `App\Livewire\Admin\StandalonePtpGenerator::updated()`/`reconcileApEndForTopology()` auto-flips `ap_end` to the other radio when the current AP end is CPE-only *and* topology is `'ptmp'` (whether that came from toggling `cpe_only` or from switching topology itself) — but won't flip to an equally-invalid CPE-only radio. Step-2 validation independently rejects, only under `'ptmp'`, both "a CPE-only radio selected as `ap_end`" and "both radios marked CPE-only" (no valid AP end left) as a safety net regardless of the auto-flip. `StandalonePtpScriptGenerator` itself stays unaware of `cpe_only` entirely -- by the time config reaches it, `ap_end` is already guaranteed valid for the chosen topology.

The two standalone tools (Script Generator, PTP Radio Generator) share one sidebar entry, "Tools" (`admin/tools/script-generator`/`admin/tools/ptp-generator` are still two separate routes/controllers/Livewire components — nothing consolidated server-side), with an in-page tab strip (`<x-admin.tools-tabs active="hotspot|ptp">`, `resources/views/components/admin/tools-tabs.blade.php`) linking between them via `wire:navigate`. Both routes already share the same nav "active" match pattern (`admin.tools.*`, from `$sectionPatternFor()` in the admin layout), so the single sidebar link correctly highlights on either page without any nav-logic changes.

`admin/docs` (super admin only, `App\Http\Controllers\Admin\DocsController` — same `abort_unless($request->user()->isSuperAdmin(), 403)` gate as Tools/Tenants/Security) renders the `docs/*.md` files inside the admin panel itself, so onboarding a new super admin or checking infra steps doesn't require leaving the app to browse the repo. `App\Support\DocsCatalog` is a read-only, framework-light lister/renderer: it only ever enumerates `*.md` files actually present under `base_path('docs')` and looks up a requested slug against that in-memory list (never re-derives a filesystem path from the request), so it can't be used to read anything outside that one folder. Markdown is rendered via Laravel's `Str::markdown()` (`league/commonmark`, already a framework dependency — no new package needed for parsing) with `html_input: strip` so raw HTML in a doc can't execute; the docs are trusted repo content, not user input, but stripping costs nothing and every doc's few literal HTML snippets (e.g. the login-page example in `router-onboarding.md`) live inside fenced code blocks, which CommonMark always escapes regardless of that setting. `App\Livewire\Admin\DocsIndex` is a single component (not the multi-controller "Tools" pattern) with a live-filtered search box (matches title or full content) and a master-detail layout: `$activeSlug` (synced to `?doc=` via Livewire's `#[Url]` for shareable/bookmarkable links) picks the doc shown in the content pane, while `$showListOnMobile` — a separate flag, not derived from `$activeSlug` — controls which pane is visible below the `lg` breakpoint, so mobile lands on the doc list first but a deep link (`?doc=...`) opens straight into that doc's content with a "Back to docs" control. The priority docs CLAUDE.md itself recommends reading first (`current-project-status`, `roles-and-product-direction`, `deployment-architecture`, `router-onboarding`, `raspberry-pi-deployment`) sort to the top of the list; anything else in `docs/` sorts after them alphabetically with no code change needed when a new doc file is added. Rendered content uses Tailwind's official `@tailwindcss/typography` plugin (`prose prose-zinc dark:prose-invert`) — the one addition to `package.json` this feature needed, since hand-rolling heading/list/code/table styling for arbitrary markdown wasn't worth it against a well-maintained, purpose-built plugin.

Router-to-Pi WireGuard connectivity is app-managed, not manual: `App\Models\Router` auto-generates a WireGuard keypair on creation (`App\Support\WireGuardKeyPair`, via `paragonie/sodium_compat` so it works without the native sodium extension), the private key is baked into the generated script instead of letting RouterOS pick its own, and `App\Services\WireGuardPeerSyncService` (run via the `hotspot:sync-wireguard-peers` scheduled command) reconciles the Pi's live WireGuard peers from the `routers` table. That command is inert everywhere by default (`WIREGUARD_MANAGE_PEERS=false`) and only does anything once enabled on the Pi per `docs/wireguard-server-setup.md`.

A router whose site is behind carrier-grade NAT (CGNAT — common on Starlink/mobile) can never form a WireGuard tunnel at all, since WireGuard has no relay/fallback of its own. `Router::tunnel_mode` (`wireguard` default, `wireguard_zerotier`, or `zerotier`) adds ZeroTier as a per-router opt-in fallback or replacement — ZeroTier has built-in NAT traversal with automatic relay fallback, which raw WireGuard categorically lacks. RouterOS has native ZeroTier support since 7.5+, but as a separate installable package restricted to **ARM/ARM64 hardware only** — this is why it's a router-level choice in the wizard (Identity step, alongside the WireGuard fields), never assumed available, the same "capability toggle, not a hardware model database" pattern as `enable_builtin_wifi`. Deliberately built around a **self-hosted ZeroTier network controller on the Pi**, not ZeroTier Central's cloud service — Central's free plan caps at 10 devices and has zero API access at all (Essential plan, $18+/mo, required for automated node authorization), while a self-hosted controller is free, uncapped, and its local API (`http://127.0.0.1:9993/controller/...`, loopback-only) needs no ZeroTier subscription. See `docs/zerotier-fallback-setup.md` for the one-time Pi bootstrap.

`App\Services\ZeroTierControllerService` was never exercised against a real controller before this shipped, and a live 2026-08-19 report of a router stuck `ACCESS_DENIED` after following the setup doc surfaced two real bugs at once, both now fixed: `setAuthorized()` (backing `authorizeMember()`/`deauthorizeMember()`) was POSTing `{"config": {"authorized": ..., "ipAssignments": [...]}}`, but ZeroTier's real controller API takes those fields flat at the top level and silently ignores an unrecognized `"config"` wrapper — the POST always returned HTTP 200, so every authorize call "succeeded" while never actually authorizing anything, the same class of bug as the RouterOS `!trap`-parsed-as-success issue above. Separately, `listMembers()` assumed `GET .../member` returns an array of full member objects; the real endpoint returns a flat `{address: revision}` map with no per-member detail at all, so it now does a second `GET .../member/{address}` per node (the same endpoint the POST already targets) to get each one's real `authorized`/`ipAssignments` — an N+1 pattern accepted here the same way `WireGuardRouteSyncService` accepts one-request-per-router, given this app's realistic router count. Since `ZeroTierMembershipSyncService::reconcile()` returns early on any `listMembers()` failure, this second bug meant the entire automatic authorization sync silently no-opped on any network that already had a member on it — not just a wrong-field-name issue.

`RouterOsConnectionService::client()` (the single choke point every other method in that file routes through) tries `candidateHosts($router)` in order — WireGuard IP first when applicable, then the ZeroTier IP — so live monitoring/"Provision via API"/etc. all get the fallback for free with no other call-site changes; `evilfreelancer/routeros-api-php`'s `Client` connects synchronously in its constructor, so a failed attempt throws immediately and the loop just tries the next host. `MikroTikProvisioningService::radiusClientLines()` emits one `/radius add` per enabled tunnel — RouterOS's own RADIUS client already fails over across multiple entries, tried in the order they appear in `/radius print`, so that's the entire "use ZeroTier whenever WireGuard fails" mechanism on the RADIUS side, no custom health-check scripting. RouterOS's `/radius` menu has **no `priority` property at all** — confirmed live 2026-08-19 (`unknown parameter priority`) after an earlier version of this line, and the live-API mirror of it, both emitted `priority=1`/`priority=2` for years with neither ever having been exercised against a real router. Correct WireGuard-before-ZeroTier ordering instead falls out for free from emission order alone (`radiusClientLines()` always writes the WireGuard line before the ZeroTier line), as long as an existing entry is never removed and blindly re-added. Since a dual-mode router might send RADIUS traffic from either IP, `RadiusProvisioningService::syncRouter()` writes a **second** `nas` row keyed to the ZeroTier IP (FreeRADIUS matches a NAS/client definition by the packet's source IP) — mirrored in `FreeRadiusClientSyncService::managedContent()`'s optional flat-file path for parity. `MikroTikProvisioningService::apiServiceAddressRestriction()` also extends the RouterOS API's allowed-address firewall rule to include the ZeroTier subnet in dual/ZeroTier-only mode — easy to miss, since without it the tunnel itself works but RouterOS's own firewall still only trusts the WireGuard subnet, so "Provision via API" and friends silently fail.

Switching an already-provisioned router's `tunnel_mode` (e.g. WireGuard-only → `wireguard_zerotier`) used to need the whole script re-pasted by hand — `RouterOsConnectionService::provisionHotspot()`/`provisionPppoe()` previously just blindly ran one `/radius/add` per enabled tunnel every time, with no idea what the router already had. Confirmed live (2026-08-19): re-provisioning a router after a tunnel_mode change would have added a genuine duplicate WireGuard entry alongside the new ZeroTier one. `syncRadiusClients()` replaces that with a real reconcile, mirroring `syncWalledGarden()`'s "list what's actually there first" shape: `desiredRadiusClients()` (pure) says what *should* exist for the current `tunnel_mode`, `planRadiusClientChanges()` (pure) diffs that against a live `/radius print`, and only the actual differences get pushed — `/radius/add` what's missing, `/radius/remove` an entry whose address is one of this app's own two known endpoints (`services.radius.server_ip` / `services.zerotier.pi_ip`) but is no longer desired, leave anything else alone entirely. An earlier version of this also tried to `/radius/set` a mismatched `priority` on an existing entry — removed the same day it was written, once the very first live "Provision via API" click against it came back `unknown parameter priority` (see the `radiusClientLines()` note above: that property was never real). Since there's nothing left to *fix* on a matched entry, "remove-scoped-to-known-endpoints" is the only mutation this performs on anything already present — an entry whose address matches *neither* known endpoint (an admin's own unrelated RADIUS client) is never touched, the same safety boundary `WireGuardRouteSyncService`'s `proto` tag provides for kernel routes, just keyed on address instead of a tag since RADIUS clients have no equivalent ownership marker.

Enabling ZeroTier and actually joining the specific network are two separate RouterOS steps — confirmed live 2026-08-19 from a router that had a real ZeroTier identity (enabled by hand for testing) but had never run `/zerotier interface add`, leaving it authorized on the controller yet permanently unconnected (`vMajor:-1` etc. in the controller's own member listing — never actually checked in). `RouterOsConnectionService::syncZeroTierNetworkMembership()` is the live-API equivalent of `MikroTikProvisioningService::zeroTierLines()`'s `/zerotier enable zt1` + `/zerotier interface add network=... instance=zt1` pair, wired into `provisionHotspot()`/`provisionPppoe()` as a no-op (zero steps, no connection attempt) for a router that doesn't use ZeroTier at all — checks the router's actual state first (`existingZeroTierState()`) so re-running it after the network is already joined is a safe no-op, not a second, likely-rejected "add". `self::ZEROTIER_INSTANCE_NAME` (`'zt1'`) assumes an instance by that name already exists by default on the router, matching `zeroTierLines()`'s existing assumption — confirmed true on the real hardware this was tested against, but not guaranteed universally. `mapZeroTierState()`'s `instance_disabled` check also needed a same-day fix: RouterOS's API frequently omits a boolean property entirely when it's at its `no`/false value rather than echoing it back explicitly, and the first version of this defaulted a missing `disabled` key to `'true'` — meaning a router with ZeroTier genuinely already enabled still got sent an unnecessary (if harmless) `/zerotier/enable`. Fixed to default a missing key to `'no'` instead, matching the one live-confirmed row shape actually seen (`disabled=no` shown explicitly for an enabled instance).

Both syncs make their own separate live connection attempt (to list current state) before the actual write attempt, on top of the several `provisionHotspot()`/`provisionPppoe()` already made — meaning "Provision via API" against a genuinely unreachable router now takes noticeably longer to report failure than before (confirmed: `test_provision_hotspot_reports_a_clear_error_when_router_is_unreachable` went from a few seconds to ~56s). Accepted deliberately: the reachable-router case (what this feature is actually for) only adds a small number of fast, local-network round trips, and a router that's genuinely offline was always going to end in failure regardless of how many attempts it takes to get there.

**The one real limitation, not hidden**: WireGuard automation works because the app generates a router's keypair *before* the router ever connects, pre-authorizing it centrally. ZeroTier is the opposite — a router generates its own node identity locally the first time `/zerotier enable` runs, which this app can't predict in advance, and a new node sits unauthorized on the (required-private) network until approved. `App\Services\ZeroTierMembershipSyncService` (via `hotspot:sync-zerotier-members`, same 5-minute/no-op-by-default pattern as the WireGuard sync, gated by `ZEROTIER_MANAGE_MEMBERS`) only ever authorizes node IDs this app already knows about; a node it can't attribute to any router shows up in that command's `unmatched_members` output instead of being silently ignored. `App\Livewire\Admin\RoutersIndex::fetchZeroTierNodeId()` covers the common case (a router still has working WireGuard) by reading `/zerotier print` back over that link automatically; a router with no working WireGuard at all needs its node ID entered by hand, once, from the router's own console. Ongoing operation is fully automatic either way — only *initial onboarding* of a ZeroTier-dependent router isn't 100% push-button the way pure-WireGuard onboarding is.

`fetchZeroTierNodeId()` originally parsed the node ID from a plain `address` field on `/zerotier print` -- another assumption never checked against real hardware, confirmed wrong 2026-08-19 via a live "no node-ID field was found" report. RouterOS's actual output has no such field; the node's own ID is the part before the first `:` in `identity` (or its public-only counterpart `identity.public`, e.g. `identity="69ae7250fc:0:<public-key-hex>:<private-key-hex>"`) -- both fields only surface via the RouterOS API's full property set, not the interactive terminal's default `/zerotier print` column view (which only shows `NAME`/`PORT` unless you add `detail`, a purely cosmetic CLI difference that has no bearing on what the API itself returns). Fixed to prefer `identity.public` over `identity` when both are present, purely so a parsing failure never has private key material to leak.

Staff/Management Wi-Fi (WPA-PSK SSIDs, distinct from the open customer hotspot) gets a second access control layer beyond the shared password: `App\Models\TrustedWifiDevice` (admin: `admin/trusted-wifi-devices`) registers devices by MAC per shop/network (`staff`|`mgmt`), synced into `radcheck` via `RadiusProvisioningService::provisionTrustedWifiDevice()`. For the MikroTik built-in Wi-Fi test profile (`l009_builtin_wifi`), the script generator also emits a local `/interface wifi access-list` allow/deny list from the same registered devices — regenerated on demand, not live-pushed to the router. See `docs/staff-wifi-access.md` for the external-AP RADIUS MAC-auth path and its current limitations.

An external AP's RADIUS MAC-auth requests only reach the Pi if the router's LAN/VLAN subnets are actually routed through the WireGuard tunnel — by default only the router's own `/32` tunnel IP is (`WireGuardPeerSyncService::desiredPeers()`), which is exactly the gap `docs/staff-wifi-access.md` used to flag as unresolved. `provisioning_settings.route_lan_through_tunnel` (per-router opt-in, Network plan step of the wizard) closes it: when enabled, `desiredPeers()` widens that router's `AllowedIPs` to include its `mgmt_network`/`staff_network` CIDRs alongside its `/32`. Widening `AllowedIPs` alone isn't sufficient, though — `wg set` (used for all runtime peer updates, since this Pi's `wg-saas.conf` has no `[Peer]` blocks at all) doesn't create a kernel route the way `wg-quick up` would from a config file at startup; that's only invisible today because every existing peer IP already falls inside `wg-saas`'s own directly-connected `10.8.0.0/24` subnet. A router's mgmt/staff VLAN isn't part of that subnet, so `App\Services\WireGuardRouteSyncService` (via `hotspot:sync-wireguard-routes`, gated by its own `WIREGUARD_MANAGE_ROUTES` flag — deliberately separate from `WIREGUARD_MANAGE_PEERS` since this one touches the kernel routing table) also manages an explicit `ip route` per opted-in router's subnets. Every route it touches is tagged `proto hotspotfreerad` (registered once in `/etc/iproute2/rt_protos` — `docs/wireguard-server-setup.md`), which is what makes automatic *removal* safe here unlike `WireGuardPeerSyncService` (which deliberately never removes a peer) — reconciliation only ever reads/writes routes carrying that tag, so it can never touch the interface's own connected route or anything added by hand. Not yet verified against a real Pi.

Since every router's `mgmt_network`/`staff_network` defaults to the exact identical literal subnet regardless of profile (`RouterManagementService::defaultProvisioningSettings()`) and WireGuard's `AllowedIPs` must be unique/non-overlapping per peer on a given interface, `RouterManagementService::lanRoutingOverlapRule()` validates a router's subnets against every *other* router that also has `route_lan_through_tunnel` enabled (via the new `App\Support\CidrOverlap` pure helper) before allowing the save — routers that don't use this feature are unaffected by each other regardless of subnet collisions.

Registering a Trusted Wi-Fi Device requires already knowing its MAC address, and there was previously no way to see what's actually connected — a real gap surfaced 2026-08-09 by a live report of devices joining Management Wi-Fi with just the shared password and never showing up anywhere. `RouterOsConnectionService::dhcpLeases()` (a router's `/ip/dhcp-server/lease/print`, optionally filtered `where('server', ...)`) backs a new "Connected Devices" section on a router's Live tab (`App\Livewire\Admin\RouterConnectedDevices`, `resources/views/livewire/admin/router-connected-devices.blade.php`), letting an admin browse live leases per network (`mgmt`/`staff`/`pos`/`hotspot`) and one-click "Register as trusted" (mgmt/staff only, reuses `TrustedWifiDeviceManagementService::create()` as-is). This is **DHCP-lease-based, not wireless/wifi registration-table-based**, deliberately: a registration-table query only ever shows clients associated to the MikroTik's own radio, which stops working the moment a network's AP is an external device (e.g. Ruijie) bridged into the same VLAN instead — DHCP leases are recorded by the router regardless of which physical AP the client came through. This feature is visibility-only — it does not change or fix the enforcement gaps documented in `docs/staff-wifi-access.md` (the built-in Wi-Fi access-list still isn't auto-pushed to the router, and external-AP RADIUS MAC-auth still has the WireGuard LAN-routing gap); the "Register as trusted" action's flash message says as much rather than implying it blocks anything.

Live router monitoring (as opposed to the WireGuard/RADIUS provisioning above) needs to talk to the router directly, not just write RADIUS rows. `App\Models\Router` also auto-generates a RouterOS API user/password on creation (`api_username`/`api_password`, mirroring the WireGuard keypair pattern), baked into the generated scripts by `MikroTikProvisioningService::apiUserProvisioningLines()` and restricted to the WireGuard subnet only. `App\Services\RouterOsConnectionService` (wrapping `evilfreelancer/routeros-api-php`, which needs `ext-sockets`) is the single place that opens a live RouterOS API connection, always with short timeouts so an offline router fails fast instead of hanging a request. Historical bandwidth graphs (`App\Support\RouterUsageHistory`) need none of this — they read existing `radacct` data. CPU/RAM/disk/health/uptime history (`router_metric_samples`, populated every 5 minutes by `hotspot:sample-router-metrics` / `App\Services\RouterMetricSamplingService`) mixes both: latency is a plain ICMP ping needing no RouterOS API at all, while CPU/RAM/disk/health do. Router health alerts (`App\Notifications\RouterAlertNotification`, `implements ShouldQueue`) fire from state *transitions* detected in `RouterMetricSamplingService` (offline/online/high CPU/high RAM) — edge-triggered, not repeated every sample while a condition persists. In-system (database) delivery is always on; email is gated per-user by `User::notify_by_email` inside `via()`. Recipients are every super admin plus the tenant admins of the router's tenant. Being queued, delivery goes through the existing persistent `hotspotfreerad-worker` systemd service (`docs/raspberry-pi-deployment.md`), not a cron-triggered send. See `docs/router-monitoring.md`, including the honest caveats on Wi-Fi scan session cleanup, hardware-health field variability, and the topology view's deliberately-limited scope (org hierarchy, not physical LLDP discovery).

The API user's group policy used to be `read`-only (deliberately denying `write`) since it was originally scoped just for monitoring — but `RouterOsConnectionService::provisionHotspot()`/`provisionPppoe()`/`syncWalledGarden()` all issue genuine write commands (`/radius/add`, `/ip/hotspot/*/add`, `/ip/hotspot/walled-garden/add`), which RouterOS silently rejected under that policy. Compounding it, `evilfreelancer/routeros-api-php`'s `Client::read()` parses a RouterOS `!trap` (rejected command) identically to `!done` (success) and never throws — so `RouterOsConnectionService::runSteps()`/`applyHotspotProfile()` reported every one of those rejected writes back to the admin as a success ("walled garden synced" with nothing actually changed on the router). Found 2026-08-07 from a live report of "Provision via API" appearing to succeed with no effect on the physical router. Fixed both halves: the policy now grants `write` (`apiUserProvisioningLines()`), and `runSteps()`/`applyHotspotProfile()` now call `read(false)` (raw, unparsed) and check for a `!trap` block via the new `RouterOsConnectionService::extractTrapMessage()` before reporting a step successful. A router bootstrapped before this fix needs its script re-run (or just the `/user group set` policy line re-applied) before any API write will actually take effect — `hotspot:resync-walled-garden` (see Commands) is the quickest way to re-push and get an honest success/failure result now. `syncWalledGarden()` also lists the router's existing walled-garden entries first and only sends `/add` for hosts genuinely missing (`RouterOsConnectionService::missingWalledGardenEntries()`) — RouterOS doesn't dedupe `dst-host` on its own, so re-running a sync repeatedly used to keep piling up duplicate entries.

`html-directory=flash/hotspot` and `dns-name=<hotspot_dns_name>` are both set on the hotspot profile (`apiUserProvisioningLines()`'s sibling, the hotspot-profile step in `provisionHotspot()`), but RouterOS does **not** redirect hotspot logins to an external URL on its own just because `dns-name` is set — the local `flash/hotspot/login.html` file itself has to do that, or customers "log in" against RouterOS's own stock local form and never reach this app's portal, payment gateways, or RADIUS provisioning at all. That file used to require a manual copy/paste per router (still documented as a fallback in `docs/router-onboarding.md`'s from-scratch walkthrough) — as of 2026-08-09, `RouterOsConnectionService::pushHotspotLoginPage()` automates it as another `provisionHotspot()` step: the router `/tool fetch`es a small redirect-stub HTML from `GET /hotspot/login-page` (`PortalController::loginPage()`, content from `MikroTikProvisioningService::hotspotLoginPageHtml()`) into a local directory. The stub carries MikroTik's own login-time variables (`$(mac)`/`$(identity)`/`$(link-login)`/`$(link-orig)` — substituted by RouterOS when it serves the file, not by Laravel) into the real portal URL via a `window.location.replace()`. It has no per-router content at all — every router fetches the exact same file, since there's only one portal host per install (`MikroTikProvisioningService::loginPageUrl()`, built from the same host as `portalUrl()` rather than Laravel's `route()`/`APP_URL`, so it stays correct if `HOTSPOT_PORTAL_URL` points at a different public host). `/tool fetch` was chosen over trying to write file content through the RouterOS API directly — the binary API has no reliable cross-version way to do that, whereas every router already has outbound reach to the portal host (the same host its own walled-garden entries allow customer devices to reach), so having the router pull the file itself is simpler and more reliable. Needs no new API user policy — `test` (which `/tool fetch` requires) was already granted.

The automatic `provisionHotspot()` step pushes to `RouterOsConnectionService::DEFAULT_HOTSPOT_DIRECTORY` (`flash/hotspot`) — correct for a router freshly onboarded through this app (that's exactly what `saas-prof`'s own `html-directory` is), but **not** guaranteed for a router that already had a hotspot server set up another way (MikroTik's own `/ip hotspot setup` wizard, a differently-named profile, or an older/different RouterOS version — confirmed live: the same file shows as `hotspot/login.html` with no `flash/` prefix on some routers). Blindly hardcoding the destination would silently write into a directory RouterOS never actually serves from, leaving the admin thinking it's fixed when nothing changed on the live router. `pushHotspotLoginPage(Router $router, ?string $directory = null)` takes an optional directory override, and `RouterOsConnectionService::listHotspotDirectories()` (`/file/print` filtered to `type=directory`) lets an admin see a router's real directory layout instead of guessing — both back a standalone "Hotspot Login Page" section on the router's Live tab (`App\Livewire\Admin\RouterHotspotLoginPage`, `resources/views/livewire/admin/router-hotspot-login-page.blade.php`) alongside Wi-Fi Scan/Connected Devices/Console: list directories, pick one (or type one manually), push. Re-running "Provision via API" re-pushes to the default directory, which is also the recovery path if a firmware update or manual edit changes that specific file — the standalone section is for when the default directory itself is wrong.

Pushing the login page live failed with RouterOS's `failure: cannot open file: permission denied` (confirmed 2026-08-09) even though the write-policy fix above already grants `write` — because `/tool fetch dst-path=...` writing to local storage is gated by RouterOS's confusingly-named `ftp` policy flag, not `write`. `ftp` is a holdover name from when file transfer/backup only happened over literal FTP; it does **not** enable the FTP *service* (this app never touches `/ip service ftp`), it gates local file-system write access generally. The API user's policy denied it (`!ftp`) on an original least-privilege assumption made before this account needed to touch files at all. Fixed by granting `ftp` in `apiUserProvisioningLines()`'s policy string. Same remediation as the write-policy fix: a router bootstrapped before this needs its script re-run, or just `/user group set [find name=mmsradius-api-group] policy=<the new string>` pasted directly on the router.

### Tenant scoping is manual, not a global scope

There is no Eloquent global scope for tenancy. Every tenant-scoped query/authorization goes through the static helpers in `app/Support/TenantAccess.php` (`scopeShops`, `scopeRouters`, `scopePackages`, `assertShop`, `assertRouter`, etc.), each of which special-cases `$user->isSuperAdmin()` to bypass the `tenant_id`/`shop.tenant_id` filter. When adding a new tenant-owned resource, add a matching `scopeX`/`assertX` pair here rather than filtering ad hoc in the controller. Controllers also gate super-admin-only actions with inline `abort_unless(request()->user()->isSuperAdmin(), 403)` (e.g. `TenantController`) — this stays true for `super_admin` vs `tenant_admin`. **`TenantAccess` answers "which rows can this actor see," not "can this actor perform this action"** — that second question is what the `tenant_staff` role below needs, and it's a separate mechanism.

Three roles: `super_admin` (platform owner, no `tenant_id`), `tenant_admin` (full access to one `tenant_id`), and `tenant_staff` (scoped to one `tenant_id` like `tenant_admin`, but further restricted to specific feature areas). Staff authorization is the one place this codebase DOES use route-level middleware: `App\Http\Middleware\AuthorizeTenantStaff` wraps the entire `admin.*` route group in `routes/web.php` and checks each request's route name against the deny-by-default map in `App\Support\StaffPermissions::forRoute()` (`User::canAccessRoute()` is the model-side helper it and the sidebar nav both call). Super admin and tenant admin are unaffected — the middleware is a no-op for them. When adding a new admin route that staff should ever reach, it needs a deliberate entry in that map; nothing is allowed by default. See `docs/roles-and-product-direction.md` for the full rule set and the permission catalog.

### Request flow: thin controllers, fat services

`app/Http/Controllers/Admin/*` and `app/Livewire/Admin/*` stay thin and delegate business logic to `app/Services/*ManagementService.php` (e.g. `PackageManagementService`, `RouterManagementService`, `PppoeSubscriberManagementService`, `PosDeviceManagementService`, `VoucherManagementService`). Reporting has its own service layer (`SalesReportService`, `PaymentReportService`, `SubscriptionReportService`, `SecurityActivityReportService`). Livewire is used for interactive index/filter/table components; plain controllers handle CRUD resources and exports.

The real, tenant-bound router create/edit form (`admin/routers` — not the unrelated standalone script generator) is a 4-step wizard on `App\Livewire\Admin\RoutersIndex` (2026-08-08), not a single flat form: Identity, Hardware (wireless yes/no + port count/roles), Features (POS/PPPoE/QoS + conditional wireless credentials), Network plan. `App\Http\Controllers\Admin\RouterController::create()`/`edit()` now just redirect into this wizard (`?open=create` / `?open_edit={id}`) instead of rendering their own page — the old parallel full-page form (`admin/routers/form.blade.php`) was deleted since maintaining a second, independently-drifting implementation of the same step-gated/conditional form wasn't worth it; `store()`/`update()` and `RouterManagementService::validated()` are kept as-is for non-Livewire regression coverage, just no longer linked from the UI. Wireless-only fields (`builtin_wifi_interface`, `mgmt_wifi_password`, `staff_wifi_password`, `pos_wifi_password`) and POS/PPPoE network fields only render when their matching `enable_*` toggle is on, backed by `required_if` rules in `RouterManagementService::rules()` so they can't be saved blank while enabled.

Ports are no longer typed as raw interface-name strings by default — `App\Support\RouterPortLayout` (pure, static, framework-free) turns a `port_count` into numbered dropdown options (`portOptions()`) and reverse-derives a port number from an existing `"etherN"` string (`portNumberFromInterfaceName()`, returns `null` for anything that doesn't match, e.g. `sfp-sfpplus1`). `RouterManagementService::derivePortInterfaceNames()` converts `wan1_port_number`/`wan2_port_number`/`trunk_port_number`/`pi_port_number` into the `wan1`/`wan2`/`trunk_port`/`pi_port` strings `MikroTikProvisioningService` actually reads — that service needed zero changes, since it still just reads plain interface-name strings. An "advanced: type interface names manually" toggle (`ports_advanced_mode`) bypasses all of this for non-standard interfaces. On edit, `RoutersIndex::routerProvisioningSettings()` reverse-derives port numbers from a router's saved strings so the dropdowns open pre-selected; if any of the four doesn't cleanly parse, it opens in advanced mode instead of guessing wrong — and a router that's never re-edited keeps generating byte-identical scripts, since the derivation only overwrites a string when its `*_port_number` was actually submitted (a real bug caught during this work: `RouterManagementService::validated()` used to call `normalize()` and then `create()`/`update()` called it *again*, so the second pass saw the first pass's defaulted port number as if it had been explicitly submitted and clobbered manually-typed strings like `sfp-sfpplus1` — fixed by making `validated()` return unnormalized data and letting `create()`/`update()` be the single normalization point).

The `provisioning_settings.profile` preset used to include `l009_builtin_wifi`, a preset literally named after a specific MikroTik board — removed in favor of the independent `enable_builtin_wifi` toggle (any of the remaining `starlink_plaza`/`small_hotspot`/`pppoe_isp` bandwidth/VLAN templates can have wireless on or off now). A data-only migration (`2026_08_07_120000_remap_l009_builtin_wifi_router_profile.php`) rewrites just the `profile` key on already-saved rows to `small_hotspot`, leaving every other field (`wan1`/`wan2`/`enable_builtin_wifi`/etc.) untouched — those were already fully materialized per-row at save time, not re-derived from the profile string, so this is cosmetic for existing routers, not a behavior change.

### Payment gateways

Two independent gateway stacks exist, both selected/configured per entity via `App\Support\PaymentGatewayCatalog`:

- **Tenant/shop-level hotspot checkout** (customer paying for hotspot/PPPoE/POS access): `FlutterwaveService`, `PaystackService`, `MonnifyService`, `SquadService`, `StripeService`, `ManualBankTransferService`, orchestrated by `App\Services\Payments\HotspotHostedCheckoutManager` implementing `App\Services\Payments\Contracts\HotspotHostedGateway` per provider, confirmed via `HotspotPaymentConfirmationService`. Entry points are the `/hotspot/pay`, `/hotspot/payment/*` routes on `PortalController`.
- **Platform billing** (tenant paying HotspotFreeRAD for their subscription plan): `PlatformFlutterwaveService`, `PlatformStripeService`, confirmed via `PlatformBillingConfirmationService`. Entry points are the `/billing/*` routes on `Admin\BillingController`.

Webhook routes (`/hotspot/payment/webhook`, `/billing/payment/webhook`) are explicitly excluded from CSRF (`withoutMiddleware([ValidateCsrfToken::class])`) since gateways POST to them directly — keep that exclusion narrow if adding new webhook routes.

A shop has exactly one active gateway at a time (`Shop::paymentGateway()`, defaults to `flutterwave`), not a menu of simultaneously-enabled gateways — `resources/views/hotspot/portal.blade.php` reads it directly (`$shop->paymentGatewayName()`/`paymentGatewayLogoUrl()`) to show the customer which gateway they're paying through, and only Flutterwave gets the OPay/Transfer/Card sub-choice (the other gateways route through `HotspotHostedCheckoutManager` regardless of `payment_method`). Because 5 of the 6 gateways redirect the customer's browser to an external hosted checkout domain *before* the device is RADIUS-authenticated, each gateway also carries `walled_garden_hosts` metadata in `PaymentGatewayCatalog` — `MikroTikProvisioningService::walledGardenLines()` emits `/ip hotspot walled-garden add dst-host=...` entries for the router's shop's active gateway (plus the portal host and `*.cloudflare.com`) in both `generateScript()` and `generateFreshInfrastructureScript()`. Those host lists are best-effort, based on each provider's known public checkout domains — not verified against a live checkout flow from this codebase.

A router whose walled-garden entries don't cover its shop's active gateway fails checkout hard, not gracefully: MikroTik can rewrite the captive-portal login redirect into unencrypted HTTP responses, but for HTTPS destinations outside the walled garden it can't inject anything into the encrypted stream, so it resets the connection instead — the customer sees `net::ERR_CONNECTION_CLOSED` at "Continue to payment" rather than a redirect to login. This only self-heals on routers that get a fresh script paste or a manual "Provision via API" click; a shop that switches gateways without re-provisioning its routers silently breaks checkout (diagnosed 2026-08-07 from a live Squad report — Squad's own domains were already covered by the `*.squadco.com` wildcard, the router just never got the new gateway's entries pushed). Two fixes: `RouterOsConnectionService::provisionHotspot()`'s live API push now also walled-gardens the shop's active gateway (it previously only added the portal host, so even the manual remediation path was incomplete) via a new public `syncWalledGarden()` method it shares with the fix below; and `PaymentSettingsService::update()` now diffs the shop's `payment_gateway` before/after and, when it changed, dispatches `App\Jobs\SyncRouterWalledGarden` (queued, default queue — picked up by the existing Pi worker with no deployment change) for every router the shop owns, so switching gateways in Payment Setup re-syncs live routers automatically instead of requiring a manual re-provision.

`PaymentSettingsService::updates()` **merges** newly-submitted `gateway_settings` into a gateway's existing saved settings rather than replacing the sub-array wholesale (fixed 2026-08-06 — it used to silently wipe every field not resubmitted that save, e.g. losing a saved secret key just from switching the Environment dropdown, contradicting the form's own "leave blank to keep saved value" placeholder text). Any future gateway-settings save logic should keep this merge behavior.

All four online gateways (Squad, Monnify, Paystack, Stripe) carry an `environment` field in `PaymentGatewayCatalog`'s `select_fields` (`live`/`test`, defaulting to `test`) — a per-gateway field that renders as a `flux:select` in `PaymentSettingsCard` instead of a free-text credential input, is excluded from `tenantReadiness()`'s badges (it's a preference, not a "missing credential"), and is validated with a strict `Rule::in()` in `PaymentSettingsService` on top of the generic `gateway_settings.*` wildcard rule. It is only *functional* for Squad and Monnify, which have genuinely different API base URLs per mode: `SquadService`/`MonnifyService::baseUrl()` take `Payment $payment` and pick `config('services.<gateway>.live_base_url')` or `.base_url` (sandbox) based on the shop's saved `environment` — there's no platform-wide `.env`-only base URL forcing every tenant onto the same environment anymore.

Paystack and Stripe share ONE API host regardless of mode — the secret key's `sk_test_`/`sk_live_` prefix is the only thing that actually determines live vs test, so their `environment` field does not change any base URL; it's saved purely for the admin's own reference (2026-08-06, added after a user request for a consistent field across all four gateways). Because an independently-editable field can drift out of sync with the actual key (pick "Live" while a `sk_test_` key is still saved), `PaymentGatewayCatalog::detectedEnvironment(?string $secretKey)` derives the real live/test state straight from the key prefix, and `PaymentSettingsCard` shows it as a read-only badge ("Detected: Live key" / "Detected: Test key" / "Environment not detected") next to the Secret Key field, plus an inline warning under the Environment dropdown when the two disagree. `PaymentSettingsCard::KEY_DETECTED_ENVIRONMENT_GATEWAYS` is the list of gateways this detection applies to (currently `paystack`, `stripe`) — add a gateway there only if it shares this one-URL-plus-key-prefix shape.

`App\Livewire\Admin\PaymentSettingsCard` is the single place gateway credentials/environment are edited (2026-08-06) — it used to be duplicated as hardcoded Flutterwave-only fields on the separate Shops CRUD (`App\Livewire\Admin\ShopsIndex`'s edit flyout and `Admin\ShopController`'s full-page form), which had no way to configure Squad/Monnify/Paystack/Stripe at all despite letting you pick them as the active gateway. Both Shop edit surfaces now embed `<livewire:admin.payment-settings-card>` directly (as a sibling section after the shop-details `<form>`, never nested inside it — Livewire's own `<form wire:submit="save">` inside another `<form>` is invalid HTML) once the shop exists; `App\Services\ShopManagementService` was stripped down to just `tenant_id`/`name`/`location_city`/`is_active` accordingly. A shop must be saved once before its payment settings can be configured.

### Packages and RADIUS attribute mapping

Packages carry bandwidth, uptime, and optional data caps/FUP. When synced to RADIUS: `Mikrotik-Rate-Limit` = bandwidth, `Session-Timeout` = uptime (seconds), `Mikrotik-Total-Limit`/`Mikrotik-Total-Limit-Gigawords` = data quota. Data values are stored/compared in raw bytes (see unit table in `docs/roles-and-product-direction.md`). `NAS-Identifier` on the router must exactly match the router's stored identity — mismatches are the most common "router not registered" support issue.

### Expiry/cleanup model

Hotspot subscriptions, PPPoE subscribers, and POS devices are each revoked from RADIUS by a scheduled command (see Commands section) rather than by a live TTL in FreeRADIUS — the `Schedule::command(...)->everyFiveMinutes()` jobs in `routes/console.php` are what actually cut off expired access. If a feature depends on "access should end at time X," it needs a corresponding scheduled sync, not just an `expires_at` column.

### Dark mode

The admin panel (`resources/views/components/layouts/admin.blade.php`) has a manual Light/Dark/System toggle using Flux's built-in `@fluxAppearance` directive/dropdown pattern (`$flux.appearance`, `x-on:click="$flux.appearance = '...'"` in the header) — `@fluxAppearance` already handled `.dark` class toggling, localStorage persistence, system-preference following, and flash-of-wrong-theme prevention before this work; it just had zero `dark:` classes anywhere to make any of that visible. Auth pages (login, forgot-password, reset-password, two-factor-challenge, force-password-change), `welcome.blade.php`, and `tenants/public-site.blade.php` follow system preference only, via the same directive with no toggle UI rendered — these are quick/standalone documents where a visible toggle isn't worth the UI real estate. The customer-facing hotspot captive portal (`resources/views/hotspot/*.blade.php`) is deliberately excluded entirely — it's already a fixed `bg-zinc-950 text-white` dark brand aesthetic, not a light-mode page needing a dark counterpart.

Elevation hierarchy used throughout: body (darkest, `dark:bg-zinc-950`) → card/sidebar/header panels (`dark:bg-zinc-900`) → subtle backgrounds/hover/badge surfaces (`dark:bg-zinc-800`) → borders (`dark:border-zinc-700`, or `dark:border-zinc-800` for very subtle dividers). Separately, several UI patterns use `zinc-950` as a light-on-dark **accent** (selected cards, active tabs, primary CTA buttons, progress-bar fills, file-input buttons, avatar chips) rather than a body/surface tone — these need **inversion** (`dark:bg-zinc-100 dark:text-zinc-900` or similar) instead of the elevation rule, since a near-black accent against an already-near-black dark body has poor contrast. When adding new UI, classify which bucket a `zinc-950`/`bg-white`/`bg-zinc-100` token falls into before picking its `dark:` pair rather than applying the elevation rule uniformly.

## Known environment quirk

Local XAMPP MariaDB has previously hung due to a crashed `mysql.db` table; if the app hangs on load, check MySQL first and repair with `aria_chk` before assuming an app bug (see `docs/current-project-status.md`).

## Real infra values are not in this repo

`mondiison/hotspotfreerad` is a **public** GitHub repo, so real WireGuard endpoints, public keys, and RADIUS server IPs must never be committed here — the docs in `docs/` intentionally use placeholder values. The actual live values (WireGuard endpoint/port/public key, RADIUS server IP, known `.env` gotchas) are recorded locally in `.local-notes/infra-settings.md`, which is git-ignored. Check that file before re-deriving these from scratch or asking the user to repeat them; it only exists on this machine, not on the Pi or a fresh clone.
